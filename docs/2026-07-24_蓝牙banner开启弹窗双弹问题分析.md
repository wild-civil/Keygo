# 蓝牙 Banner「开启蓝牙」弹窗问题分析与方案评估

> 日期：2026-07-24 ｜ 关联提交：fix11(`b48389f`) 之后 ｜ 范围：App（`stores/ble.js` / `utils/ble.js` / `App.vue` / `pages/index/index.vue`）
> 背景：用户实测发现①冷启动蓝牙未开时系统「开启蓝牙」弹窗连弹两次（几乎必现）；②极少情况下点开启后红 banner 复现。本文先分析现状与根因，再评估方案 A 的利弊。

---

## 1. 现状概述

### 1.1 Banner 状态机
- **红 banner**（`btState === 'off'`）：提示「蓝牙未开启」，按钮 `handleEnableBluetooth`（`index.vue:462`）→ `bleStore.enableBluetooth()`。
- **绿 banner**（`btState === 'just_enabled'`）：表示「正在开启中」，由 `STATE_TURNING_ON` 原生广播置位（`ble.js:804`），蓝牙完全开启（`STATE_ON`）后流转为 `'on'` 自然消失（`ble.js:807`）。
- **无 banner**（`btState === 'on'` / `'unknown'` 已解析）：正常态。

### 1.2 系统「开启蓝牙」弹窗的唯一来源
系统底部弹窗「BLE车钥匙 想要开启蓝牙」**只**来自 `utils/ble.js` 的 `requestEnableBluetoothAndroid()`（ACTION_REQUEST_ENABLE Intent，`utils/ble.js:330`）。它**仅**在 `initBluetooth()` 内部、且 `uni.openBluetoothAdapter` 失败 `code === 10001`（系统蓝牙未开）时被调用（`utils/ble.js:254-260`）。

`uni.openBluetoothAdapter` 本身**不会**弹系统框——弹框是 `initBluetooth` 在发生 10001 时「主动」追加的行为。

---

## 2. 根因：冷启动有两条路径都在自动弹开启框（① 几乎必现）

`initBluetooth()` 把「开适配器 + 申请权限 + （BT 关时）弹开启框」**绑死**在同一函数里。`openBluetoothAdapter` 失败且 `code===10001` 即弹框。冷启动 BT 关时，有**两处自动调用 `initBluetooth`**，于是弹两次：

### 路径 1 — `App.vue:172`（`onLaunch`，每次打开 App 都跑）
```172:179:app/BLE_Key_Go_App/App.vue
initBluetooth({
  onAllowing: () => {
    bleStore.btState = 'just_enabled'
    console.log('[App] ⚡ onAllowing → 绿 banner（与系统弹窗同步）')
  }
}).catch(() => { /* code=10001 静默，让 index 页横幅引导用户 */ })
```
BT 关 → `initBluetooth` 内部 10001 → **弹第 1 次**。

### 路径 2 — `prepareForAutoConnect()`（`stores/ble.js:2849`，有已知设备时冷启动跑）
```2856:2861:app/BLE_Key_Go_App/stores/ble.js
try {
  await initBluetooth()   // 打开适配器 + 申请权限（仅 BT 关闭时才弹系统框）
  this._adapterReady = true
  await this._reconcileBtState()
```
调用方：`index.vue:402`（`onShow` 冷启动）、`main.vue`（同）。只要存在已知设备（已配对，几乎必有），这条路径**必跑** → 又进 `initBluetooth` → 10001 → **弹第 2 次**。

> 两路径叠加 = 连弹两次。**「几乎必现」的解释**：日常使用都配对过（knownId 几乎总有），`prepareForAutoConnect` 必然执行，所以两条路径几乎总是同时触发。

### 正确的「点一次」路径（不受影响）
APP 已开 + 手动关 BT → 原生广播 `STATE_OFF` 置 `btState='off'`（红 banner）→ 点「开启」→ `handleEnableBluetooth` → `enableBluetooth` → `initBluetooth`（**仅此一处**）→ 弹一次。这正是用户补充里「正常情况只弹一次」的来源。**方案 A 不改动这条路径的语义。**

---

## 3. 期望行为 vs 当前设计

| | 当前 | 期望 |
|---|---|---|
| 启动（BT 关） | 自动弹开启框（×2） | **不弹**，仅显示红 banner 引导用户点 |
| 点红 banner「开启」 | 弹一次 | 弹一次（不变） |

即：开启框**只在用户主动点红 banner 时才弹**；启动/自动连准备路径只负责「初始化 + 正确显示红 banner」。

---

## 4. 方案 A（推荐）

### 4.1 机制
给 `initBluetooth` 增加 `options.autoEnable`（默认 `true`，保持 banner 点击行为不变）：
- `autoEnable === false` 且 BT 关（`code===10001`）→ **不调** `requestEnableBluetoothAndroid`，直接 reject（带 `code:10001`）。调用方 catch 后：`btState` 已由原生广播 `STATE_OFF` 置 `'off'`，或由 `_reconcileBtState()` 在 `!available` 时回落 `'off'` → **正确显示红 banner，零弹窗**。
- `autoEnable === true`（默认，即 `enableBluetooth` 红 banner 点击路径）→ 维持现状，弹一次。

### 4.2 改动点（局部、低风险）
1. `utils/ble.js`：`initBluetooth` 签名加 `autoEnable`，`code===10001` 分支在 `autoEnable===false` 时走 `reject(err)` 而非弹框。
2. `App.vue:172`：`initBluetooth({ autoEnable: false })`（去掉 `onAllowing`，因不会触发）。
3. `stores/ble.js:2857`：`await initBluetooth({ autoEnable: false })`。
4. 红 banner 点击路径 `enableBluetooth`（`ble.js:1157`）：保持默认 `autoEnable:true`（不动）。
5. （建议一并）扫描路径 `ble.js:2541` 的 `initBluetooth()` 也设 `autoEnable:false`，保持「扫描时 BT 关只显红 banner、不自动弹」的一致语义。

### 4.3 副作用核查（无）
`prepareForAutoConnect` 的 try/catch 已吞 10001（`ble.js:2870`）；且全局监听器（`_ensureGlobalListeners`，`:2853`）与前台服务（`_ensureForegroundService`，`:2854`）**已在 `initBluetooth` 之前注册**。因此即便启动不弹框、BT 后来由用户点 banner 或通知栏打开，`STATE_ON` 原生广播（`ble.js:805`）仍会驱动自动重连 → **无功能损失**。

### 4.4 方案 A 利弊

**利**
- 精确贴合诉求：启动路径零骚扰，开启框只在用户点红 banner 时出现，**彻底消除①双弹**。
- 改动极小、局部（1 个函数加开关 + 2~3 处调用方传参），回归风险低。
- 红 banner 行为不变且正确：未弹框时 `btState` 仍可靠落到 `'off'`。
- 自动连能力不受影响：监听器/前台服务早注册，BT 开后 STATE_ON 照常驱动重连。

**弊**
- 启动时不主动帮用户开 BT：用户需自己点红 banner。但红 banner 本就是为此设计的引导入口，**符合预期**，不算缺陷。
- **未解决权限框双弹**（见 §4.5）：`initBluetooth` 头部 `requestAndroidPermissions`（`utils/ble.js:145`）若权限未授予，两启动路径仍各弹一次权限框。用户本次没遇到（已授权），但新装/清权限后会复现。方案 A 只针对「开启蓝牙框」。
- 若 `autoEnable:false` 路径因**权限未授予**而 reject `PERMISSION_DENIED`（而非 10001），红 banner 虽显示，但用户点开启后仍可能卡在权限——这是既有问题，方案 A 不改它（也建议在 §4.5 一并处理）。

### 4.5 旁支：权限框双弹是否一并去重
`initBluetooth` 在 `openBluetoothAdapter` 之前先 `requestAndroidPermissions`（`utils/ble.js:228`）。权限未授予时同样会双弹。可选做法：把「启动路径不主动要权限」也纳入——即启动路径只做 `openBluetoothAdapterOnly` + 状态校正（类似已有的 `ensureAdapterReady`，`ble.js:2822`，它本就不申请权限）；真正要权限/开 BT 时统一交给红 banner 点击。这样权限框与开启框都只在用户点 banner 时出现，**一次都不多**。成本略高（需让 `prepareForAutoConnect` 改走 `ensureAdapterReady` 式逻辑），但语义最干净。

---

## 5. 备选方案对比

| 方案 | 做法 | 贴合「启动不弹」诉求 | 改动量 | 风险 |
|---|---|---|---|---|
| **A（推荐）** | `initBluetooth` 加 `autoEnable` 开关，启动路径传 `false` | ✅ 完全贴合 | 小 | 低 |
| B：去重标记 | 加会话级 `_btPromptShown`，本次只弹一次 | ❌ 启动仍会弹一次（不符合诉求） | 小 | 中（跨路径共享标记） |
| C：剥离弹框 | 弹框从 `initBluetooth` 拆成独立 `showEnableBluetoothPrompt()`，仅 banner 点击调用 | ✅ 最彻底 | 大（改所有调用方语义） | 中 |

**结论**：方案 A 最贴合诉求、改动最小、风险最低；方案 C 最彻底但工作量大，可作为后续重构方向；方案 B 不解决「启动不弹」的核心诉求，不推荐。

## 6. ② 现象与候选根因（暂挂，待①落地后查）

### 6.1 现象
点开启 → BT 开 → 绿 banner 出现并消失 → **红 banner 又出现（但 BT 已开）** → 再点开启才消失。

### 6.2 候选根因
`btState` 被**延迟的 `getBluetoothAdapterState` 误覆盖回 `'off'`**：
- `_reconcileBtState()`（`ble.js:1049`）仅保护 `'just_enabled'` 不被覆盖（`else if (this.btState !== 'just_enabled')` 才置 `'off'`），**不保护 `'on'`**。即 `!available && btState==='on'` 时仍会置 `'off'`。
- 延迟来源：`prepareForAutoConnect` / `tryAutoConnect` 在 BT 开启后调用的 `_reconcileBtState()`（`ble.js:2861` / `:2904`），若此刻 `getBluetoothAdapterState` 因 Android BLE 适配器初始化滞后返回 `available=false`，就把刚置的 `'on'` 覆盖成 `'off'`。
- 为何「再点才消失」：`STATE_ON` 原生广播（`ble.js:805`）已发过一次，没有第二次事件来纠正；直到用户再点开启 → `enableBluetooth` → `openBluetoothAdapter` 返回 `already open` 成功 → `_reconcileBtState` 此刻 `available=true` → 恢复 `'on'`。

> 对照：`_checkBluetoothState()`（`ble.js:1074`）与 `_onUniBtAdapterStateChange`（`ble.js:840`）**已**对 `'on'`/`'just_enabled'` 做了保护（信任原生广播、不覆盖）；但 `_reconcileBtState` 漏了 `'on'`。另 `_forceRefreshBluetoothState()`（`ble.js:1114`）也无保护，但当前代码中**未见调用点**（仅定义），故本次②主嫌是 `_reconcileBtState`。

### 6.3 建议修复方向（待验证）
给 `_reconcileBtState` 增加 `'on'` 保护：当 `!available && btState==='on' && this._nativeBtFired` 时信任原生广播、不覆盖（与 `_checkBluetoothState` 逻辑对齐）。或统一让 `_forceRefreshBluetoothState` 也加同等保护（若后续启用）。
