## 2026-07-30 · LED 跟随脉冲方案 + 低功耗优化讨论（decided + open）

- **议题**：TMOS 16 事件位占满，讨论腾位；制定 LED 跟随脉冲方案（省 2 事件位）；评估 350mAh 续航与低功耗优化；DCDC 旁路(VSW 接 VDCID) 的硬件约束。
- **结论**：
  1. **16 事件腾位**：去 LED 闪烁事件（0x0040+0x0200）腾 2 位；合并 DEFERRED_STATUS+DEFERRED_RAW 再腾 1 位；PERIODIC+STATE_MACHINE、ADV_RESTART/DISCONNECT_LOCK/UNBOUND_TIMEOUT 不建议动。
  2. **LED 跟随脉冲（decided，待落地不 commit）**：解锁/锁/后备箱脉冲期间亮、结束灭；RIDE 跟随双脉冲闪两下；平时全灭（顺带消灭常亮 2-5mA）。删 `SBP_LED_RIDE_BLINK_EVT`+`SBP_LED_TRUNK_BLINK_EVT`。
  3. **功耗基线**：当前 `HAL_SLEEP=FALSE`+`DCDC=FALSE`+60MHz → 约 10mA → 350mAh 仅 ~1.5 天。优化（HAL_SLEEP+DCDC+32M+LED 灭）后可到数月。
  4. **DCDC 硬件约束（关键）**：用户澄清 VSW 直接接 VDCID(VDD)=DCDC 旁路接法（非悬空），故 **`DCDC_ENABLE` 必须保持 FALSE**（短路风险），走内部 LDO。
- **状态**：LED 方案 `decided`（待落地）；低功耗 `open`（先讨论，受 DCDC 电感约束）；骑行退出链"状态机 vs 新事件" `open`（待讨论）。
- **关联**：`docs/02-技术方案与专项设计/2026-07-30_LED跟随脉冲与低功耗优化.md`、`code/CH582M/.../peripheral.h`、`config.h`、`keygo_core.c`。

## 2026-07-24 (17:20 日志) · 晃动根因纠正：非 RSSI 重渲染，是 control.vue 顶层 v-if 子树重挂载打断 swiper（已改 v-show 根治）

## 2026-07-24 (15:42 日志) · AUTH 失败却无 30s 断连 根因分析

- **议题**：用户标准基座复现——回前台重连后 App 自动重认证（AUTH 握手）耗时 ~15s 且最终"自动会话鉴权失败"，但连接并未在 30s 后主动断开。
- **结论1（无 30s 断连 = 设计行为，已确认）**：固件确有未鉴权 30s 强断（`UNBOUND_CONN_TIMEOUT_MS=30000`，`keygo_core.h:89`；触发 `peripheral.c:565`）。门控 `!osEncNoApp && !pairWinOpen`：`osEncNoApp = g_encRequired ? (链路已加密?1:0):0`（`peripheral.c:556-558`）。标准基座下手机与设备已 bond，回前台重连时**手机 OS 用 LTK 自动重加密链路** → `LINK_ENCRYPTED` 真 → `osEncNoApp=1` → 固件**故意跳过** 30s 强断。属无 App 模式设计（OS 加密即身份证据），App 层 `sessionAuthed` 失败只掉应用层、不拆 OS 加密链路。连接从 15:42:58(auth fail) 活到 15:45:49(Status Notify 超时→App 强制重建 GATT→断) 约 3 分钟，符合预期。
- **结论2（真正后果 = 连着但控不了）**：固件 `osEncNoApp` **仅用于是否跳过 30s 强断，不用于放行控制命令**。C1 锁/解锁仍要求 App 层 AUTH（`s_sessionAuthed` + 会话盐，仅 AUTH/BIND 成功建立，`bonding.c`）。故 AUTH 失败期间：链路活着，但 App 锁/解锁被固件拒（`DENY:AUTH_REQ`）。即"连着但控不了"，非"连不上"。
- **结论3（AUTH 失败根因 = 假设，待坐实）**：App 自动重认证（`_maybeAutoAuth`→`ensureSession`→`_requestNonce`）写 `NONCE`(FF03)→等 FF02 回 `NONCE:xxxx` notify(4000ms)→算 HMAC 写 `AUTH:`→等 `AUTH:OK`。日志 15:42:43/49/54 三次 `NONCE` 写入成功，但**全程无 `NONCE:` 回复、无 `AUTH` 写入** → `_requestNonce` 每次 4000ms 超时→重试 4 次(1500ms 间隔)→15:42:58 失败。三次间隔≈6s/5.5s = 4000ms 等待 + 1500ms 重试，吻合"NONCE 回复没收到→超时→重试"。`NONCE:` 回复走 FF02（`bonding.c:957` `Bonding_HandleNonceReq`→`KeyGo_SendRawNotify`，确认 FF02 短报文）。**假设根因：重连时 `_maybeAutoAuth` 的 NONCE 写入跑在"FF02 通知订阅启用(`[BLE] Notify 启用`)"之前/之中 → 设备发了 `NONCE:` 但 App 端 CCCD 未开→被协议栈丢弃**。佐证：15:45 重连日志 `Notify 启用 成功`(15:45:51) 明确在 `NONCE` 成功(15:45:54) 之前且那次认证成功。15:42 日志从 NONCE 写入才截，缺"连接成功/Notify 启用"段，未能 100% 确认。
- **结论3 修订（2026-07-24 16:59 日志 → 推翻订阅竞态假设）**：原"订阅竞态导致收不到 NONCE"**不成立**。16:59:23.639 明确收到 `[BIND] notify: NONCE:2D2E...`（FF02 订阅正常、设备回了 nonce），但 16:59:27.655 仍"自动会话鉴权失败"。新证据：16:59:09.428 写 `NONCE` 成功后**隔 14s 才在 16:59:23.639 收到回复**；中间 16:59:17.370 / 16:59:22.870 又多次写 `NONCE`。`_maybeAutoAuth` 虽有 `B._autoAuthRunning` 互斥锁（ble.js:3477）防重入，但 `ensureSession` 内 `_requestNonce` 4000ms 超时→`_maybeAutoAuth` 重试(1500ms)→再次 `_requestNonce` 写 NONCE；每次 `_requestNonce` 都重建单槽 `_waitFor('NONCE')` waiter（ble.js:3520），旧 waiter 被超时 resolve 丢弃。→ **新假设根因 = 多次 NONCE 请求 + 单槽 waiter 错位**：设备对早前请求(16:59:09)的回复迟到 16:59:23.639，此时 App 已用后续请求的 nonce 算 AUTH，nonce 与设备期望不匹配 → HMAC 校验不过 → AUTH 失败。或另一可能：设备侧实际已解绑（`bound/devBound` 是 App 侧状态，不等于设备真绑）→ 任何正确 HMAC 也失败。
- **坐实方法（修订）**：① 看 16:59:23.671 写 `AUTH:` 之后有无 `[BIND] notify: AUTH:OK` 或 `AUTH:FAIL`：有 FAIL→HMAC 不匹配（nonce 错位或 key 错）；全程无回包→设备静默拒。② 用另一手机/重新绑定确认设备侧是否真绑定。③ 抓固件侧 `Bonding_HandleNonceReq` 是否每次请求都立即回、还是只某时机回（解释 14s 延迟）。
- **修复方向（修订，待确认）**：`ensureSession` 一次性等待窗口拉长（如 8~10s）减少重试频次；或 `_requestNonce` 重试时复用同一 waiter 而非重建，避免 nonce 错位；或在重试间隙先确认 `_statusNotifyReady` 与链路稳定。
- **状态**：`open`（订阅竞态假设已推翻；新假设=nonce 错位/设备解绑，待上述坐实法确认）。
- **关联**：`peripheral.c:556-572`、`keygo_core.h:89`、`bonding.c:957-965`、`stores/ble.js` `_maybeAutoAuth`/`ensureSession`/`_requestNonce`、用户 15:42 / 15:45 日志。

## 2026-07-24 (15:28 复现) · 跳动与晃动同源 + 断连归因修正

- **议题**：用户标准基座（Keygo-Foreground 未启用，正常现象）复现：锁屏 8 分钟回前台，控制页数字乱跳；乱跳时左右滑动 → 屏幕左右拉扯（"左滑一下优化一下"往复）。
- **结论（重要）**：**跳动与晃动是同一根因**，非两个独立 bug。控制页「信号」绑未节流的 `filteredRssi`(control.vue:56)，每条 FF02 直写 → 控制页高频重渲染；该高频重渲染在滑动手势期间**打断 swiper 触摸手势状态** → 滑动被取消/回弹 → 再滑 → 往复 = "拉扯"。故 Fact1(跳动) 与 Fact2(晃动) 同源，**修控制页头条改绑 `displayRssi`（节流）应一并缓解两者**。
  - 佐证：晃动只在"数字乱跳 + 滑动"同时出现；本场景 `tabIndex` 三写入点（switchTab/onSwiperChange/onShow=0）均未触发（回前台 `connected=true` 早返回；重连不碰 tabIndex），排除"tabIndex=0 撞手势"。`tabIndex=0` 仅作"连不上回前台被踢回连接页"次生风险保留。
- **断连归因修正**：标准基座无原生后台保活，8 分钟后台断连属 Android 后台 BLE 老化预期；app 自动重连恢复（15:28:19 断→15:28:22 GATT 重建恢复）。**非 bug**，根治需自定义基座+Keygo-Foreground 插件。先前"插件缺失致断连"猜测撤销。
- **状态**：晃动根因锁定=未节流重渲染 destabilize swiper，与跳动同源 → 合并到跳动修复。`confirmed`（同源）。**⚠ 此归因已被 17:20 日志推翻纠正（见 17:20 条目）：swiper 在 main.vue、control.vue 无 swiper；真正主因是 control.vue 顶层 v-if(connected)/v-else 子树重连期间反复挂载/卸载打断父 swiper 手势，已改 v-show 根治；RSSI 节流只治"数字乱跳"。**
- **关联**：`pages/control/control.vue:56`、`stores/ble.js:3069/3077/3085`、用户 15:28 日志。

## 2026-07-24 · 后台锁屏 RSSI 跳动 + 回前台页面左右晃动（探讨，未改代码）

- **状态**：**事实1 `confirmed`**（非对称真机证实 + 后台触发点明确）；**事实2 `open`**（晃动待证实，但与跳动同源）。修复：①【跳动·**已实施 2026-07-24**】控制页「信号」头条改绑已节流的 `displayRssi`（control.vue:56，附详细注释说明根因/影响），info-grid「原始/滤波 RSSI」保留作诊断；②【晃动·待证实】swiper 改"程序切换用实例方法、用户拖拽只同步高亮"，或 `onShow` 的 `tabIndex=0` 仅首次连接引导流程触发；③ 回前台重连副作用错峰。**① 已落地，待用户真机回前台测试验证（是否一并缓解晃动）。**
