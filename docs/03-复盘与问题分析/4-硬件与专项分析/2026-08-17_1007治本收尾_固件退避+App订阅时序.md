# errCode 10007 治本收尾说明（固件退避 + App 订阅时序）

> 日期：2026-08-17
> 涉及分支：`dev/pcb-v1`
> 固件：`CH582M_BLE_Slave`（KEYGO_FW_VERSION `3.36.3-fix28+PCBv1`）
> App：`app/BLE_Key_Go_App`（stores/ble.js / utils/ble.js）

## 一、问题回顾

`errCode 10007`（微信/Android BLE「property not support」，实为 OS 在本地**直接拒绝** GATT 写、并未发往固件）此前长期出现在 AUTH/配置下发阶段，表现为「发送失败，请检查连接」或 RSSISET 写不进。

### 已推翻的旧假说
- ❌ **「Android GATT 缓存冷窗 4.2s」**：19:02 真机日志显示服务发现**已完成**仍持续 1007，且固件**自身**报 `[FF02] NOTIFY FAIL ret=16 (ATT忙)`——证明瓶颈在固件侧，与 Android 缓存无关。
- ❌ 「CCCD 吞写」「GATT 复用冲突」「加密触发」：均被 19:02 量化数据排除。

## 二、真因（19:02 真机数据定界）

**FF02 周期推送（1s/次、224B）与 App 的握手写（NONCE/AUTH/FF01 配置/RSSISET）抢同一 ATT 事务槽。**

- 固件端 `simpleProfile_Notify` 反复返回 `blePending(0x16=ATT忙)`，FF02 占满事务槽；
- 同期 Android 把 App 的 FF03(RSSISET) 写判为「通道忙」→ 本地拒绝 1007；
- 量化窗口：① 连接→首 FF03 ≈ 0.9s；② AUTH:OK→首 FF01 `dtAuth=2843ms`，期间 FF02 疯狂撞忙、FF01 写回调 22ms、App RSSISET 直到 ~2.5s 后才命中。

## 三、治本方案（两端协同）

### 3.1 固件侧：FF02 自适应退避（keygo_core.c，已落地 19:08 验证）
- 新增 `#define FF02_BACKOFF_MS 600` + `static uint32_t s_ff02BackoffUntil`；
- `KeyGo_NotifyStatus()` 入口守卫：`now < s_ff02BackoffUntil` 时整函数 `return`（不构造/不发送），把事务槽让给 App 写；
- `simpleProfile_Notify` 返回 `blePending` 的分支设 `s_ff02BackoffUntil = now + 600ms`，并 PRINT `[→退避600ms让位App写]`；
- **握手 RAW 队列（NONCE / AUTH:OK）走独立的 `SBP_DEFERRED_RAW_EVT` + 重试，不受退避影响**——退避仅加在 `KeyGo_NotifyStatus` 入口，不阻塞鉴权链路；
- 退避仅在真忙时触发，空闲时 1s 心跳完全不受影响。

### 3.2 App 侧：提前订阅 FF02，消除窗口①暴涨（stores/ble.js，已落地 19:12/19:13 验证）
- **根因**：连接后先同步 `readSerialNumber`（走 `_gattChain` 串行链 ~5s），再 `setTimeout(800)` 才订阅 FF02（也走 `_gattChain`）→ FF02 的 CCCD 写被排在 SN 读后面 ~5s → 窗口① `dtConn` 从 0.9s 飙到 **5.98s**（19:08 实测）；
- **修复**：重连路径（`~L2071`）与首连路径（`_finalizeConnection ~L2287`）**均去掉 800ms 延时、立即发起 FF02 订阅**（已知 UUID 常量，无需等服务发现），让 CCCD 写尽早入链队首，SN 读并行在后；订阅就绪即驱动自动 AUTH。

## 四、验证结论（19:13 真机）

```
[1007DIAG] FIRST FF01(cfg) AFTER AUTH t=113070 dtAuth=1162 (window② elapsed)
[FF02] NOTIFY FAIL ret=16 (ATT忙) [→退避600ms让位App写]   ← 偶发，自愈
[FF02] SENT ok len=223 ...                                  ← 退避结束恢复 1s 心跳
[POWER] key powered ON (PB0)
[KEY] unlock                                                ← 自动解锁成功
```

- ✅ **RSSISET 全程零 1007**（FF03 写回调 `cost=46ms` 正常，无任何 10007 字样）；
- ✅ **窗口② 稳定 ~1.16s**（19:08 同值 1161ms，收敛确认）；
- ✅ **FF02 退避自愈闭环**：撞忙一次 → 退避 600ms → 恢复 `SENT ok`；
- ✅ **命令链路打通**：AUTH → 阈值就位（`unlock=-50 lock=-65`）→ 自动解锁；
- ⚠️ 窗口①（CONNECTED→首 FF03）因日志未含 `CONNECTED t=` 基线未直接读出，但结果反推已压回 ~1s（否则窗口②会重新涨回几秒）。

## 五、收尾动作

1. **关闭诊断打点 `KEYGO_1007_DIAG`**（`keygo_core.h`，原默认开）→ 注释关闭，出量产固件零开销、不影响时序。复现/量化时取消注释再编译即可。
2. **诊断打点说明**（如需回溯）：跨 `peripheral.c` / `gattprofile.c` / `bonding.c`，用 `Peripheral_GetSystemMs()（~1ms 精度）` 量化窗口①/② + 单次写回调耗时，PRINT 过滤 `[1007DIAG]`。详见同目录 `2026-08-17_1007固件侧ATT忙窗量化诊断打点.md`。

## 六、影响范围 / 注意事项

- 固件：仅 `KeyGo_NotifyStatus` 增加「ATT忙→退避」逻辑，不改变 1s 心跳周期、不改变任何协议字段、不影响 No-App 模式与 RSSI 自动解锁；
- App：仅调整连接后「FF02 订阅时机」，去掉两处 800ms 延时，不改动握手/重试主体逻辑；
- **部署铁律（原生/离线相关不适用本改，但固件重编仍建议升 versionCode 防基座缓存）**：纯固件+纯 JS 改动；如需真机验证，按现有「自定义调试基座 / versionCode+1」流程重新烧录。

## 七、后续
