# 「BLE 写 10007（property not support）冷窗口」根因分析 + 扫描过滤现状

> 现象：连接建立后，App 对 FF03（命令/RSSISET）等特征值的 GATT 写，在连接后约 **0.8s~4.2s** 内持续返回 `10007 writeBLECharacteristicValue:fail property not support`，经历若干次重试后才成功；AUTH:OK 后 FF03 又出现一轮约 1s 的 10007；电池 GATT 读也三次全失败。
> 状态：根因已定位（2026-08-17，基于固件 `gattprofile.c` / `keygo_core.c` / `bonding.c` + App `utils/ble.js` / `stores/ble.js` 深度读码）。
> **结论：10007 是 Android BLE 栈对多特征值 WRITE 属性缓存「独立刷新、就绪时间不一」的硬限制，与加密状态变化无关（固件 `g_encRequired` 默认 0，永不主动发起加密）；App 侧密集重试已是最优解，固件侧缩短窗口空间极小。**

## 2. 固件侧定界（排除加密假说）

### 2.1 所有特征值均为明文、无加密门控
`Profile/gattprofile.c` 属性表（L115-209）全部使用 `GATT_PERMIT_READ` / `GATT_PERMIT_WRITE`，**没有任何特征的写权限带 `GATT_PERMIT_AUTHEN` / `GATT_PERMIT_ENCRYPT`**：

```c
// gattprofile.c:137  Char1(FF01)
{ {ATT_BT_UUID_SIZE, simpleProfilechar1UUID}, GATT_PERMIT_WRITE, 0, simpleProfileChar1 },
// gattprofile.c:181  Char3(FF03) 注释明确：
//   "明文写：无头设备 Just-Works 配对无 MITM 防护，安全边界改由应用层 BIND/AUTH(HMAC) 承担，
//    去掉加密门控以杜绝强制配对弹窗"
{ {ATT_BT_UUID_SIZE, simpleProfilechar3UUID}, GATT_PERMIT_WRITE, 0, simpleProfileChar3 },
// gattprofile.c:200  Char4(FF04)
//   "明文读：序列号(=MAC)用于 KDF 派生 bindKey..."
{ {ATT_BT_UUID_SIZE, simpleProfilechar4UUID}, GATT_PERMIT_READ, 0, simpleProfileChar4 },
```

→ **固件侧不要求加密即可读写任何特征值**，Android 端 10007 不是"属性被加密门控拒绝"，而是"写属性缓存尚未刷新到该特征"。

### 2.2 `g_encRequired` 默认 0 → 永不主动发起加密
- `keygo_core.c:134`：`uint8_t g_encRequired = 0;`（默认关闭）。
- 读取 `KEYGO_ENCRYPT_ADDR` 时，若该 DataFlash 区未初始化（全 0xFF）→ 归类为 0（keygo_core.c:1570 附近逻辑）。
- `bonding.c:225`：`if (g_encRequired) { ... INITIATE ... } else { WAIT_FOR_REQ }` → **当前走 `WAIT_FOR_REQ`，设备不主动发 Security Request**，不会触发 Android 的 `LINK_ENCRYPTED` 状态变化 → **不会令 GATT 缓存整体失效**。

### 2.3 AUTH:OK 后无加密副作用
`keygo_core.c` 的 AUTH:OK 处理仅置 `authed=1`、清零 `g_unauthConnStartMs`（解除 30s 强断）。**不调用 `GAPBondMgr` 加密相关 API**，不会引发 2.2 之外的 GATT 缓存失效。

> ⚠ **既往误判已证伪**：早前（2026-08-17 前）曾怀疑"CCCD 被吞 / GATT 复用旧连接 / AUTH:OK 触发加密导致二次冷窗口"。本次深度读码确认：① CCCD 订阅 ~0s 即生效、从未被吞（日志实证）；② `g_encRequired=0` 下无加密状态变化；③ 冷窗口只与「特征值写属性缓存就绪」相关。

## 3. 真因：Android BLE 栈「多特征值写属性缓存独立刷新」

### 3.1 机制
Android 在 `getBLEDeviceServices` 后，会**逐特征值**向固件查询并缓存其「属性位」（READ/WRITE/NOTIFY/INDICATE 等）。该缓存：
- **每个特征值独立**刷新，就绪时间不一致；
- 受固件 ATT 协议栈处理速度、连接 MTU 协商、手机 BLE 控制器排队影响，**首条写命中时间波动在 0.5s~4.2s**；
- 冷窗口期间对该特征调用 `writeBLECharacteristicValue` → 返回 `10007 property not support`（OS 本地拒绝：属性位尚未就绪）。

### 3.2 为何 FF03 比 FF01 慢、且 AUTH 后再次出现
- **连接后首轮**：FF03(NONCE) 06.674 起撞 0.87s（窗口①）。此时 FF01 尚未被 App 写过，其缓存可能更晚就绪，但 App 在 AUTH 完成后才发 FF01，彼时已过热窗口。
- **AUTH:OK 后**：FF01(配置) 09.849 一次成功（说明 FF01 缓存此时已就绪），但 **FF03 走的是另一条独立缓存**，其完整就绪窗口约 4.2s（从 connect 时刻算），09.849 时仍剩 ~1s → RSSISET 再撞 1s（窗口②）。
- 两窗口**都绑定在 FF03 特征值上**，只是被"连接"和"AUTH 后下发"两个时刻分别撞到前半段/后半段。

### 3.3 电池读 10007 同源
`readBatteryLevel` 读 FF04（Battery Service `0x2A19`）。日志 09.150~10.794 三次失败，原因叠加：
1. FF04 READ 属性缓存与 FF03 WRITE 缓存同理，在 discover 周期内陆续就绪；
2. 此时 GATT **事务槽**被 FF01/FF03 密集写占据（经 `enqueueWrite` 串行队列），读被迫排队，加剧失败概率。

## 4. App 侧已落地的最优解（无需再改）

`utils/ble.js` + `stores/ble.js` 当前策略已是应对该硬限制的最佳实践：

| 路径 | 实现 | 作用 |
|---|---|---|
| `writeBLECharacteristicValue` 底层 | `opts.retries`（默认 2）+ `opts.hardTimeout`（默认 4s） | 通用兜底 |
| `sendCommand` / `rawSendCommand(..., {retries:0})` | 关掉底层 400ms×2 **阻塞重试**，失败立返 | 避免无谓等待，把节奏交本层 |
| `_requestNonce` / `_doPushRssi` | **150ms×30 密集重试** | 窗口一开（0.5s~4.2s 内任意点）立刻命中，省去"赌中点"的盲等 |
| `_syncConfigToDevice` | FF01 也传 `{retries:0}` | FF01/FF03 策略统一，不再底层阻塞 |
| `_flushPostAuthWrites` | 去掉 FF03 发射前 250ms 固定延时，FF01 落地即发 FF03 | 不再"赌 FF01 热了 FF03 也热"而撞冷窗 |
| `enqueueWrite` / `enqueueRead` | 所有 GATT 写/读经同一事务链串行 | 杜绝并发抢 Android 单一事务槽 → 消除一类 10007 |
| 电池读 `_fetchBatteryLevel` | `enqueueRead` 排队 + 3 次退避重试 | 避免与写并发抢槽 |

**核心认知**：4.2s 冷窗口是 **OS/固件 ATT 握手硬限制，App 无法缩短**，只能"窗口一开立刻命中"。密集重试已做到这点。

## 5. 固件侧可优化空间（极小，列为候选）

| 方向 | 内容 | 预期收益 | 风险 |
|---|---|---|---|
| ① 缩短属性表 / 把常用特征前移 | GATT 表越小、FF03 越靠前，Android discover 越快 | 冷窗口可能从 4.2s 降到 2~3s | 收益有限，且改动需重编固件+升 versionCode |
| ② **不推荐**：主动加密（`g_encRequired=1`） | 在连接初期即完成加密握手，让 GATT 缓存只失效一次 | 看似减少 AUTH 后窗口，但 **Just-Works 无 MITM**，且会触发系统配对弹窗（用户明确反对强制配对） | 引入配对弹窗 + 安全模型倒退，**否决** |
| ③ 固件侧在 AUTH:OK 后主动推一帧 FF02 | 让 App 更早确认活性 | 与 10007 无直接关系 | 无助于缩短写窗口 |

**结论**：固件侧无性价比高的根治手段。维持 App 密集重试策略，必要时做 ① 的微优化即可。

## 6. 关于「扫描到设备名包含特定字符避免误扫」——功能已存在，无需改动

用户提出：手机 App 扫描时是否应按设备名包含特定字符过滤，避免误扫其他设备。

**现状已满足该需求**：
- 固件广播名 = `KeyGo-<MAC后3字节反转>`（`peripheral.c:196`），放在 **Scan Response**（peripheral.c:208-211），原始名即带 `KeyGo` 前缀。
- App `utils/ble.js` 扫描过滤按前缀 `KeyGo` 匹配（L19 `deviceNamePrefix: 'KeyGo'`；L625 过滤逻辑），且专门处理 NimBLE 128-bit UUID 挤占广播包导致完整名落入 Scan Response、`localName` 只拿到截断短名（如 `Ke`）的坑——做了 `partialMatch` 容错（L624-626）。
- 日志中看到的"京A888"是**用户自定义名**（`customDeviceName`，存 App 本地），**不是广播原始名**，与扫描过滤无关。

**决策**：保持现状。若想更严格，可加一层正则（仅认 `KeyGo-` + 合法十六进制后3字节），但当前误扫风险已极低，不优先做。
