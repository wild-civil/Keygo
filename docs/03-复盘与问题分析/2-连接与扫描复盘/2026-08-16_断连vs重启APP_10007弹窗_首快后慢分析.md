# 断连 vs 重启 APP、10007 弹窗、"首快后慢" 深度分析（2026-08-16）

> 本文档基于 `app/BLE_Key_Go_App/stores/ble.js` 与 `utils/ble.js` 代码实证，
> 配套固件 `code/CH582M/CH582M_BLE_Slave/APP/peripheral.c`。
> 结论：三个现象**共用同一条根因链**——Android 对"同 deviceId 重连"的 GATT 实例预热慢。

---

## 0. 一句话总览

| 现象 | 真因 | 与什么有关 |
|------|------|-----------|
| 首次绑定快、之后绑定慢 | 首连走"新建 GATT"路径写属性 ~0.4s 就绪；同 deviceId 重连走"恢复既有连接"路径 ~1.6s 就绪 | 与 App 是否重启**无关**，与"是否复用 GATT 实例"有关 |
| 10007 "蓝牙缓存可能过期" 弹窗 | 绝大多数（90%+）是重连冷窗口 > 连接宽限期的**假阳性**，非真缓存过期 | 重连慢的下游症状 |
| 断开连接 | 主要是异常掉线→自动重连→重连慢→可能撞 30s 强断；少数是用户主动断开 | 见 §4 |

---

## 1. 断开连接 vs 重启 APP 的本质差异

### 1.1 断开连接（用户点断开 / 异常掉线）
走 `_handleDisconnect`（stores/ble.js ~L1285）：
- 复位 `_connFinalizedFor = null`、`_gattWriteReady=false`、`_postAuthWritesInFlight`、`_postAuthWriteTimer`
- `uni.closeBLEConnection` 主动拆 ACL
- **App 进程、uni 蓝牙适配器、Android 蓝牙系统栈全部存活**
- 重连：`_doReconnect` 先 `closeBLEConnection` 再 `connectDevice`（L2335/2352）

→ 同 `deviceId` 的 **GATT 实例被系统复用/重建为"恢复既有连接"路径** → 写属性就绪慢 ~1.6s。

### 1.2 重启 APP
- JS 运行时全清（`_gattWriteReady`/`_postAuthWritesInFlight` 等回到初始 false）
- **但 Android 蓝牙系统栈（系统进程）不重启** → 磁盘 GATT 缓存表仍在
- 首连 `createBLEConnection` → 系统**新建 GATT 实例**（走"首次建链"路径）→ 写属性就绪 ~0.4s

### 1.3 核心矛盾
两者 OS 栈都活着、缓存都在。差异**不在缓存、不在是否重启 App**，而在：
**Android 对同 `deviceId` 重连的 GATT 实例预热更慢（~1.6s）**，实测首连仅 ~0.4s。

> 即你记忆中的铁律："首连快、重连慢 ~1.6s"。根因是 Android GATT 实例生命周期路径差异，
> 不是缓存过期、也不是 App 进程状态。

### 1.4 为什么 APP 会扫到其他 KeyGo 设备（用户疑问）
- **固件广播**（peripheral.c L87-125）：广播数据含 `0xFF` 这个 16-bit Service UUID（注释 "KeyGo Service"）
  + Battery + HID 三个服务 UUID；扫描响应带完整设备名 `KeyGo-XXXXXX`（由 MAC 后 6 位生成，L209-210）。
- **App 扫描**（utils/ble.js `startScan`）**内部用该 service UUID 做硬件过滤**（L1825 注释："内部已配置 service UUID 硬件过滤"）。
  → 任何广播里带 `0xFF` 的 CH582M 设备（同事的板子、另一块开发板、同型号别设备）**全被扫成 KeyGo 候选**。
- **这是设计产物**：硬件过滤本意是"只扫 KeyGo 类、省电"，但不分 MAC，所有 KeyGo 一律进列表。
- **产品语义决定要不要管**：
  - 若 KeyGo 是**一对一车锁**：应在"可连接/绑定列表"里**只显示已绑定/已记住的 MAC**，
    其他 KeyGo 不该进用户连接候选（避免误连别人的车）。建议做"绑定流程白名单"。
  - 若允许多车管理：现状合理，无需改。

## 2. "10007 弹窗" 逐层拆解

### 2.1 10007 的本质（铁律）
uni-app/微信 BLE `errCode 10007 "property not support"` **不是**"特征没有写属性"，而是
**"GATT 通道忙 / 写属性尚未就绪，本次提交被框架拒绝"**。两类来源：
1. **并发抢槽**：read/write/notify-enable 共用一个事务槽，并发提交被拒。
2. **重连后写属性就绪慢（~1.6s 冷窗口）**：同进程重连后硬写必撞，与并发无关。

当前架构（2026-08-13 终审）：所有 GATT 读写 + notify 使能都经 `command-queue.js` 的
`_gattChain` 串行化 → 已解决①并发。故**现在 10007 几乎全是②重连冷窗口**。

### 2.2 为什么还会弹窗（4s 宽限兜不住）
弹窗触发条件（utils/ble.js 64-86）：`10007` **且** 不在 `_CONNECT_GUIDE_GRACE`（4s）**且** 不在冷却。
- 连上后 `_CONNECT_GUIDE_GRACE = 4000`（utils/ble.js L749）。
- 理想：重连冷窗口 ~1.6s < 4s，AUTH 期间 10007 应被宽限吃掉。
- 实际：AUTH 失败走 `_retryWithBackoff`（最大 4 次、每次 `isReconnect?1500:1000ms`）→
  若重连 AUTH 拖到 4s 之后仍在重试（NONCE 1.6s + AUTH 再撞 + RSSISET/best-effort 写在 4s 后才发）
  → 撞 10007 **已超出宽限** → 弹窗。
- **"重连慢" 直接喂给 "10007 弹窗"**——同一根因上下游。

### 2.3 字面"蓝牙缓存可能过期"的真·来源（B 类，罕见）
仅开发期频繁换固件/板子 → Android 磁盘缓存的 GATT 表是旧固件的 → 连接后某些特征
UUID/属性对不上 → 10007 在宽限期外真实发生。量产冻结 GATT 结构后普通用户不会遇到。

**结论**：日常弹窗 90%+ 为 A 类（重连冷窗口超宽限的假阳性），非真缓存过期。

## 3. "首次绑定快、之后绑定验证慢" 时序账

路径：`_finalizeConnection` → 读 SN → `_maybeAutoAuth()`（`AUTH_WARMUP_MS=0` 立即）→
`_requestNonce()` → NONCE 写 → 等 FF02 → AUTH。

- **首次**（APP 刚启动、首连路径）：NONCE 写 ~0.4s 就绪一枪过，`_requestNonce` 底层
  `retries:2 + 400ms` 兜底用不上 → AUTH 几百 ms 完成 → **快**。
- **之后重连**（同 deviceId GATT 复用）：NONCE 写撞 ~1.6s 冷窗口 → 底层 `_attempt(0)` 失败 →
  400ms `_attempt(1)` 仍失败 → 再 400ms `_attempt(2)` 才过 → **仅 NONCE 就 ~0.8s+**，
  AUTH 那笔可能再撞 → 整段 AUTH 2~3s → **慢**。

> 注：2026-08-13 曾用"12×150ms 密集重试"跨冷窗口，因拖慢首连而回退。
> 回退后重连慢的根因（1.6s 窗口）**未治**，只是从"可见更慢"变为"底层 0.8s 静默才过"。

## 4. 固件侧"断开连接"的两条路径

### 4.1 30s 未 AUTH 强断（peripheral.c L593-599）
连接后 30s 内没 AUTH/BIND → 发 `BIND:TIMEOUT:30S` → 400ms 后 `GAPRole_TerminateLink`。
正常车主 AUTH 远小于 30s，永不触发。**与"重连慢"基本无关**（除非 AUTH 连续 4 次全失败
拖过 30s，但 MAX_TRIES=4×1.5s≈6s，够用）。门控：`!osEncNoApp && !pairWinOpen`。

### 4.2 异常掉线（主要来源）
手机离远 / 锁屏 Doze / OS 回收 GATT → 走 `_handleDisconnect` → App 自动重连 →
触发 §1.3 的"重连慢 + 10007"链。

## 5. 优化方案

### 方案 A（低成本，立即可做）：放宽连接宽限
`_CONNECT_GUIDE_GRACE` 4s → 8s（utils/ble.js L749 一处常量）。
让重连 AUTH + 后续 best-effort 写都落在宽限内 → A 类 10007 弹窗基本消失。
代价：真·缓存过期（B 类）提示晚几秒（罕见，仍会弹）。风险：零。

### 方案 B（治本）：重连 = 首连（"模仿重启 APP"）
**目标**：重连时把连接态恢复到"重启 APP 首连"的样子，让系统走"新建 GATT"路径（0.4s 就绪）。

#### B-1 轻量版（推荐，先上）★ 2026-08-16 已实施
在 `_doReconnect` 的 `closeBLEConnection` 之后、下一个 `createBLEConnection` 之前，
调用一个 `_resetConnectionStateLikeAppRestart()`：
1. 全清 App 侧会话态（新增函数 stores/ble.js）：
   `_gattWriteReady=false`、`_postAuthWritesPending=false`、`_postAuthWritesInFlight=false`、
   `_postAuthWriteTimer` 清掉、`_statusNotifyReady=false`、`sessionAuthed=false`、
   `_autoAuthState='idle'`、`B._sessionSalt/_cmdSeq/_lastNonce` 清。
   （`batteryLevel/deviceName/_configPushedThisConn` 由 `_finalizeConnection` 连接成功后处理，此处不碰。）
2. `closeBLEConnection` 后等待 **300ms → 700ms**（与亮屏路径 `_tryAutoConnect` 统一），
   确保 OS 真正销毁旧 GATT 再 `createBLEConnection`，逼系统走"新建 GATT"（首连路径 0.4s 就绪）。
→ 写就绪回到 ~0.4s，重连 = 首连速度；10007 弹窗消失；解决"设备重启后连不上需重启 APP"。
代价：重连多 ~400ms 等待（300→700）。与 `_finalizeConnection` 复位互补不冲突。

#### B-2 重锤版（保底，仅当 B-1 偶发陈旧 GATT 才上）
每次重连先 `_resetBluetoothAdapter()`（stores/ble.js L2494：关适配器→等 800ms→
重开→等 500ms）。这是"重启 APP 蓝牙栈"的等价操作，已在 `ALREADY_CONNECT_STALE` 场景验证。
代价：重连慢 ~1.5s，且会短暂丢失所有蓝牙设备、用户若关蓝牙会误重开。**不默认启用**。

> 关键判断：轻量版 B-1 已足够。重锤版 B-2 不必须——"首连快"的真相是"GATT 实例新建"，
> 不是"适配器刚开"。只要重连逼系统新建 GATT（close 后等真拆链再建），速度即恢复，
> 无需重置整个适配器。

### 方案 C（治真·缓存过期 B 类，按需）
连接成功后 `getBLEDeviceServices` 比对特征 UUID，若缺失/不匹配 →
自动提示"取消配对重连"而非干等。开发期友好，量产用户几乎遇不到。

---

## 6. 推荐落地顺序

1. **方案 A**（提宽限 4s→8s）：一处常量，零风险，立刻减少 90% 弹窗。
2. **方案 B-1**（重连即首连轻量版）：治本，消除"之后慢"和 A 类弹窗。
3. **方案 C / B-2**：按需。
