# 2026-08-09 P1-② 删除已知设备交互

## 现象 / 诉求
已知设备列表（首页重连卡片）只能「连接 / 设为默认」，没有删除入口。用户想彻底移除某台 KeyGo 在本机的记录（换机、卖设备、清掉误加的设备）时无从下手。

## 根因 / 设计
此前只有 `_removeKnownDevice(mac)` 这一个**内部**方法，且仅在「设备复位/被解绑」时由 `_forgetDeviceKey` / `UNBIND:OK` 自动调用，清理范围**只覆盖 `knownDevices`**。它从设计上就不服务于「用户主动删除」，也没有暴露给 UI，更不会清理自定义名 / 默认标记 / 重连锚点。

若直接复用 `_removeKnownDevice` 给 UI 调，会导致残留：
- 自定义名（`_customNamesByMac` / `ble_device_custom_names`）还在 → 扫描列表里仍显示旧名字；
- 若删的是默认设备（`defaultDeviceId`）→ 默认标记悬空；
- 若删的是当前重连锚点（`knownDeviceId` / `lastDeviceId`）→ 断连后还自动重连一台已不存在的条目。

因此需要一个**面向用户的、全量清理**的公共方法，而不是复用内部增量方法。

## 修复
### 1. `stores/ble.js` 新增公共方法 `removeKnownDevice(mac)`
在 `_removeKnownDevice` 之后新增，按 ①→④ 顺序彻底清理一台设备在本机的全部痕迹：
- ① `knownDevices` / `ble_known_devices`（调 `_removeKnownDevice`）；
- ② `_customNamesByMac` / `ble_device_custom_names`（按去冒号 MAC key 删）；
- ③ 若删的是默认设备（`defaultDeviceId===key`）→ 回退到已知集合其余首项，无其他设备则清空 `ble_default_device_id`；
- ④ 若删的是当前重连锚点（`knownDeviceId===key` 或 `lastDeviceId===key`）→ 清 `ble_last_device_id` / `lastDeviceId`，不再自动重连它。
- 返回值：以前是否在已知集合里（`true`=确实删掉了），供 UI 提示区分「已删除」与「本就不在列表」。

### 2. `pages/index/index.vue` 增加删除交互
- **多设备列表项**：在「连接 / 默认」按钮后新增红色 `删除` 按钮（`remove-btn` 样式）。
- **单设备卡**：原「重新连接」按钮旁新增「删除设备」按钮，外包 `single-actions` flex 容器保证并排。
- 新增 `handleRemoveDevice(mac)`：`uni.showModal` 二次确认（红色「删除」按钮 + 文案说明「设备端绑定不受影响」）→ 确认后调 `bleStore.removeKnownDevice(mac)`，按返回值 toast「已删除」/「该设备不在已知列表」。

## 影响 / 验证
- 仅本地痕迹清理，不影响设备端绑定关系（与 `_forgetDeviceKey` 语义不同：后者清本机密钥、要求重绑；此处只清本机列表，设备端无需复位）。
- 删除默认设备后会自动把默认权移交给其余设备，避免默认标记悬空。
- 删除当前重连锚点后，断连态不再自动重连该条目，重连卡片实时收缩。
- 待真机验证：多设备下删除其中一台、删除默认设备后默认回退、删除最后一台后卡片消失。

## UI 交互演进（二次提交 c2df650）
首版（fd2c9bf）平铺「连接 / 默认 / 删除」三按钮，用户反馈太挤太乱。经讨论确定方向：

- 用户明确「单击即连接不合适，易误连」→ 单击列表项**不**触发连接，「连接」保留为显式按钮。
- ⋯ 三点图标放列表项右侧，点击弹 ActionSheet（设为默认/删除/取消）作兜底入口，与左滑功能互补（UI 不同：左滑是 iOS 原生感，⋯ 是显式更多菜单）。

### 实现要点（pages/index/index.vue）
- `known-item` 拆两层：**前景层 `known-item-front`**（内容 + 连接按钮，背景盖住背后）+ **背后层 `known-item-back`**（绝对定位右侧铺 `默认`/`删除` 红块）。
- `openMac` ref 记录当前展开项，互斥（一项展开其他收起）；`:style` 绑定 `translateX(-168px)` 露出（168px=2×84px 按钮宽，与 CSS `.back-btn width:84px` 对应）。
- 手势：`onItemTouchStart` 记起点+当前 openMac；`onItemTouchMove` 锁定方向，纵向直接 return；`onItemTouchEnd` 横滑 dx<-40→展开，>40 或已展开轻滑→收起。
- `openItemMenu(mac)`：`uni.showActionSheet`，非默认设备才显示「设为默认」，删除标红 `#e64340`，tapIndex 映射回对应 action。
- 单设备卡维持「重新连接 + 删除设备」平铺（单卡无需左滑，避免复杂）。
- 提交消息因 PowerShell 中文/连字符解析坑，改用纯英文（详见 memory 工具坑）。

## UI 交互演进（三次迭代：左滑体验打磨）
首版左滑上线后，用户反馈三个问题，逐一修复：

### ① 左滑与页面纵向滑动「同时发生」
**根因**：首版 `onItemTouchMove` 仅 `return` 不阻止默认滚动，纵向意向判定过慢（>8px 才锁定），轻横偏被锁成横滑后 scroll-view 仍滚动 → 两者并发。
**修复**：保留「touchstart 记起点 → touchmove 实时锁定首个明显方向(>8px)」；横向意向时 `e.stopPropagation()` 阻断冒泡到 scroll-view 的纵向滚动手势；`onItemTouchEnd` 阈值 -40 吸附展开、>40/已展开轻滑收起，**维持实时跟手**（用户明确表示不接受「抬手才滑出」非实时方案）。
新增 `_touchMoved` 标记区分「滑动」与「点击」，避免滑动结束误触 `onFrontTap` 收起。

### ② 夜间模式未同步（前景层白底）
**根因**：`.known-item-front` 用 `var(--card-bg, #fff)`，而项目主题卡片变量是 `var(--bg-card)`（`--card-bg` 未定义 → 夜间回落白底 `#fff`）。
**修复**：背景改为 `var(--bg-card)`，与列表/卡片其他块一致，dark 下自动切 `#1a1a3e`。

### ③ ⋯ 点击应是滑动展开，而非底部弹窗
**根因**：首版 `openItemMenu` 调 `uni.showActionSheet`（底部弹窗），与左滑「滑动露出」UI 不一致，用户觉得割裂。
**修复**：删除 ActionSheet，改 `toggleItem(mac)`——点击 ⋯ 直接 `openMac` 切换（与左滑同一套 `translateX` 滑动 UI），互斥逻辑不变。

### ④ 提升易用性：点空白处收起
新增两处收起入口（除既有的「左滑回拖」「⋯ 再点互斥」「展开后轻滑」外）：
- `onFrontTap(mac)`：已展开时点击前景**空白处**（非连接/删除/⋯ 按钮，按钮均 `@tap.stop` 拦截）→ 收起。
- `onListTap()`：点击列表 scroll-view 自身空白 → 收起所有展开项。
满足「顺手点一下空白就收起」，降低误触与操作心智负担。

## ★ 左滑手势已禁用（2026-08-09 决策）
左滑上线后实测仍「与页面纵向滑动同时发生」。
**根因**：uni-app `<scroll-view>` 在更底层捕获 touch 事件，子元素 `e.stopPropagation()` 对**原生滚动**无效；
手写方向锁只能拦 JS 冒泡，拦不住 scroll-view 自身的纵向滚动手势 → 横向意图锁定后屏幕仍纵滑，两者并发。
该冲突在「可滚动列表 + 手写 touch 判定」组合里近乎无解（除非自实现虚拟滚动或改 catch:touchmove 拦截），
故**撤掉左滑，保留 ⋯ 点击滑出 作为唯一展开入口**（同套 translateX UI，零冲突、最稳）。
template 中 `@touchstart/@touchmove/@touchend` 与脚本 `onItemTouchStart/Move/End`（含 `_touch*` 变量）
均暂注释保留，便于日后回滚或改用 catch 方案重做。

### 当前交互终态（pages/index/index.vue，左滑禁用后）
- `openMac` 互斥记录展开项；`backWidth=168`。
- 展开入口：`toggleItem(mac)`（⋯ 点击 → `openMac` 同值清空、异值设为该项，滑动 UI）。
- 收起入口：① `onFrontTap(mac)` 已展开点前景空白 → 收起；② `onListTap()` 列表空白 → 收起所有；③ `toggleItem` 再点互斥。
- 删除/默认/连接按钮保留 `@tap.stop`，不触发收起逻辑。

## ⑦ 「已知设备 (N)」标题排版 —— 对齐控制页（2026-08-12）
P1-② 收尾后又一轮纯 UI 排版打磨，目标是让首页重连卡片的标题"已知设备 (N)"**和控制页观感一致**。过程踩了几个坑，逐一记清楚，免得下次又绕。

### 用户原始诉求
「像控制页那样，(N) 放在『已知设备』下面居中」。

### 关键认知坑：控制页"实际样子" ≠ 源码样子
- 我先查 `control.vue` 源码，看到 `reconnect-label { font-size:22rpx; color:var(--text-tertiary); }` 是**单行一行**（`已知设备 (N)` 在同一行，左对齐），于是误判"控制页没居中"。
- 用户发来控制页截图后，我误读成"分两行、(N) 整行居中"，做出了 flex column + `width:100%` 的两行整行居中方案。
- **用户纠正**：控制页的 `(N)` 是落在"已知设备"四个字里"知"和"设"的正下方（即按四字整体中心对齐），且**字号和控制页一致（22rpx / text-tertiary）**，并不更大。
- 我一度把字号错改 26rpx / text-secondary，用户要求改回 22rpx / text-tertiary。
- 又一度为了"两行居中"加 `width:100%`，导致 (N) 被**整张卡片宽度**居中（"太宽"），与控制页"只在四字下方居中"不符。
- 还出现过"已知设 / 备"折行——因为 flex column 容器在窄宽度下把单行文字挤折了，需 `white-space:nowrap` 兜底。

### 终态方案（用户手动微调后定稿）
**模板**（多设备列表 + 单卡两处都改）：
```html
<view class="reconnect-label">
  <text class="reconnect-title">已知设备</text>
  <text class="reconnect-count">({{ bleStore.knownDevicesList.length }})</text>
</view>
```
**样式**：
```css
/* 对齐控制页观感 —— "已知设备"一行，(N) 在四字正下方居中（落在"知""设"间），不整行居中。 */
.reconnect-label { display: inline-flex; flex-direction: column; align-items: center; gap: 2rpx; margin-bottom: 8rpx; margin-right: 12rpx; }
.reconnect-title { font-size: 22rpx; color: var(--text-tertiary); white-space: nowrap; }
.reconnect-count { font-size: 22rpx; color: var(--text-tertiary); white-space: nowrap; }
```
**要点**：
- 用 `display:inline-flex`（不是 `flex` / 不是 `width:100%`）→ 容器宽度**收缩到"已知设备"四个字本身宽度**，不撑满卡片；
- 内部 `flex-direction:column` + `align-items:center` → 第二行 `(N)` 只在四个字正下方居中（落在"知""设"之间），而非整行居中；
- `white-space:nowrap` 防窄容器把"已知设备"折成两行；
- 字号/颜色严格对齐控制页 `22rpx / var(--text-tertiary)`；
- 用户手动补 `margin-right:12rpx` 让标签与右侧设备名留点呼吸间距（已纳入）。

### 经验固化
- **"对齐控制页"类需求，永远以用户截图 / 真机观感为准，不要只信源码**——源码是单行，但渲染+字体度量让 (N) 视觉落在四字下方。
- flex 容器想"内容宽度自适应、不撑父"→ 用 `inline-flex` 而非 `flex`+`width:100%`。
- 改 `index.vue` 标题排版时，多设备列表 + 单卡两处都要同步改，否则两处观感不一致。
