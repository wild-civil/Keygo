# 复盘：BLE 设备名重名坑 —— MAC 字段结构 + CH582 字节序 + 业界命名参考

> 日期：2026-08-21
> 固件：CH582M_BLE_Slave（peripheral.c / Peripheral_BuildBroadcastName）
> 关联：2026-08-21_BLE断连后设备名N_A_scanRsp丢失复盘.md

---

## 一、问题现象

同批次 CH582M 设备，MAC 前 5 字节相同、仅末字节不同，例如：
- `E4:66:E5:5C:D8:BB`
- `E4:66:E5:5C:D8:B9`

实测多台设备广播名**全部显示为 `KeyGo-E5566E4`**（按当前代码 `[3][4][5]` 应得 `KeyGo-5CD8BB`，但实际不是）。
→ App 按名扫描无法区分多台设备、存在误连/不可选风险。

（前述 scanRsp 丢失修复后名字能显示，但暴露了"重名"这一更隐蔽的问题。）

---

## 二、MAC 地址字段结构（必读）

```
44:90:46 : 95:C2:9B     ← 以手环为例
└─OUI──┘   └─NIC─┘
```

| 字段 | 字节 | 含义 | 同批次是否相同 |
|---|---|---|---|
| **OUI** | 前 3 字节（44:90:46） | IEEE 分配给厂商的厂商标识 | **完全相同**（厂商+批次决定） |
| **NIC** | 后 3 字节（95:C2:9B） | 厂商自分配的设备唯一标识 | **不同**（全球唯一） |

第 1 字节还有 2 个特殊位（以 `44`=`0100 0100` 为例）：
- **U/L 位**（第 2 bit）：0=全局唯一（出厂 MAC）/ 1=本地管理
- **I/G 位**（最低 bit）：0=单播 / 1=组播

**核心结论**：区分不同设备的唯一字段是 **NIC（后 3 字节）**。用 OUI 段做名字 = 同批次 100% 重名。

---

## 三、CH582 特有的字节序坑（关键）

`GetMACAddress()` 返回的 `g_deviceMac[6]` 是 **小端存储**：

```
g_deviceMac[0..5] = BB D8 5C E5 66 E4   （小端，[0]=MAC 末字节）
广播出去的 MAC     = E4:66:E5:5C:D8:BB  （大端，人类可读）
```

证据：`HAL/MCU.c` 中 `cfg.MacAddr[i] = MacAddr[5 - i]` —— 协议栈在初始化时把
`GetMACAddress` 的返回**翻转**成标准大端再对外广播。

因此：
- **NIC（设备唯一段）= 数组视角的 `[0][1][2]`**（小端下 `[0]=BB` 是末字节）
- OUI 段 = 数组视角的 `[3][4][5]`（`E5 66 E4`）

**当前代码 `Peripheral_BuildBroadcastName` 用 `[3][4][5]` → 取到的是 OUI 段 → 同批次重名。**
这正是 `KeyGo-E5566E4` 撞车的根因。

## 四、荣耀手环命名规则参考（业界范本）

手环 MAC：`44:90:46:95:C2:9B` → 名字：`HONOR Band 9-29B`

后缀 `29B` 的来历：取 **MAC 末 2 字节（`C2:9B`）的低 12 位**：
```
0xC29B = 1100 0010 1001 1011
低12位  = 0010 1001 1011 = 0x29B → "29B"  ✅
```
（关于名字中 `9-` 的来源辨析：用户曾猜测"取 `90` 的 9 + `-` + `C2` 的 2 + 末 `9B` → `9-29B`"，
形式上可拼出。但更准确的解读是：**`HONOR Band 9` 的 `9` 是型号号（Band 9），并非来自 MAC 的 `90`**；
真正从 MAC 派生的只有后缀 `29B`。因此 `90` 的 `9` 与名字里的 `9` 只是巧合（同型号第 2 字节都是 `90`，
若真取 OUI 段则所有同型号手环前缀相同、无区分度，语义上也错误——设备后缀应只表达"这台设备的唯一性"）。
跨 OUI/NIC 三段抽字符 + 拼字符串的实现既碎又易错，**工程上厂商不会这么做**；唯一干净、可测试、
跨平台一致的解释仍是末 2 字节低 12 位（`0xC29B & 0x0FFF`）。）


**荣耀做法印证了本文结论**：
1. 用 MAC **尾部（NIC 段）**，不用头部 OUI；
2. 做**短编码截断**（12 bit = 3 字符）以缩短名字、并避免暴露完整 MAC（隐私）；
3. 结构 = 固定前缀 + 唯一后缀（`HONOR Band 9-` + `29B`），与我们的 `KeyGo-` + 后缀一致。

## 五、首 3 vs 末 3，哪个更不容易重名

| 取法 | 内容 | 同批次 | 跨厂商 |
|---|---|---|---|
| 首 3 字节 `[3][4][5]`（OUI） | 厂商标识 | **必重名** ❌ | 同厂必同 |
| 末 3 字节 `[0][1][2]`（NIC） | 设备唯一段 | **不重名** ✅ | 几乎不撞 |

**末 3 字节（NIC）完胜。** 首 3 字节是同批次最差选择（已踩坑）。

### 业界常见命名策略（按普遍度）
1. **完整 MAC 6 字节全编码**（如 `KeyGo-E466E55CD8BB`，14 字符）→ 零重名，最稳。
2. **MAC 末 2~3 字节（NIC）短编码** → 同厂商多设备最常用折中（荣耀即此类）。
3. **出厂烧录序列号 / 唯一 ID**（DataFlash）→ 不依赖 MAC，防 MAC 被改。
4. **哈希 / MAC 后几位 + 校验** → 少数场景。

## 六、我们的修复方案（✅ 已实施 2026-08-21）

把 `Peripheral_BuildBroadcastName` 的名字后缀从 `[3][4][5]`（OUI，重名）
改为 **`[0][1][2]`（小端 NIC 段，已含变化的末字节）**，代码已落地：

```c
static void Peripheral_BuildBroadcastName(char *out, uint8_t outSize)
{
    /* ★ 2026-08-21 修复重名: CH582 GetMACAddress 返回【小端】, g_deviceMac[0..5]=BB D8 5C E5 66 E4
     *   (数组[0]=MAC 字符串末字节)。NIC(设备唯一段)在 [0][1][2], 含变化的末字节(BB/B9);
     *   [3][4][5]=E5 66 E4 是 OUI(厂商标识, 同批次必相同) → 旧代码取此段致所有设备重名 KeyGo-E5566E4。
     *   改取 [0][1][2](NIC 末3字节): ...:BB→KeyGo-BBD85C, ...:B9→KeyGo-B9D85C, 可区分不误连。 */
    snprintf(out, outSize, "KeyGo-%02X%02X%02X",
             g_deviceMac[0], g_deviceMac[1], g_deviceMac[2]);
}
```

效果：
- `E4:66:E5:5C:D8:BB` → `KeyGo-BBD85C`
- `E4:66:E5:5C:D8:B9` → `KeyGo-B9D85C`
- 同批次后缀不同 → App 可区分、不误连。

> 备选：若要求绝对零重名（如混用不同批次板），可改 6 字节全编码
> `KeyGo-%02X%02X%02X%02X%02X%02X`（15 字符，scanRsp 仍装得下）。当前 `[0][1][2]` 已足够。

注意：`Bonding_BuildSerial` 用 6 字节全编码本就唯一，无需改动；仅广播名取错段需修。

## 七、经验沉淀

1. **BLE 设备名必须用 NIC（MAC 后段），绝不能用 OUI（前段）**——同批次必重名。
2. **CH582 `GetMACAddress` 返回小端**：数组 `[0]` 是 MAC 字符串末字节，NIC 在 `[0][1][2]`。
   协议栈初始化时 `cfg.MacAddr[i]=MacAddr[5-i]` 翻转为大端对外广播，二者顺序相反，易踩坑。
3. **验证命名规则用数据说话**：手环 `29B` = 末2字节低12位（`0xC29B & 0xFFF`），
   而非"抽字符拼接"——字节边界运算才靠谱。
4. **小端/大端 + OUI/NIC 两个维度要同时考虑**，否则像本案一样取到 OUI 还以为是 NIC。
5. 断连 scanRsp 丢失 Fix 之后，**重名是下一个隐蔽坑**：名字能显示 ≠ 名字唯一。
