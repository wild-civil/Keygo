# KeyGo UI 高频 BLE 通知流渲染策略分析（2026-07-24）

> 背景：连接页/控制页出现「温度数字跳动」「横向抖动失控」现象。根因拆成两类独立问题：
> ① **数据速率 / 渲染抖动**（每条 FF02 同步改 N 个响应式属性 → 每次通知 = 一次渲染，回前台 burst 砸来几十条 → 狂跳/一次性涌出）；
> ② **DOM 生命周期**（顶层 `v-if(connected)` 在重连期翻转 → swiper-item 子树被挂载/卸载 → 父 swiper 手势追踪被打断 → 横向抖动，且不自愈直至重启）。
> ② 只能靠 `v-show`，节流救不了；① 才是「要不要在入口合并通知流」的问题。
> 本文对比四种业界处理模式（A 渲染节拍合并 / B 流控算子 / C last-value-wins / D keep-alive·v-show），并给出本 App 选型。

---

## 0. 先澄清一个关键误判：固定 200ms 定时器与 100ms RSSI 间隔的冲突

结论：**固定 200ms 提交定时器会和固件间隔错配，但不是模式 A 的本质限制。**

### 0.1 错配推导（固件每 100ms 发一条 status，每条含 `t`/`rssi`）

| 时刻 | 事件 | 暂存对象 | 200ms 定时器提交的 store 值 |
|---|---|---|---|
| 0ms | 包①到 | X0,R0 | — |
| 100ms | 包②到（覆盖暂存） | X1,R1 | — |
| 200ms | 定时器触发 | X1,R1 | **X1,R1**（X0/R0 被丢弃） |
| 200ms | 包③到 | X2,R2 | — |
| 300ms | 包④到 | X3,R3 | — |
| 400ms | 定时器触发 | X3,R3 | **X3,R3** |

- 显示只以 **5Hz（200ms）** 刷新，隔一个样本丢一个 → **设 100ms 实际显示 200ms 粒度（降级）**。
- 反向：固件间隔 300ms（比 200ms 慢）→ 定时器每 200ms 提交一次但暂存值未变 → 同值重复提交（无害但浪费）。

即**固定定时器把「显示速率」与「包速率」解耦成「取较慢者」**，这就是冲突来源。

### 0.2 正解：用 `requestAnimationFrame` 替代固定定时器（推荐）

`rAF` 在页面活跃时约每 **16.7ms（60fps）** 触发，两个关键性质：
- 包间隔 100ms > 16.7ms → 每条包到达后 ~16ms 内被提交 → **100ms 粒度完整保留，不降级**。
- 回前台 burst（多条包挤在 16ms 内）→ 全堆进暂存，下次 rAF 只提交一次 → **依旧合并，不狂跳**。

→ **rAF 变体的模式 A 自动适配任意固件间隔，根本不存在 100ms/200ms 冲突。**
唯一注意：标签页后台时 rAF 暂停——恰好是期望行为（后台只攒最新值，回前台一次性提交、不回放历史）。

退路（若对 webview rAF 不放心）：让提交间隔跟随固件间隔 `commitInterval = clamp(firmwareInterval, 100, 2000)`（即现有 `rssiReadPeriodMs` 做法），同样消除错配。

## 1. 四种模式利弊分析

### 模式 A：渲染节拍合并（Frame-coalesced commit）

**原理**：通知处理层不直接改响应式状态，而是写进一个**普通（非响应式）暂存对象**；由一个 `rAF`（或自适应定时器）把「最新暂存值」一次性 `Object.assign` 进 store。Vue 把这次同步提交里的所有字段变更合并成**一次渲染**。

```js
// 伪代码：入口合并，而非逐字段节流
let _staged = null                       // 非响应式暂存
function onStatusPacket(data) { _staged = data }          // 每条包只覆盖，不触发渲染
function flush() {                        // rAF / 自适应定时器一次
  if (_staged) { Object.assign(reactiveState, _staged); _staged = null }
  requestAnimationFrame(flush)
}
```

| 维度 | 评价 |
|---|---|
| ✅ 优点 | ① **一处修改，所有字段自动受益**，零扩展成本（未来加字段不用再想节流）；② 合并渲染，消除「一次性涌出/狂跳」；③ 解耦显示速率与包速率；④ 实现简单（一个暂存对象 + 一个 rAF）；⑤ 计数器 `ucnt/lcnt` 一并受益，解锁进度 N/N 仍「即时感」。 |
| ❌ 缺点 | ① 若用**固定**定时器才与固件间隔错配（见 §0，用 rAF 即消除）；② 引入 ≤1 帧（16~250ms）显示延迟，对遥测无感，但**命令反馈路径绝不能走这层**；③ rAF 后台暂停（实为优点）；④ 若 rAF 常驻运行有极轻微开销，可优化为「仅暂存有数据时才调度 rAF」。 |
| 适用 | 任何「高频传感器流 → UI」场景；Vue/React 通用。 |
| 本 App 落地成本 | 低。`_parseSingleStatus` 改「写暂存」，新增 rAF 提交循环；顺带可退休 `displayRssi`/`rawRssiDisplay` 节流副本。 |

### 模式 B：流控算子（RxJS `sampleTime` / `throttleTime`）

**原理**：把通知建模成流 `notify$.pipe(sampleTime(200))` 或 `throttleTime(200,{leading:false,trailing:true})`——只采样/节流「流」的最新值。

| 维度 | 评价 |
|---|---|
| ✅ 优点 | ① 声明式、组合性强，复杂流（`debounce`/`buffer`/`window`）易表达；② 同样是「节流流而非字段」，理念与 A 一致。 |
| ❌ 缺点 | ① **引入 RxJS 依赖**（包体积、学习曲线），本 App 现状零 RxJS，为这点功能加重框架属过度工程；② 小程序侧 RxJS 体积受限（虽本 App 是纯 App）；③ 概念等价于 A，但成本更高；④ 同样存在固定窗口与固件间隔错配问题（用 `sampleTime` 取最近值也丢中间样本）。 |
| 适用 | 已用 RxJS 的大型流式应用，或流变换非常复杂的项目。 |
| 本 App 落地成本 | 高（引依赖 + 改写入口）。不推荐。 |

### 模式 C：last-value-wins + rAF（React `useRef` 模式）

**原理**：模块持有可变 `latest` 变量，每条包 `latest = data`；rAF 里 `commit(latest)`。**与模式 A 同源**——`latest` 即 A 的「暂存对象」，`useRef` 即「非响应式容器」。

| 维度 | 评价 |
|---|---|
| ✅ 优点 | 与 A 完全等价；在 React 里因 `useRef` 天然非响应式，表达更地道。 |
| ❌ 缺点 | 在 Vue 里就是 A 的「暂存对象」实现，**无额外收益**；概念上 C ⊂ A，单列意义不大。 |
| 适用 | React 技术栈。 |
| 本 App 落地成本 | 等同 A（即 A 本身）。 |

### 模式 D：keep-alive / v-show（DOM 稳定性）

**原理**：连接相关 UI 用 `v-show`（仅切 `display`，不挂载/卸载）或 `keep-alive` 常驻，避免父容器（`<swiper>`）的子树在 `connected` 翻转时被重建。

| 维度 | 评价 |
|---|---|
| ✅ 优点 | ① **治横向抖动唯一正确的位置**（纯 DOM 生命周期问题，节流救不了）；② 实现简单，纯模板改动；③ tab 容器业界标准做法（保持节点常驻、只切显示）。 |
| ❌ 缺点 | ① **只解决 DOM 重建/手势问题，不解决数据速率/渲染抖动**——必须与 A 配合；② `v-show` 节点常驻有微小内存成本（可忽略）；③ `v-show` 元素初始即渲染，若含重计算可能影响首屏（本场景连接态 UI 不重，无影响）。 |
| 适用 | 任何「连接态/登录态切换导致父容器子树重建」引起手势/动画异常的场景。 |
| 本 App 落地成本 | 极低。连接页/控制页块状 `v-if(connected)` → `v-show`。 |

## 2. 模式关系与选型矩阵

| 模式 | 本质 | 解决抖动? | 解决数字跳动? | 引入依赖 | 本 App 推荐 |
|---|---|---|---|---|---|
| A（rAF 变体） | 入口流合并 | ❌ | ✅ | 无 | ★ 推荐（治跳动） |
| B（RxJS） | A 的流库实现 | ❌ | ✅ | RxJS | ✗ 过度工程 |
| C（useRef） | A 的 React 表达 | ❌ | ✅ | 无 | =A（Vue 里即 A） |
| D（v-show） | DOM 常驻 | ✅ | ❌ | 无 | ★ 推荐（治抖动） |

关键判断：
- **B、C 本质是 A 的特化**——B = 用流库的 A，C = React 里的 A。不引入额外依赖时，A+D 最务实。
- 「每个字段都节流」是**错误方向**：不可扩展、重复状态（`displayRssi`/`rawRssiDisplay` 即打补丁遗留），应升级为「在入口把流合并成固定渲染节拍」。
- 抖动（D）与跳动（A）是**不同问题、必须分别治理**，不能指望一个节流同时解决。

---

## 3. 推荐落地方案（本 App）

**组合 = 模式 A（rAF 变体）+ 模式 D（v-show）**，一次性根治，未来加字段零额外成本。

1. **入口流合并（A·rAF）**
   - `onBLECharacteristicValueChange` → `_parseSingleStatus` 改「写非响应式暂存对象」。
   - 单一 rAF 循环把「最新暂存值」`Object.assign` 进响应式 store；仅暂存有数据时才调度 rAF。
   - 退休 `displayRssi` / `rawRssiDisplay` 节流副本（流合并成立后不再需要；UI 直接用 `rssi`/`filteredRssi`）。
2. **连接态 UI 常驻（D·v-show）**
   - 连接页/控制页所有块状 `v-if(connected)`（signal-section / conn-extra / temp-card / status-rssi / control 顶层等）→ `v-show`。
   - 保留的 `v-if` 仅限小文本/已隐藏内部块。
3. **命令下发路径（写 FF03）不合并**：那是控制指令，必须即时，绕过暂存层。
4. **延迟评估**：通知到显示最多晚 1 帧（16~250ms），对车锁遥测完全无感；计数器 `ucnt/lcnt`、解锁进度仍「即时感」。

---

## 4. 结论

> 不是「每个数据都节流」，而是「在通知入口把流合并成固定渲染节拍（模式 A·rAF）+ 连接态 UI 用 v-show 常驻（模式 D）」。节流对象应该是**流**，不是**字段**。
> 固定 200ms 定时器才会与 100ms 固件间隔冲突（降级显示）；改用 rAF 后该冲突自动消失，且保留任意粒度、合并回前台 burst。

## 5. 追问 refine：自适应提交间隔 = RSSI 间隔（用户 2026-07-24 追问）

用户提议：把固定 200ms 定时器改为「跟随 RSSI 间隔」，是否即完美？深度分析如下。

### 5.0 事实基线：三个独立频率（固件实测，关键纠正）

| 层 | 含义 | 周期（固件实测） | 控制方 |
|---|---|---|---|
| ① 采样 | 传感器读一次 | 温度 **5s**（`TSENSE_SAMPLE_INTERVAL_MS=5000`）／电量 **30s**（`SBP_BATTERY_CHECK_PERIOD=48000` tick×0.625ms=30s，且仅变化时 `Battery_Notify`）／RSSI = App 下发 `interval`（`KeyGo_GetRssiPeriodTicks`） | 固件 |
| ② 发送 | status 包推一次 | **1s**（`SBP_PERIODIC_EVT_PERIOD=1600` tick=1s，独立于 `interval`）+ 阈值穿越即时发 | 固件 |
| ③ 显示 | App 刷屏时机 | 现状：temp/rssi 每条包(~1s)直写；displayRssi 受 `rssiReadPeriodMs` 节流 | **App（要改的）** |

- tick 单位：`peripheral.h:54` 注释 "TMOS tick ≈ 0.625ms" → `1600×0.625=1000ms`、`48000×0.625=30000ms`。
- **电量不是 5s 而是 30s**，且当前取自 3.3V LDO 恒 ~100% → 基本不变。温度 5s。两者均远慢于 1s 包速率 → **都不是跳动源，跳动源是 RSSI（每条波动）**。
- ⚠ **关键定性（用户点破）**：本方案只改 **第③层「显示提交时机」**，**完全不动 ①采样(5s/30s/interval) 与 ②发送(1s)**。即「数据多新鲜」不变，只决定「多久呈现一次已收到的数据」。

### 5.1 必须先纠正的模型偏差（来自固件实测）

固件 `KeyGo_NotifyStatus()`（`keygo_core.c:891-932`）把所有字段塞进**同一条 JSON**：
`{"c":1,"st":...,"r":,"f":,...,"ucnt":,"lcnt":,"th":,...,"t":,"er":...}`。

- **温度 `t` 与 RSSI `r`/`f`、计数 `ucnt`/`lcnt`、阈值 `th`、模式 `m` 等全在同一条 status 报文（多路复用）**。
- **该 JSON 无 `b`（电量）字段**：电量走独立 Battery Service（`_fetchBatteryLevel` GATT 读 / `Battery_Notify`），不在 status 流内。

→ 因此：
1. **温度"跟着"RSSI 间隔 = 无害且本该如此**：温度固件侧 5s 缓存（`TSENSE_SAMPLE_INTERVAL_MS=5000`），burst 内同值 → Vue 原语等值不重渲染。
2. **电量不会跟着变慢（好消息）**：电量走独立路径，应**绕过暂存层、即时提交**，与 RSSI 间隔解耦。
3. **控制流副作用必须绕过暂存**：命令回执 `st=UNLOCKED`（立即 `resolve` 命令 waiter，`ble.js:3108`）、`NONCE`/`AUTH`、toast —— 这些只进「周期性 status 流」的暂存层会误延迟控制确认，绝不可 staging。

### 5.2 自适应定时器 = rssiReadPeriodMs 是不是完美？

App 侧基本完美，且本质就是现有 `displayRssi` 节流窗口（`rssiReadPeriodMs`，`ble.js:3081-3083`）的**泛化**（从"只管 RSSI"扩到"管整条 status 流"），一处修改即可退役所有逐字段节流副本。

**但有一个固件侧的不完美（来自 `ble.js:3082` 注释）**：
> FF02 通知周期(~1s)独立于此，故显示实际最多每 1s 跳一次（除非固件 FF02 周期也跟随 interval）。

即 App 下发的 `interval` 只改**固件内部 RSSI 采样率**，**status 包发送周期仍 ~1s**（加阈值穿越即时发）：
- 设 `interval=100ms` → 定时器窗口 100ms，但**包每 ~1s 才来** → 实际显示仍 ~1s（定时器快不过包速率）。
- 设 `interval=2000ms` → 窗口 2000ms > 包速率 1s → **丢包**（每两条提交一条）。

→ 真正让显示跟随 RSSI 间隔需**固件 FF02 发送周期也跟随 interval**（注释那句"除非…也跟随"）。当前未做；但对遥测 1s 足够，属概念上限非实际痛点。

### 5.3 工程补丁（避免 interval>1s 丢包）

提交间隔取 `commitInterval = Math.min(rssiReadPeriodMs, 1000)`：
- `interval ≤ 1000ms`：严格跟随用户设置；
- `interval > 1000ms`（省电档）：封顶 1000ms，保证**不慢于包速率、不丢包**，且比"固定 200ms"更贴合意图。

### 5.4 与上轮 rAF 对比

| 维度 | 自适应定时器 = rssiReadPeriodMs（封顶 1s） | rAF（§1 变体） |
|---|---|---|
| 显示延迟上限 | ≤interval（封顶 1s） | ≤16ms |
| 实际差异 | 固件包 ~1s，两者都≈1s 落地 | 同左，理论更猛无实测收益 |
| 依赖/复杂度 | 零，复用现有 `rssiReadPeriodMs` | 需 dirty 调度优化；webview rAF 有怪癖 |
| 结论 | **更贴合本 App、更简单** | 边际收益，不划算 |

**结论**：自适应定时器 = RSSI 间隔（封顶 1s）即本 App 的「完美」解；rAF 仅理论更低延迟，但被固件包速率卡住无实际差别。唯一真·上限是固件 FF02 周期未跟随 interval（需固件改，且当前不需要）。

## 6. 用户最新三问：1s 刷新？50 条积压从哪来？现在只显最新？

基于 `stores/ble.js` 实代码（3077/3085/3093-3097/3260）逐条回答。

### 6.1 现在的显示是 1s 刷新一次吗？

**稳态（正常连接、App 前台）下：是，≈1s。** 但机制要分清楚：

- **固件 status 包发送周期恒 1s**（`SBP_PERIODIC_EVT_PERIOD=1600` tick，§5.0 ②层）。每来一条，App 立刻跑 `_parseSingleStatus`。
- `rssi` / `filteredRssi` / `deviceTempC` **每条包直写响应式 state（零节流）** → 每条包 = 一次写入。
- `displayRssi` / `rawRssiDisplay` 受 `rssiReadPeriodMs` 节流，**默认窗口 500ms**（< 1s 包间隔）→ 节流从不拦截，等于每条包也写入。

→ 三个字段的写入节奏都被「包到达」卡在 **1s**，所以**当前稳态显示确实 ≈1s 刷新**（温度 5s 才变一次 → 显示每 5s 跳一档；电量 30s/变化）。

⚠ **一个隐藏陷阱**（来自 `ble.js:3338`）：`rssiReadPeriodMs = clamp(interval, 100, 2000)`。若用户把采样间隔设到 **2000ms**，节流窗口变成 2000ms > 1s 包周期 → `displayRssi` 每两条包才提交一次 → **显示反而掉到 2s（丢一半）**。这正是 §5.3 要 `Math.min(rssiReadPeriodMs, 1000)` 封顶的原因。默认 500ms 时不会发生。

> **实测澄清（2026-07-24 用户反馈："感觉像 500ms"）**：FF02 稳态周期**确为 1s**（`SBP_PERIODIC_EVT_PERIOD=1600` tick × 0.625ms，唯一稳态来源 + 阈值穿越即时发）。觉着"像 500ms"是两个**不同来源**，均非"FF02 每 500ms 发一次"：
> 1. **500ms 是「固件 RSSI 采样」间隔**（`SBP_READ_RSSI_EVT_PERIOD=800` tick=500ms，即 App `rssiReadPeriodMs` 默认 500）。它**只喂内部 Kalman 滤波 / 解锁判定，并不发 FF02 状态包**——`peripheralRssiCB`→`KeyGo_RssiProcess` 内**无 `KeyGo_NotifyStatus` 调用**，全工程仅 `peripheral.c:482`（周期）、`keygo_core.c:854`（计数器变化即时）、命令回执（one-shot）三处推 FF02。所以显示数字**仍只在 FF02 到达时（1s）变化**。
> 2. **走动时显示会快于 1s**：`KeyGo_NotifyStatus` 在 `g_unlockCounter`/`g_lockCounter` 变化（RSSI 穿越 uc/lc 阈值区）时**即时触发**（`keygo_core.c:854-857`）。走动中 RSSI 反复穿越阈值 → 频繁即时推 FF02 → 显示更新节奏短于 1s。
>
> **结论**：稳态（人/车都静止）显示严格 1s；**500ms 是采样率不是显示率**；移动会让显示快于 1s。不要用 `rssiReadPeriodMs`(500ms) 的值去推断 FF02 显示周期。

### 6.2 为什么「之前」会出现 50 条积压包依次显示（回放/狂跳）？

"50 条积压"不是稳态，是**异常突发（burst）**，来源有二：

1. **后台积压 → 回前台释放**：App 退回后台时 webview/JS 线程被节流或暂停，但 BLE 连接（尤其前台服务/OS 加密链路）仍活，固件照常每 1s 发 status。这些通知在 OS/BLE 栈侧排队，JS 没空 drain。回前台瞬间队列被一次性 flush——若后台 50s 就积压约 50 条。
2. **重连/订阅竞态释放**：断重连瞬间，BLE 栈可能把缓冲的通知一次性放出。

为什么这 50 条会"依次显示"而非 Vue 自动合并？
- Vue 3 的渲染批处理**只在「同一同步执行块」内**合并：同一 macrotask 里的多次写入 → 一次渲染（只看末值）。
- 但 `onBLECharacteristicValueChange` 是**逐条异步回调**：50 条 = 50 次独立回调，回调之间 JS 线程让出 → 渲染调度器在每条回调后各自 flush → **50 次渲染，每次显示该条包的值** → UI 肉眼可见地"回放"历史（包①→包②→…→包⑤₀），即用户说的"依次显示/疯狂跳跃"。

**实证据对齐（§5.0 已记）**：控制页头条信号绑的是**未节流的 `filteredRssi`**（`ble.js:3085` 每条直写），连接页大号 RSSI 绑的是**受节流的 `displayRssi`**（`ble.js:3093`）。所以用户实测"连接页正常、控制页乱跳"完全吻合——`displayRssi` 已被节流挡掉大部分 burst，而 `filteredRssi` 全程裸奔。这正是 2026-07-24 已做的"头条改绑 displayRssi"补丁要修的真因。

### 6.3 现在要做的是「50 条积压包只显示最后一次/最新数据」吗？

**对，正是 last-value-wins 合并（模式 A 的本质）**。落地行为：

```
50 条包到达 ──每条约 1s 间隔、但回前台被压缩在极短时间内──
   每条：_staged = 该包数据      （非响应式，零渲染、零开销）
   ── 窗口结束（rAF / Math.min(interval,1000) 定时器）──
   一次 Object.assign(reactiveState, _staged)   → 仅渲染 1 次
   显示 = 第 50 条（最新）的值；第 1~49 条的中间值被「覆盖丢弃」，不进入 UI
```

- **不是「永久丢数据」**：节流/合并只作用于「显示层」；若将来 App 侧有需要每条样本的控制逻辑，应让它读「未暂存的实时字段」或单独处理。当前本 App 的阈值判定/解锁决策**都在固件侧**（per-phone 阈值由固件评估），App 只展示，故丢弃中间显示值对控制零影响。
- **效果**：50 次渲染 → 1 次；UI 直接显示最新态，不回放历史、不狂跳。
- **顺带退役现有补丁**：`displayRssi`/`rawRssiDisplay` 节流副本（只为拦 RSSI 字段）与"头条改绑 displayRssi"补丁，在流合并成立后都不再需要——整条 status 流统一在入口合并，一处修改全字段受益。

### 6.4 三问小结

| 问题 | 答案 |
|---|---|
| 现在显示是 1s 刷新吗？ | 稳态≈1s（被 1s 包速率卡）；`rssiReadPeriodMs` 默认 500ms 不拦截。设 2000ms 会因节流窗口>包周期反掉到 2s（须封顶 1s）。 |
| 之前为何 50 条依次显示？ | 后台/重连积压 → 回前台逐条异步回调 flush，每条触发一次渲染 → 回放历史。控制页（绑未节流 `filteredRssi`）尤其明显，连接页（绑已节流 `displayRssi`）较轻。 |
| 现在只显最新吗？ | 是。暂存层 last-value-wins + 窗口一次提交：50 条只渲染 1 次、显示最新值；中间值被覆盖丢弃（仅显示层，不影响固件侧控制）。 |

## 7. 长期后台 → 回前台：显示该怎么做（用户 2026-07-24 最新纠结）

用户两个提议：
- 甲：长时间后台，App 只显示"接收到的最新的数据"。
- 乙：切到前台显示的那个数据，切回后台后还显示它、直到收到新数据（即"冻结"前台值）。
用户直觉乙"不太合适"，求更好方案。

### 7.1 结论先行
- **甲 = 我们方案本来就要做的（last-value-wins 暂存）**，天然满足：后台每来一条包只覆盖非响应式 `_staged`，绝不渲染，故后台 10 分钟也只在缓冲区留"一条最新值"，回前台一次性提交、无回放。
- **乙（冻结前台值）不可取**，理由见 §7.3。
- **真正该做的是「缓冲区在后台持续更新 + 回前台一次性提交 + 过期标 stale」**，见 §7.4。

### 7.2 先纠正一个隐含误解（关键）

"乙"担心的是：回前台会看到"离开前台时那个旧值"在闪。但 staging 设计下**缓冲区在后台是被每条包持续覆盖的**——

> 你离开前台时站在车边（RSSI -40）；走开 200m 后后台仍每 1s 收包 → 缓冲区早被更新成 -80。回前台提交的，是**后台最新的 -80**，不是离开时的 -40。

所以"旧前台值残留"在 staging 下**根本不会发生**。只有"后台不更新缓冲区"才会残留，而我们的设计恰恰是**持续更新**的。这正是 §6.3 last-value-wins 的精髓。

### 7.3 为什么"冻结"不好

1. **后台屏幕不可见**，冻结在视觉上零收益（用户根本看不到后台的屏幕）。
2. 若"冻结 = 忽略后台所有包"，回前台看到的是离开时的陈旧值，反而更误导，且丢失了后台这 10 分钟的真实变化。
3. 若"冻结 = 抑制提交直到新包"，那本就等价于正常逻辑（收包才更新），无额外保护。
4. 正确防"误导旧数据"的手段是 **`statusStale` 看门狗**（连续无 FF02 超时即判过期 → 显示 `--`/「信号过期」），**不是冻结数值**。冻结会在连接仍活时错误地长期显示一个静态数，比"收包才更新"更糟。

### 7.4 推荐设计（最终形态）

1. **后台**：每条 FF02 仍跑 `_parseSingleStatus`，但只写非响应式 `_staged`（last-value-wins）；不触发渲染（页面不可见，rAF 暂停）。
2. **回前台**：一次 `Object.assign` 提交 `_staged` 最新值 → 仅 1 次渲染，显示**后台最新真实值**，**无回放**（根治 §6.2 的 50 条依次显示）。
3. **首帧即时（可选抛光）**：`onShow` 时立即 flush 一次暂存（不等下一个定时器/rAF），保证回前台第一帧就是最新值。
4. **过期兜底**：保留 `statusStale` 看门狗（>4s 无包 → 显示 `--`/过期标识），绝不明示一个"自信错误"的 RSSI。
5. **电量 / 控制流绕过暂存**（§5.1），即时提交，不受后台合并影响。

### 7.5 小结

| 方案 | 评价 |
|---|---|
| 甲：后台只留最新 | ✅ staging 天然满足 |
| 乙：冻结前台值 | ❌ 误导 + 后台不可见零收益，正确手段是 `statusStale` |
| **推荐：后台持续更新单值 + 回前台一次性提交 + 过期标 stale** | ✅ 直接显示当前真实态，无回放、无陈旧误导 |

稳态显示仍 ≈1s，温度 5s、电量 30s 不变；**唯一变化是：回前台不再回放历史，直接显示当前真实态；若已断连则正确显示过期/--**。
