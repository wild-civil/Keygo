# 蓝牙 Banner 全局横幅组件化抽取与跨页条件渲染

> 系列第 8 篇 · 主题：**组件抽取（抽离重复 UI）+ 跨页条件渲染（同一组件在不同 tab 的显隐门控）**
> 关联阅读：本系列 ②《小程序 v-show/v-if/display 切换》讲清显隐原语；⑥《蓝牙开启交互 modal 双弹 vs banner 引导》讲清红 banner 出现的产品动机；本篇聚焦"怎么把 banner 抽成一个全局组件，并在 4 个 tab 里只让 2 个显示"。

---

## 1. 背景：问题从哪来（fix11.3）

蓝牙横幅（红=已关闭 / 绿=正在开启）最早是 **内联在连接页 `pages/index/index.vue`** 里的。问题：

- 控制页（`pages/control/control.vue`）**没有横幅** → 用户在控制页切到"已关闭蓝牙"状态，看不到任何提示，体验割裂。
- 配置页、帮助页本来就不该显示（那里在讲功能，不是操作蓝牙）。
- 横幅的"开启"逻辑、`btState` 监听、权限申请散落在连接页，无法复用。

于是做了 **方案 1（v3.36.3fix11.3）**：把横幅抽成独立组件 `components/BtStateBanner.vue`，在 **壳页面 `pages/main/main.vue`** 顶层渲染，用一行条件控制它只在"连接页 / 控制页"出现。

```4:4:app/BLE_Key_Go_App/pages/main/main.vue
    <BtStateBanner v-show="tabIndex === 0 || tabIndex === 1" />
```

这就是"组件化抽取 + 跨页条件渲染"的全部：一个组件，渲染一次，靠外层条件决定它出现在哪些 tab。

## 2. 知识点一：组件化抽取（消除重复 UI 的硬规则）

### 2.1 什么时候该抽组件

判断标准（来自本项目的实际经验）：

| 信号 | 说明 |
|---|---|
| 同一段 UI 出现在 ≥2 个地方 | 红/绿 banner 本要出现在连接页+控制页 → 抽 |
| 它依赖同一份状态、同一套交互逻辑 | 都读 `bleStore.btState`/`connected`，开启都走 `bleStore.enableBluetooth()` → 抽 |
| 它和所在页面的主逻辑无关 | banner 是"全局系统状态提示"，不属于连接页的扫描列表、也不属于控制页的按键区 → 抽 |
| 改动频率一致 | 蓝牙开启交互一改，两页要同步改 → 抽成一处 |

**反例**：连接页里的"信号强度条""电量卡""进度卡片"只属于连接页，控制页没有 → **不抽**，留在原页用 `v-show`/`v-if` 局部控制即可。

### 2.2 抽取后的组件契约（BtStateBanner.vue）

组件是**纯展示 + 自包含交互**，对外零 props、零事件：

```23:31:app/BLE_Key_Go_App/components/BtStateBanner.vue
<script setup>
// ★ 原连接页内联横幅抽出的全局组件（方案1，v3.36.3fix11.3）。
// 仅由 main.vue 在「连接页(0) / 控制页(1)」渲染，配置页/帮助页不显示。
// 自身按 btState + connected 决定红/绿/无，开启逻辑与原 index.vue 完全一致。
import { watch } from 'vue'
import { useBleStore } from '@/stores/ble.js'
import { toast } from '@/utils/toast.js'

const bleStore = useBleStore()
```

设计要点（可复盘点）：

- **对外零 props**：组件自己 `useBleStore()` 拿状态，调用方（main.vue）只管"要不要显示"，不关心"显示什么"。这样壳页面最干净。
- **自己驱动状态机**：`btState`/`connected` 在 store 里，组件只消费。符合"状态上提、视图下沉"。
- **交互自闭环**：`handleEnableBluetooth()` 在组件内，含 App 端权限申请（`#ifdef APP-PLUS` 门控）+ MP 端静默（见 ⑥《modal vs banner》），调用方无需知道开启细节。
- **防止递归弹窗**：组件内用 `_enableBluetoothLocked` 防抖，避免用户狂点导致 `Modal`/`openBluetoothAdapter` 死循环（模拟器常见坑）。

> **经验法则**：被多个页面共享、且"只靠全局 store 就能自洽"的 UI，抽成**零 props 的展示+交互组件**最省心；别为了"看起来解耦"硬加 props 把状态往下传。

## 3. 知识点二：跨页条件渲染——`v-show` 在壳层门控

`main.vue` 用 `v-show="tabIndex === 0 || tabIndex === 1"` 决定 banner 在哪些 tab 出现。

```1:7:app/BLE_Key_Go_App/pages/main/main.vue
<template>
  <view class="main-root" :class="themeClass">
    <!-- ★ 全局蓝牙状态横幅（方案1, v3.36.3fix11.3）：仅连接页(0)/控制页(1)显示，配置页(2)/帮助页(3)不显示 -->
    <BtStateBanner v-show="tabIndex === 0 || tabIndex === 1" />
```

### 3.1 为什么选 `v-show` 而不是 `v-if`（在壳层）

壳层（main.vue）的 banner **不在 `swiper` 内部**（它在 swiper 之外、页面顶部），所以：

- 用 `v-if`：切到配置页就把 banner 卸载，切回连接页再挂载 → 每次切 tab 都重建组件，丢失组件内 `watch`、防抖锁等临时状态。**没必要**。
- 用 `v-show`：组件常驻 DOM，`tabIndex` 变化时只是 `display` 切一下，状态保留、切换零重建。**更合适**。

> 注意这与本系列 ② 的结论互补：② 说"在 swiper 内**绝不用 v-if**（会打断手势）"；本篇说"在 swiper **外**的壳层，v-show/v-if 都安全，选 v-show 更省"。两条规则不冲突——**关键变量是"是否在 swiper 内"**。

### 3.2 ⚠ MP 平台可靠性提醒（与 ② 一致）

② 已坐实：**`v-show`（编译成 `hidden`）在 mp-weixin 的 `view` 上也切不动 `display`**。所以这一行 `v-show="tabIndex===0||1"` 在**纯小程序端可能无法隐藏**——表现成"在配置页/帮助页也能看到蓝牙 banner"。

这是已知的小瑕疵（视觉层面，不影响功能）。若要彻底跨端稳，按 ② 的正解改：

```html
<!-- 稳健写法：:class + CSS display:none（详见 ②） -->
<BtStateBanner :class="{ 'banner-hidden': tabIndex !== 0 && tabIndex !== 1 }" />
```

```css
.banner-hidden { display: none; }
```

> **复盘要点**：壳层门控用 `v-show` 在 App 端完美，但 MP 端有 ② 描述的失效风险。本项目因 banner 在 MP 端显示与否只是轻微视觉问题（不遮挡操作），暂未强制改 `:class`；若你做正式跨端组件，建议**从一开始就走 `:class`+CSS `display:none`**，别等 MP 端出问题再返工。

## 4. 知识点三：组件内部红/绿互斥——用 `v-if`（故意）

组件内部红、绿两条 banner 是**互斥**的（同一时刻只能一种），且都在组件根 `view` 下、不在 swiper 内：

```7:19:app/BLE_Key_Go_App/components/BtStateBanner.vue
    <view class="bt-off-banner" v-if="!bleStore.connected && bleStore.btState === 'off'">
      <text class="bt-off-icon">🔴</text>
      <text class="bt-off-text">蓝牙已关闭</text>
      <button class="bt-enable-btn" @tap="handleEnableBluetooth">开启</button>
    </view>
    <!-- ★ 绿色"正在开启"横幅：与底部系统弹窗同步出现/消失，模仿 nRF Connect。 -->
    <view class="bt-on-banner" v-if="!bleStore.connected && bleStore.btState === 'just_enabled'">
      <text class="bt-on-icon">🟢</text>
      <text class="bt-on-text">正在开启蓝牙...</text>
    </view>
```

这里**故意用 `v-if`**（原来试过 `v-show` 踩过坑，注释里写明了）：

- 红/绿 banner 在**自定义组件内部** → ② 指出 `v-show` 在自定义组件里编译成 `hidden` 属性、小程序不支持 → **`v-show` 直接失效，红绿同显**。
- 改 `v-if`：互斥条件本就满足（一个 `off`、一个 `just_enabled`），同一刻只可能命中一个；用 `v-if` 把不命中的从 DOM 彻底移除，**跨端都稳**。
- 且组件不在 swiper 内，DOM 卸载不影响任何手势 → ② 的"别用 v-if"禁忌在此不适用。

> **复盘要点**：组件内部互斥 UI + 在自定义组件内 + 不在 swiper → **用 `v-if` 是对的**；在 page 内 view、要切 display 但不卸载、且可能在 MP → **用 `:class`+CSS（见 ②）**；在 swiper 内 → **绝不用 v-if（见 ②）**。三条规则按"所处位置 + 是否互斥 + 是否 MP"三维度组合判断。

## 5. 知识点四：banner 背后的状态机（`btState`）

banner 显示什么，完全由 store 的 `btState` + `connected` 决定。理解这个状态机，才能看懂"红绿何时切换、为何会卡"。

### 5.1 状态定义

```263:264:app/BLE_Key_Go_App/stores/ble.js
    btState: 'unknown',           // 'on' | 'off' | 'just_enabled' | 'unknown'
    _adapterReady: false,         // ★ 冷启动修复：本会话是否已 openBluetoothAdapter（避免 "not init" 误判）
```

### 5.2 状态驱动路径（含 MP 可达性）

| 触发源 | 赋值 | 平台可达性 | 备注 |
|---|---|---|---|
| `_mapNativeState`（原生广播，~739） | `just_enabled` | 仅 Android（`_nativeBtMonitorActive`，MP=false） | MP 不可达 |
| 原生广播 `STATE_TURNING_ON`（~829） | `just_enabled` | `typeof plus==='undefined' \|\| 非 Android` 直接 return | MP/iOS 不可达 |
| `onAllowing` 回调（~1207） | `just_enabled` | `#ifdef APP-PLUS` 剔除 | 纯 MP/iOS 不可达 |
| Uni 适配器事件 `STATE_ON`（~836） | `'on'` | 全平台 | 红/绿都消失 |
| Uni 适配器事件 `STATE_OFF`（~855） | `'off'` | 全平台 | 红 banner 出现 |
| `_reconcileBtState`（~1082） | `on`/`off` | 全平台 | 校正，含 ② 的延迟 `available=false` 保护 |

> **关键结论（坐实于 2026-07-25）**：`just_enabled`（绿 banner）在**纯 mp-weixin** 逻辑里三条赋值路径全不可达 → 纯小程序的绿 banner 不该出现。真机 MP 若看到绿 banner，要么是测的是"自定义调试基座"（有 plus+原生），要么是包未含最新代码。详见本系列 ② ⑥ 的 `[A1-DIAG]` 诊断日志说明。

### 5.3 两个保护逻辑（避免 banner 卡死）

1. **`just_enabled` 不被延迟事件覆盖**（~873）：用户点开启 → 原生广播设 `just_enabled`（绿）→ 但 Uni 的 `available` 延迟返回 `false` → 若直接据此设 `off` 会把绿盖成红，闪一下又红。代码专门 `return` 忽略。
2. **原生广播优先**（~1124 / ~1135）：Android 上 `getBluetoothAdapterState()` 有延迟，可能返回 `available=true` 但原生已报 `off`；绝不允调用延迟数据反转已确认的 `off`/`on`。

> **经验法则**：蓝牙这类"系统状态异步、多来源"的场景，状态机必须有**单一权威源 + 来源优先级 + 过渡态保护**，否则 banner 会在红/绿/无之间乱跳。本项目以"原生广播 > Uni 事件 > 主动探测"为优先级。

## 6. 知识点五：组件内的交互分支（App vs MP 双端）

`handleEnableBluetooth` 在组件内按平台分两支，正好呼应 ⑥《modal vs banner》和 MP 硬限制：

```53:95:app/BLE_Key_Go_App/components/BtStateBanner.vue
  // #ifdef APP-PLUS
  // ★ App 平台：先申请运行时权限
  if (typeof plus !== 'undefined' && plus.os.name === 'Android') {
    ...申请定位/蓝牙权限，被拒则 showModal 引导去设置...
  }
  // #endif
```

```129:135:app/BLE_Key_Go_App/components/BtStateBanner.vue
    // #ifndef APP-PLUS
    if (code === 10001 || msg.includes('not available')) {
      // 静默：btState 已经是 'off'，红色 banner 保持显示
    } else {
      toast.error('蓝牙开启失败')
    }
    // #endif
```

| 平台 | 点"开启"时 | 失败处理 |
|---|---|---|
| App-Plus Android | 先 `requestPermissions` 拿定位/蓝牙权限，再 `enableBluetooth` 弹系统窗 | 10001=用户拒/超时 → 静默（红 banner 保持）；权限拒 → Modal 引导设置 |
| 纯 MP（微信小程序） | `openBluetoothAdapter` 无法代开系统蓝牙 → 几乎必 `fail 10001` | 静默，红 banner 保持；**MP 无跳系统设置 API，"开启"按钮本质是假按钮**（见 ⑥） |

> **复盘要点**：把"平台差异交互"封进组件内部，调用方（main.vue）完全无感。这是组件化带来的第二大收益——**平台适配逻辑集中一处，不污染壳页面**。

## 7. 样式细节：`flex-shrink:0` 与 `box-sizing`

组件根做了两件事，呼应本系列 ③《死滚动 100vh 与 box-sizing》：

```140:157:app/BLE_Key_Go_App/components/BtStateBanner.vue
<style scoped>
.bt-banner-root {
  flex-shrink: 0;        /* ★ 顶部横幅不被 swiper/页面挤压，始终占满应有高度 */
}

.bt-off-banner {
  ...
  margin: 16rpx 24rpx 12rpx;
  min-height: 72rpx;
  box-sizing: border-box;  /* ★ padding 不撑大实际高度，避免破坏 min-height 布局 */
}
```

- `flex-shrink:0`：banner 在 `main-root`（flex 列布局）顶部，防止被下方内容挤压变形。
- `box-sizing:border-box`：banner 有 `padding` 又设了 `min-height`，用 border-box 保证 padding 算进高度内，不溢出（③ 的同一教训）。

> 绿 banner 还带 `@keyframes bt-on-fadein` 淡入动画（translateY + opacity），这是纯装饰、不占布局，可放心用（不影响 ③ 的滚动问题，因为动画元素不参与 flex 尺寸计算）。

## 8. 决策树（本篇 + ② 合并）

```
要不要把这段 UI 抽组件？
├─ 出现在 ≥2 页面 / 依赖同一 store / 与页面主逻辑无关 → 抽（零 props 展示+交互组件）
└─ 只在单页 → 不抽，就地 v-show/v-if

抽成组件后，在哪控制显隐？
├─ 壳层（swiper 之外）跨 tab 门控 → v-show（App 稳；MP 改用 :class+display:none，见 ②）
└─ 组件内部互斥 UI（红/绿）→ v-if（自定义组件内 v-show 失效，见 ②）

UI 在 swiper 内部吗？
├─ 是 → 绝不用 v-if（打断手势）；切 display 用 :class+CSS（见 ②）
└─ 否 → v-show / v-if 都安全，按"是否要保留状态"选
```

## 9. 经验法则速记

1. **重复 UI + 共享状态 → 抽零 props 组件**，状态上提、交互自闭环。
2. **壳层跨 tab 门控用 `v-show`**（常驻保状态）；但 MP 端记得用 `:class`+CSS（②）。
3. **自定义组件内互斥 UI用 `v-if`**（v-show 在组件里失效）；swiper 内互斥用 `:class`+CSS（②）。
4. **异步多源状态（如蓝牙）必须有优先级 + 过渡态保护**，否则 UI 乱跳。
5. **平台差异交互封进组件**，壳页面保持干净。
6. **顶部固定横幅加 `flex-shrink:0`**，带 padding+min-height 时加 `box-sizing:border-box`（③）。
