# 钥匙供电策略：固件 + APP 精确改动清单（方案 A：汽车默认 HOLD_UNTIL_LOCK）

> 日期：2026-08-14
> 前置文档：2026-08-14_钥匙供电策略_解锁后保持通电分析.md
> 目标：解锁后 PB0(KEY_POWER) 保持通电，直到 LOCK / 断连兜底锁才断电；APP 可切换「限时 / 常保持」并在限时模式设秒数。
> ★ 本文为「改动清单」，未动代码，待用户确认后实施。

---

## 一、设计决策（已定）

- **默认行为 = 方案 2（HOLD_UNTIL_LOCK）**：解锁后 PB0 保持低，直到 `g_keyState == KSTATE_LOCKED`（手动锁 / RSSI 远离锁 / 断连兜底锁）才拉高断电。
- **APP 可切换**：`KEY_POWER_MODE` = `TIMEOUT`(限时) | `HOLD_UNTIL_LOCK`(常保持)。限时模式配 `KEY_POWER_HOLD_SEC`。
- **配置属性 = 设备级参数**（与 cooldown_ms / autolock 同类），写 DataFlash，所有手机共用；连接时**不下发**，改了才 `updateConfig` 下发固件存 Flash，FF02 回显同步。★ 不走 per-phone 阈值的自动下发+本地持久化。

```c
//   KEY_POWER_MODE: 0=TIMEOUT(解锁后限时断电)  1=HOLD_UNTIL_LOCK(解锁后保持到锁车/断连)
uint8_t  g_cfgKeyPowerMode     = 1;     // 默认方案2（汽车默认常保持）
```

```c
#define KP_HOLD_MIN_SEC    5
#define KP_HOLD_MAX_SEC    300
```


### 2.3 DataFlash 持久化（KeyGo_SaveConfig / KeyGo_LoadConfig，约 L1603 / L1629）
当前 `buf[16]`，已用 buf[0..14]，buf[15] 空闲 → 用 buf[15] 存 `g_cfgKeyPowerMode`（1 字节足够）。
`g_cfgKeyPowerHoldSec` 需 2 字节，但 buf 已满（16 字节）。
**两种选择（待确认①）**：
- **A. 扩 buf 到 18 字节**：Save/Load 的 `buf[16]` → `buf[18]`，EEPROM_WRITE 长度 16→18，校验循环 12→14（注意：XOR 校验范围与 buf 扩容需同步改，且旧格式 16 字节仍可兼容读——Load 时读 18 字节，旧设备只写了 16 字节则 buf[15..17]=0，需对 mode 做合法兜底）。
- **B. 复用 buf[12] 校验字节之外**：不可行（buf[12] 是校验位）。
→ **推荐 A**：扩到 18 字节，并在 Load 对 `g_cfgKeyPowerHoldSec` 做范围兜底（越界→默认 30s），对 `g_cfgKeyPowerMode` 做 `>1 → 默认 1` 兜底。
  - Save：buf[15]=g_cfgKeyPowerMode；buf[16]=hold&0xFF；buf[17]=hold>>8；校验 XOR 覆盖 0..17（改循环上限 12→18，旧格式兼容由 Load 兜底）。
  - Load：读 18 字节；buf[15]→mode（兜底），buf[16..17]→hold（兜底）。

### 2.5 接入 KeyGo_KeyPowerCheck 调用（修复死代码，核心逻辑）
文件：`APP/keygo_core.c`
- 现状：`KeyGo_KeyPowerCheck()` 定义（约 L586）但**零调用点** → PB0 上电后永不断电。
- 改动：在状态机周期任务 `KeyGo_ProcessStateMachine`（每拍）或 `SBP_PERIODIC_EVT` 处理里调用 `KeyGo_KeyPowerCheck()`。
- `KeyGo_KeyPowerCheck` 内部按模式分支（重写该函数）：
```c
void KeyGo_KeyPowerCheck(void) {
    if (g_keyState == KSTATE_LOCKED) {
        // 已锁车 → 立即允许断电（方案2 也在此结束）
        KeyGo_KeyPower(0);
        g_powerOn = 0;
        return;
    }
    // 解锁/骑行态
    if (g_cfgKeyPowerMode == KP_MODE_TIMEOUT) {
        // 限时：到 g_powerOffAtMs 才断
        if (g_powerOn && Peripheral_GetSystemMs() >= g_powerOffAtMs) {
            KeyGo_KeyPower(0); g_powerOn = 0;
        }
    } else {
        // HOLD_UNTIL_LOCK：解锁/骑行态期间不主动断（仅 LOCK 分支断电）
        // 此处什么都不做
    }
}
```
- 新增 `KeyGo_RequestKeyPowerOff()`（供 LOCK 事件立即断电用，方案2关键）：
```c
void KeyGo_RequestKeyPowerOff(void) { KeyGo_KeyPower(0); g_powerOn = 0; }
```
  在 `KeyGo_Lock()` 三处（peripheral.c:1221、断连兜底 peripheral.c:710、骑行退出链 keygo_core.c:533）尾部调用 `KeyGo_RequestKeyPowerOff()`。
- `g_powerOffAtMs` 在 `KeyGo_EnsureKeyPower()` 上电时按 `g_cfgKeyPowerHoldSec` 重算（TIMEOUT 模式用；HOLD 模式忽略）。

## 三、APP 侧改动（BLE_Key_Go_App）

### 3.1 stores/ble.js
- state 加 `keyPowerMode: -1`（默认 -1=未同步，0=TIMEOUT，1=HOLD），`keyPowerHoldSec: -1`。
- `_parseSingleStatus` 解析 FF02 的 `kpm` / `kph` → 写入上述 state（注意 JSON 解析位置，与 `autoLockEnabled` 等同区）。
- `updateConfig` 透传 `kpm` / `kph`（若 store 已有通用透传则无需改，确认 `updateConfig` 是否直接传 object 给 `sendConfig`）。

### 3.2 utils/ble.js（sendConfig，约 L1057）
在 `parts.push` 列表加：
```js
if (config.kpm !== undefined) parts.push(`kpm=${config.kpm}`)
if (config.kph !== undefined) parts.push(`kph=${config.kph}`)
```
（key=value 格式与 cooldown_ms/autolock 一致）

### 3.3 pages/config/config.vue
- `localConfig` 加 `kpm: 1`、`kph: 30`（默认与固件一致）。
- 模板加一组 UI（建议放在「断连自动锁车延时 dlock」下方，因同为设备级参数）：
  - 模式选择器：分段控件 / switch ——「解锁后限时供电」(TIMEOUT) vs「解锁后保持到锁车」(HOLD)。
  - 限时时长的 slider/数字输入（仅 TIMEOUT 模式可编辑，HOLD 模式置灰），范围 5~300s。
- `handleSubmit` 的 `updateConfig` 对象加 `kpm: localConfig.kpm, kph: localConfig.kph`。
- `isDirty` computed 加 `|| localConfig.kpm !== bleStore.keyPowerMode || localConfig.kph !== bleStore.keyPowerHoldSec`。
- `watch(bleStore.keyPowerMode...)` / `watch(bleStore.keyPowerHoldSec...)` 回填 localConfig。
- `applyConfig`/同步初始化处把 `kpm`/`kph` 从 store 回填（与 dlock 同处理）。

### 3.4 连接后同步（不需主动下发）
与 cooldown/autolock 一致：连接后 APP 不主动下发 kpm/kph，仅从 FF02 回显显示当前值；用户改了才 `updateConfig` 下发。
