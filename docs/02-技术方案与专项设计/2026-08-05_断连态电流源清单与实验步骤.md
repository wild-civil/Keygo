# 断连态电流源清单 + 实验步骤（基于实测 250µA→210µA 复盘）

> 日期：2026-08-05
> 目标板：淘宝 YD-CH582M 开发板（ME6215 LDO，已拆 1k 限流 LED）
> 固件分支：`dev/pcb-v1`
> 实测基线：断连态最低 ~250µA（广播 120ms）→ 改广播 30s 后 ~210µA

---

## 0. 结论速览（先说结果）

**广播间隔不是断连态主战场。** 把断连态广播从 120ms 改成 30s，电流只从 250µA 降到 210µA（仅省 ~40µA）。
这推翻了"广播主导"的假设。210µA 的真实底色是：

- ME6215 LDO（<10µA，可忽略）
- CH582M **sleep 模式基线**（保 RAM30K + 32K 常跑 + DCDC 开，~几十 µA，硬地板）
- 断连态仍在跑的两个周期性唤醒源（见第 1 节）
- （若从 USB 口量整板）开发板 USB-UART 等常驻外围漏电

> 历史参照：同一块板拆 LED 后纯睡眠曾到 47µA。说明板子本身能到 47µA，210µA 与 47µA 之间 ~160µA 的差额，来自"断连态仍跑的任务 + 测量是否含板级外围"，而非 LDO/广播。

## 1. 断连态电流源清单（代码实证）

| # | 唤醒源 | 周期 | 代码位置 | 断连态是否运行 | 做了什么 | 电流性质 |
|---|--------|------|----------|----------------|----------|----------|
| 1 | **广播** | 30s（已改） | `peripheral.c` L518-548 `SBP_ADV_SLOWDOWN_EVT` / `SBP_ADV_ULTRA_SLOW_EVT`；间隔宏 `ADV_CONST_NORMAL_TICKS`（peripheral.h） | 是（断连走快窗→实际恒 `ADV_CONST_NORMAL_TICKS`） | 发一包广播 | 30s 时 ~2µA 平均（120ms 时 ~88µA） |

## 2. 测量点修正（最关键、零成本）

**先确认你量电流的方式，否则所有数字不可比。**

- ❌ 从 **USB 口量整板**：USB-UART（CH340 类）、LDO、LED（已拆）、上拉全计入，会虚高。
- ✅ **只量 CH582M 供电域**：把表串在 LDO 输出（VDD3V3）→ CH582M VDD 引脚之间（飞线/割线），剥离板级外围。

**为什么重要**：你之前"拆 LED 后 47µA"很可能是接近纯 MCU 域的数值；现在 210µA 若是从 USB 口量的整板值，USB-UART 等可能占了大头。测量点统一后，才能真正确认 MCU 域离 100µA 还有多远。

## 3. 三个验证实验（逐个隔离电流源）

### 实验 A：停掉断连态电池检测

**目的**：确认电池 ADC 采样是否吃掉电流。

**改哪里**：`peripheral.c` L553-567 的 `SBP_BATTERY_CHECK_EVT` 处理块。
当前（断连态仍在跑）：

```c
553:    if (events & SBP_BATTERY_CHECK_EVT) {
554:        tmos_start_task(Peripheral_TaskID, SBP_BATTERY_CHECK_EVT, SBP_BATTERY_CHECK_PERIOD);
555:        {
556:            uint8_t oldLevel = Battery_GetLevel();
557:            Battery_UpdateLevel();
...
566:        return (events ^ SBP_BATTERY_CHECK_EVT);
567:    }
```

**临时改法**（断连态不重排电池检测任务，即断开后不再 30s 采样）：

```c
    if (events & SBP_BATTERY_CHECK_EVT) {
        if (g_deviceConnected) {                       // ← 加门控：仅连接态才重排
            tmos_start_task(Peripheral_TaskID, SBP_BATTERY_CHECK_EVT, SBP_BATTERY_CHECK_PERIOD);
            uint8_t oldLevel = Battery_GetLevel();
            Battery_UpdateLevel();
            ...
        }
        return (events ^ SBP_BATTERY_CHECK_EVT);
    }
```

**预期**：若电流从 210µA 掉到 ~180µA，说明电池 ADC 上电是元凶之一。

> 注意：这只是验证实验。长期方案应是"电池检测在断连态大幅拉长周期（如 5~10min 一次）"，而非完全停掉——否则 App 看不到电量变化。

---

### 实验 B：关闭 BLE 校准

**目的**：确认 RF/LSI 校准（每 2min 强制唤醒）是否吃掉电流。

**改哪里**：`HAL/include/config.h` L134-136

```c
134:#ifndef BLE_CALIBRATION_ENABLE
135:#define BLE_CALIBRATION_ENABLE              TRUE
136:#endif
```

**临时改法**：把 `TRUE` 改为 `FALSE`。

```c
#define BLE_CALIBRATION_ENABLE              FALSE
```

**预期**：若电流进一步下降，说明校准唤醒是元凶之一。

> 风险提示：关闭校准可能让长时运行后 RF 频偏变大（影响连接距离/稳定性）。**仅作断连态功耗验证用，验证完建议恢复 TRUE**，或改为"连接态才校准"。

---

### 实验 C：确认是否真进 sleep（而非卡 active）

**目的**：排除"断连态根本没睡、一直在 active"的可能（历史曾实测 3.9~5.4mA active）。

**验证法（不改代码）**：用电流探头/高精度表看断连态瞬时波形：
- 若电流稳定在某值、只有稀疏尖峰（30s/2min）→ 已进 sleep，正常。
- 若电流持续在 mA 级或频繁尖峰 → 有隐藏唤醒源（如某定时器未停、UART 打印死循环）。

**相关代码**：`SLEEP.c` L57-71 的 `LowPower_Sleep` 调用；`HAL_SLEEP` 宏在 `config.h`（fix12 已开 `TRUE`）。

---

## 4. 实验顺序建议

1. **先做第 2 节测量点修正**（零成本，决定数字可信度）。
2. **实验 A**（停断连态电池检测）→ 看掉多少。
3. **实验 B**（关校准）→ 看再掉多少。
4. **实验 C**（看波形确认 sleep）→ 排除卡 active。
5. 综合：把省下的部分用"拉长周期/条件化"方式保留功能，得出最终断连态最低电流。

---

## 5. 关于破百 µA 的现实判断

- 单靠广播（实验前已证）：只省 ~40µA，**到不了百 µA**。
- ME6215 LDO：已 <10µA，**不是瓶颈，无需换**（自焊板 XC6206 山寨货才是另一回事）。
- 真正要把开发板断连态压到 100µA 以下，路径是：
  1. 测量点改纯 MCU 域（剥离 USB-UART 等板级漏电）；
  2. 断连态电池检测拉长到 5~10min（而非 30s）；
  3. 校准改为仅连接态或大幅拉长；
  4. 确认 sleep 模式基线（~几十 µA 是地板，无法再降除非改 shutdown，但 shutdown 会丢失 GPIO 状态——见 PM 铁律）。

> 若测纯 MCU 域后仍在 150µA+，则 sleep 基线 + 板级残留才是主因，需进一步查具体外围。
