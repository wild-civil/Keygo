# 绑定验证"慢" + RSSISET 10007 无效重试 优化分析（2026-08-12）

> 背景：用户实测连接后「绑定验证有时候比较慢」，抓到一段关键日志（见下），发现 AUTH 挑战应答本身极快（19ms 写完），但固件回 `AUTH:OK` 有 ~1.2s 延迟，且 `RSSISET` 写 FF03 连续 3 次 10007（瞬时窗口）浪费 ~830ms。本文给出根因 + 可落地优化方案 + 连接参数提前的坑回顾。
> **实施状态（2026-08-12 傍晚更新 → 当晚修订）**：方案 A 演进为「合并版」落地，但**首轮实测发现 FF02 作为唯一就绪信号不可靠**——重连场景下 FF02(notify/只读属性)可能在 OS 对 FF01/FF03(write 属性)缓存就绪前就到达，导致 AUTH:OK 后 FF01 仍爆 10007×3。已修订为「**FF02 首帧 OR 500ms 固定延时，任一先到即下发**」：FF02 作加速信号（首次连接提前发），500ms 作保底（重连不裸撞窗口）。见第五节。

## 一、实测日志时间线拆解

```
22:32:31.752  App 收到固件 NONCE（挑战值下发）
22:32:31.771  App 写 AUTH 回包（成功，耗时 19ms）              ← 算法极快
22:32:32.958  App 收到 AUTH:OK（固件确认鉴权通过）              ← 这一段隔了 1.187s
22:32:33.004  自动会话鉴权成功（重连恢复）
22:32:33.005  配置已下发 unlock=-50 lock=-65 ...（FF03 写成功）
22:32:33.005  RSSISET:-50:-65 写 FF03 → 10007（1/2 重试）
22:32:33.410  RSSISET 写 FF03 → 10007（2/2 重试）
22:32:33.832  RSSISET 写 FF03 → 10007（连接后宽限期内，吞掉不弹窗，累计 7）
```

### 耗时构成

| 区间 | 耗时 | 性质 |
|---|---|---|
| NONCE 收到 → AUTH 写完 | 19ms | App 侧极快（HMAC-SHA256 客户端算） |
| AUTH 写完 → AUTH:OK 回包 | **1.187s** | 固件回包受**连接事件窗口**限制（主因） |
| AUTH:OK → 配置下发成功 | ~50ms | 正常 |
| RSSISET 3 连 10007 重试 | **~830ms** | 加密握手后 GATT 缓存未刷新（视觉拖沓，被宽限期吞掉） |

**结论**：绑定验证"慢"不是算法慢，是 **① AUTH:OK 回包受 BLE 连接事件空窗波动（200ms~1.5s）** + **② RSSISET 在加密握手瞬时窗口内盲写导致无效重试** 叠加。

## 二、根因 1：AUTH:OK 回包延迟（连接参数空窗）

- 固件收到 AUTH 后做 SHA256 校验 + 比对（CH582M 60MHz，微秒级，非瓶颈）。
- 但 `AUTH:OK` 是 **GATT Notify**，必须等下一个**连接事件窗口**才能发出。
- 当前 `LATENCY=2`（peripheral.h:151）→ 每轮 GATT 最慢 `(2+1)×~240ms ≈ 720ms`；手机裁决间隔可能更宽。
- 1.187s ≈ 撞上 1~2 轮连接事件空窗。**这是"有时候慢"的核心波动源**。

> 注：此延迟已在 fix28(P15) 把 LATENCY 从 4→1~2 时大幅压缩（旧 LATENCY=4 最慢 1.8s，曾致 AUTH 30s 超时断开）。当前 LATENCY=2 已安全，但仍有百毫秒~1s 级波动。

## 三、根因 2：RSSISET 10007 无效重试（可消除）

### 代码现状

`stores/ble.js:4340` `_pushRssiThresholds`：
```js
_pushRssiThresholds() {
  if (this.fwSec < 2 || !this.deviceId || !this.connected) return
  const u = this.unlockThreshold, l = this.lockThreshold
  // 去重：阈值未变则跳过（已存在）
  if (this._lastPushedUnlock === u && this._lastPushedLock === l) {
    console.log('[Store] RSSISET 跳过(阈值未变): ' + u + ':' + l)
    return
  }
  const cmd = 'RSSISET:' + u + ':' + l
  enqueueWrite(() => rawSendCommand(this.deviceId, cmd))
    .then(() => { this._lastPushedUnlock = u; this._lastPushedLock = l })
    .catch(() => {})
}
```

`utils/ble.js:902` 10007 重试：
```js
if (_isPropertyNotSupport(err) && tryNo < _WRITE_10007_RETRIES) {  // _WRITE_10007_RETRIES=2
  setTimeout(() => _attempt(tryNo + 1), _WRITE_10007_RETRY_DELAY)  // 400ms
  return
}
```

### 为什么必爆 10007

- `AUTH:OK` 即加密握手**刚完成**，此时 OS 对 FF03 的 WRITE 属性缓存可能还没刷新（`10007 = property not support` 是 **OS 本地拒绝**，未真正发往固件）。
- `extendConnectGrace()`（utils/ble.js:47）在 AUTH:OK 时把宽限期 `+= 4000ms`（_CONNECT_GUIDE_GRACE），**刻意吞掉这段时间内的 10007 不弹窗**（防误判"蓝牙缓存过期"）。
- 于是：RSSISET 在 AUTH:OK 后紧跟着写 → 3 连 10007（首写 + 2 重试，间隔 400ms ≈ 830ms）**全落在宽限期内** → 被静默吞掉、不弹窗，但：
  1. 浪费 3 次 GATT 写 + ~830ms 时间（日志里"累计 7"说明每次连接都发生）。
  2. 去重逻辑（`_lastPushedUnlock` 相同则跳过）**只在"上次已成功推过且阈值没变"时生效**；首次/阈值变化那次必走真实写 → 必爆。
  3. 即便去重跳过了，日志显示这次**没跳过**——说明该连接阈值与 `_lastPushed*` 不同（或重连路径 `_lastPushed*` 已被某处清零），仍触发了真实写。

### 优化方案：「延后 + 去重增强」RSSISET 写

**方案 A（推荐，低风险）：AUTH:OK 后延后推 RSSISET**
- 在 `_pushRssiThresholds` 内，若距 `AUTH:OK` 不足一个安全窗口（如 600~800ms），用 `setTimeout` 延后写，避开加密握手瞬时窗口。
- 实现：
  ```js
  _pushRssiThresholds() {
    if (this.fwSec < 2 || !this.deviceId || !this.connected) return
    const u = this.unlockThreshold, l = this.lockThreshold
    if (this._lastPushedUnlock === u && this._lastPushedLock === l) return  // 去重保留
    // ★ 延后：加密握手刚完成，FF03 写属性缓存可能未就绪，避免 10007 无效重试
    const delay = Math.max(0, (this._authOkAt || 0) + 800 - Date.now())
    setTimeout(() => {
      if (!this.connected || this.deviceId == null) return
      if (this._lastPushedUnlock === u && this._lastPushedLock === l) return
      const cmd = 'RSSISET:' + u + ':' + l
      enqueueWrite(() => rawSendCommand(this.deviceId, cmd))
        .then(() => { this._lastPushedUnlock = u; this._lastPushedLock = l })
        .catch(() => {})
    }, delay)
  }
  ```
- 在 AUTH:OK 处理处（stores/ble.js:4013）记录 `this._authOkAt = Date.now()`。
- **收益**：首次/阈值变化那次也避开瞬时窗口，10007 连爆从「必现」变「基本消失」，省 ~830ms 静默浪费 + 消除日志噪声。
- **风险**：极低。RSSISET 是 best-effort（固件回 FAIL:NO_AUTH/OK 无害，下次 AUTH:OK 再推），延后 800ms 不影响解锁/上锁（阈值跟随本就是软优化）。

**方案 B（可选，配合 A）：降低 10007 重试退避噪声**
- 当前 `_WRITE_10007_RETRIES=2` + 400ms 退避是为"真瞬时窗口"兜底。若已用方案 A 延后，可保留不变（真碰上仍自愈）；也可把 RSSISET 这类 best-effort 写标记为 `bestEffort:true`，10007 时**不重试、不计入弹窗计数**，进一步降噪。
- 注意：绝不能把"真 10007"（写错通道/缓存真坏）也吞掉——只有 best-effort 类（RSSISET/状态同步）可标记跳过重试。

**方案 C（不推荐）：调大 `_CONNECT_GUIDE_GRACE`**
- 治标不治本——只是把"吞掉"的时间拉长，10007 重试仍在后台发生，浪费依旧。

## 四、连接参数提前：`SBP_PARAM_UPDATE_DELAY` 4s → 1.5s（回顾 fix23 坑）

### 用户提议
`SBP_PARAM_UPDATE_DELAY=6400`（~4s，peripheral.h:65）提前到 ~1.5s，让 AUTH 通知更早出来。

### fix23 到底踩了什么坑（memory + 文档确认）
- **fix23 坑的本质是「MIN 间隔太小被手机拒」**，不是「触发时机太早」。
- 当时把 `DEFAULT_DESIRED_MIN_CONN_INTERVAL` 设到 **250ms**（≈0.625×400 ticks）的激进短间隔 → 部分手机（尤其后台/Doze）**直接拒绝参数更新**（Android 对过短 MIN 有下限保护）→ 参数更新失败 → 连接保持在手机默认长间隔 → 反而更慢。
- 后续 fix24+ 把 MIN 收回 **128(160ms)**（peripheral.h:147），这是手机普遍接受的保守下限，更新成功率恢复。

### 提前 `SBP_PARAM_UPDATE_DELAY` 会不会再踩坑？
- **不会踩 fix23 那个坑**：被拒只跟 `MIN` 绝对值（128）有关，跟「连上后多久发起」无关。当前 MIN=128 已是安全值，提前发起不会被拒。
- **但有一个边际风险**：连上后 <1s 立即发起参数更新，可能撞上手机**连接初期协商不稳定窗口**（部分国产 ROM 在连接建立后 1~2s 内暂不接受参数更新，或更新后被系统拉回）。过早发起可能：
  1. 更新请求被静默丢弃（无损，因为 `SBP_PARAM_UPDATE_PERIOD=48000` 每 30s 会再试，fix23 已加周期重试兜底）。
  2. 或手机在握手最忙时被迫协商，短暂拖慢 AUTH（概率低）。
- **建议值**：从 6400(4s) → **2400~3200(1.5~2s)** 折中。既明显早于现在的 4s（让 AUTH 通知更早出来 ~2s），又避开 <1s 的连接初期不稳定窗口。

### 提前对 AUTH 延迟的实际收益
- AUTH 通知延迟主因是 `LATENCY=2` 的连接事件空窗（720ms 级），**参数更新把间隔从手机默认（可能 360ms+）降到 160~320ms**，能压缩空窗。
- 但参数更新本身有 ~1s 协商延迟，且手机可能不立即应用。综合看：提前到 1.5~2s 对 AUTH 通知延迟有 **数百 ms 级改善**，但**不如方案 A（消除 RSSISET 830ms 浪费）收益确定**。
- **优先级**：先上方案 A（App 侧、零风险、收益确定），连接参数提前作为固件侧次要优化，需真机验证（不同手机表现差异大）。

## 五、结论与建议实施顺序

| 优先级 | 改动 | 位置 | 收益 | 风险 |
|---|---|---|---|---|
| 1 | RSSISET 延后 800ms 写（方案 A） | `stores/ble.js` `_pushRssiThresholds` + AUTH:OK 记 `_authOkAt` | 消除 ~830ms 无效重试 + 日志噪声 | 极低（best-effort 写，延后无害） |
| 2 | `SBP_PARAM_UPDATE_DELAY` 4s→1.5~2s | `peripheral.h:65` | AUTH 通知早 ~数百 ms | 低（MIN=128 已安全；周期重试兜底） |
| 3 | best-effort 写标记跳过 10007 重试（方案 B，可选） | `utils/ble.js` | 进一步降噪 | 低（需区分真/假 10007） |

**断连 3s 窗口（_startDisconnectProbation）保持 3000ms 不变**：改 2s 对连接/验证速度无帮助，且 2s 已接近 FF02 1s 推送周期的安全下限，收益极小，不建议动。

## 五、已实施：合并版（FF02 加速 + 500ms 保底，2026-08-12 落地 → 当晚修订）

> 原方案 A（固定延后 800ms）仍在部分 ROM 上 10007（握手窗口 >800ms），且 FF01 配置下发**完全没护**也会撞窗。改为「挂起 + 信号/延时触发」：AUTH:OK 后挂起写，**FF02 首帧 OR 500ms 固定延时任一先到即下发**——FF02 作加速信号，500ms 作保底。

### 设计

- **挂起写队列**：AUTH:OK 时不再直接调 `_syncConfigToDevice()` / `_pushRssiThresholds()`，改为 `_armPostAuthWrites()`：置 `_gattWriteReady=false` + `_postAuthWritesPending=true` + 启 **500ms** 定时器（保底）。
- **FF02 首帧 = 加速信号（非唯一信号）**：`_parseSingleStatus` 收到 FF02 且 `sessionAuthed && _postAuthWritesPending && !_gattWriteReady` → 立即 `_flushPostAuthWrites()`（首次连接通常晚于握手，可提前发）。
- **500ms 保底**：定时器到点强制 `_flushPostAuthWrites()`（重连场景 FF02 可能早于写缓存就绪而早到，500ms 保底确保不裸撞窗口）。
- **触发下发**：`_flushPostAuthWrites()` 清定时器、置 `_gattWriteReady=true`、校验连接态后下发 FF01 配置 + FF03 RSSI 阈值。
- **清理点**：新连接三处（`_configPushedThisConn=false` 旁）+ `_handleDisconnect` 入口，均重置标志并清 `_postAuthWriteTimer`，避免掉线后向旧连接发写。

### ★ 当晚修订：为什么 FF02 不能当唯一信号（关键教训）

首轮实测合并版在**重连恢复**场景仍爆 10007×3：
```
23:07:14.815 AUTH:OK → 挂起
23:07:15.085 首帧 FF02 到达，触发挂起写
23:07:15.133 写入失败(10007) FF01 unlock=-46...   ← 还是爆了
```
**根因**：FF02 是 **notify（设备→手机，只读属性）**，FF01/FF03 是 **write（手机→设备，写属性）**。Android 对这两类特征的属性缓存是**分别刷新**的——FF02 能收 ≠ FF01 能写。首次连接时 FF02 晚于握手（缓存已热，碰巧都对）；但重连时固件可能很快恢复 FF02 推送（上一轮订阅未完全失效），FF02 早到时写缓存还没就绪 → 裸撞 10007。**结论：notify 属性可用不能证明 write 属性可用，FF02 只能当加速，不能当就绪判据。**

### 同时护住了 FF01 配置下发（原方案 A 没护的盲区）

原日志里 `22:48:41.141 FF01 "unlock=-50..." 10007` 才是视觉上「配置下发慢」的主因。合并版把 FF01 与 FF03 一起挂起，两者都在信号/保底触发后发。

### 去重说明（修正旧措辞）

`_pushRssiThresholds` 的去重变量 `_lastPushedUnlock/_lastPushedLock` 是 **App 运行时 RAM 标记**（重连保留、App 冷启才清空），**不是设备 Flash**。设备 Flash 存的是 `g_cfg` 里的阈值数值（断电重启仍在），但 App 侧「这次要不要再写」只看 RAM 标记。

### 实施效果预期

- 首次连接：AUTH:OK → 收首帧 FF02（晚于握手）→ 提前发 FF01/FF03，一次成功、无 10007（快）。
- 重连恢复：AUTH:OK → 500ms 保底到点发（FF02 早到也不裸撞，因有 500ms 兜底延时）→ 仍可能偶发 10007，但由 utils/ble.js 既有 400ms×2 重试自愈，功能无损。
- 验证关注日志：`[Store] AUTH:OK 后写已挂起（FF02 首帧 OR 500ms 保底任一触发）` → 要么 `首帧 FF02 到达(加速触发)` 要么 `500ms 延时保底` → 之后 RSSISET/FF01 的 `写入失败(10007)` 应显著减少（首次连接基本为零，重连偶发但自愈）。

### 附：RSSISET:OK 噪声修复

固件有时把命令回执 `RSSISET:OK` 经 FF02 Notify 透传，被 `_parseSingleStatus` 当状态包解析失败刷噪声。已在解析入口按 `RSSISET:` 前缀直接忽略。

### 附二：NONCE 首写热身延时（2026-08-12 当晚第二刀，进一步加速）

合并版护住了 `AUTH:OK` 之后的写（FF01/FF03），但**自动 AUTH 的 `NONCE` 首写**在 `AUTH:OK` 之前、走 `utils/ble.js` 重试逻辑，不受合并版保护。实测 `NONCE` 是连接后最早的写（FF03 write 属性），连爆 10007×3 + 400ms×2 退避 → 拖 ~2.3s，是"绑定验证慢"的另一主因。

**改动**：`_enableStatusNotify()` 订阅 FF02 成功后，不再**立即** `_maybeAutoAuth()`（→ `ensureSession()` 发 `NONCE`），而是加 **300ms 热身延时**再触发。让 OS 对 FF03 的 WRITE 属性 GATT 缓存刷新好，NONCE 一次成功，握手快 ~2s。两条触发路径（`readSerialNumber` 回调补订阅 / 800ms 订阅定时）都经此 300ms 闸门，`B._autoAuthRunning` 互斥锁保证只发一次 NONCE，不会重复。

**预期效果**：
- 首次连接 / 重连：`NONCE` 一次成（不再 10007×3），AUTH 握手整体快 ~2s。
- 残留慢点：`AUTH:OK` 回包 ~1.2s 是固件 LATENCY 连接事件空窗（App 改不了，需固件 `SBP_PARAM_UPDATE_DELAY` 提前，待用户确认）。
- 验证关注日志：订阅成功后应有 ~300ms 间隔再到 `自动会话鉴权成功`，且 `NONCE` 写不应再连续 `写入失败(10007)`。

### 附三：FF03(RSSISET) 必须与 FF01 错开发（2026-08-12 当晚第三刀）

实测第二刀后 NONCE 握手飞快（17.294→18.493 约 1.2s），但收尾仍慢：FF02 首帧触发同一时刻**同时发 FF01+FF03**，FF01 一次成（18.822）而 FF03(RSSISET:-50:-65) 紧接（18.833，间隔~11ms）**连爆 10007×3 直到宽限期吞掉**（19.651，意味着 RSSISET 可能最终未下发成功）。

**根因（最终拼图）**：FF01 与 FF03 是**两条不同 write 特征**，Android 对它们的 WRITE 属性 GATT 缓存**分别刷新、不同步**。FF02 首帧到达时 FF01 缓存已热、FF03 还差半拍 → 两者黏在一起发，FF03 必撞窗。

**改动**：`_flushPostAuthWrites()` 里 FF01(`_syncConfigToDevice`) **立即发**，FF03(`_pushRssiThresholds`) **延后 300ms 发**，给 FF03 写缓存独立热身窗口。与 NONCE 热身同理。

**预期**：FF03 一次成、不进宽限期、阈值确写到设备；AUTH 收尾不再被 10007×3 重试拖 ~1.3s。

### 附四：固定延时不可靠 → 改为事件驱动串行（2026-08-12 深夜第四刀，关键纠偏）

第三刀（FF03 延后 300ms）首测完美（FF03 一次成），但**第二次重连立刻破功**：FF01 自己撞 10007 重试到 ~400ms 才成，FF03 的 300ms 定时反而比 FF01 成功更早发 → 仍连爆 10007×3 进宽限期被吞。

**根因（彻底认清）**：固定延时是拍脑袋凑数，永远跟不上 ROM/系统 GATT 缓存热身速度的差异。同一台手机两次重连，热身快慢都能差一倍（FF01 一次成 vs FF01 也撞窗）。FF01 与 FF03 是两条不同 write 特征，缓存分别刷新、不同步，且**连 FF01 自身在某些重连下都未热**。

**最终正解 = 事件驱动串行（不依赖任何固定延时估算窗口）**：
1. `_flushPostAuthWrites()` 改为 `async` + **`await this._syncConfigToDevice()`**（等 FF01 真正写入落地，成功/失败都算完成）→ 再 `setTimeout 250` 发 FF03。FF03 永远在 FF01 真实写完后发，与系统热身速度无关。
2. `_requestNonce()` 发 NONCE 前加 **固定 300ms 热身**（无死角兜底）。第二刀在 `_enableStatusNotify` 订阅后加的 300ms 未能覆盖「`_statusNotifyReady` 已 true 时直接 ensureSession」那条路径（实测 NONCE 在订阅成功同毫秒发出），故把热身下沉到 `_requestNonce`——所有路径发 NONCE 都必经此处，必过 300ms。

**预期**：无论系统热身多慢，NONCE/FF01/FF03 三条写都各自在"前一条真正落地 + 小缓冲"后发，10007 应基本归零；唯一硬慢点是固件 AUTH:OK 回包 ~1.2s（LATENCY 空窗，App 改不了，需固件 `SBP_PARAM_UPDATE_DELAY` 提前，待用户确认）。

### 附五：500ms 保底延长到 1000ms（2026-08-13 第五刀，解决第二次重连仍慢）

第四刀后首次重连极快（首帧 FF02 加速触发，FF01 一次成、FF03 在 FF01 后 252ms 一次成），但**第二次重连又慢**：走的是「500ms 延时保底」路径（首帧 FF02 加速未触发），且保底触发时 **FF01 自己撞 10007×1**（48.255→48.680 重试后才成）、FF03 紧接连爆 10007×3（48.981→49.797 第三次才成）。

**根因拼图**：
1. 首帧加速闸门（3541）要求 `sessionAuthed && _postAuthWritesPending && !_gattWriteReady`。第二次 `sessionAuthed` 在 AUTH:OK 后 ~124ms 才 true（47.712→47.836），而 FF02 首帧在 47.774~47.836 窗口内若到则闸门未过（`sessionAuthed` 还 false）；之后 FF02 在 48.255 保底前又有 ~480ms 空窗没新包 → 首帧加速未触发，fallback 到 500ms 保底。
2. 500ms 对慢系统（重连 OS 重建 GATT 缓存慢）不够——保底触发时 FF01 写缓存仍没热，撞窗。第一次首帧加速能在 AUTH:OK 后 ~50ms 触发且 FF01 一次成，是因为 **FF02 实时流驱动系统把写缓存完全刷新**（FF02 是写缓存最强热身信号）。

**改动**：`_armPostAuthWrites` 的保底延时 **500ms → 1000ms**。慢系统有更充分热身，FF01 撞窗概率大降；首帧加速路径（快系统/第一次）完全不受影响。

**预期**：第二次重连类慢路径 FF01 撞窗减少，整链收尾不再被 10007×3 拖 ~1.5s；快路径仍极快。若仍有零星 10007，由 `utils/ble.js` 400ms×2 重试自愈，功能无损（阈值最终仍写入，不进宽限期被吞）。

### 附六：AUTH:OK 包自身即 FF02 实时包 → 120ms 短延时 flush（2026-08-13 第六刀，决定性，让每次都像第一次）

第五刀后首次仍极快、第二次仍慢。深挖时序发现**决定性根因**：
- AUTH:OK 的 FF02 包在 47.712 到达 → `_parseSingleStatus` 先置 `sessionAuthed=true` → 3536 行刷新时间戳 → 3540 闸门判 `sessionAuthed && _postAuthWritesPending && !_gattWriteReady`。但此时（`_armPostAuthWrites` 在 4074 行、即解析分支**之后**才调）`_postAuthWritesPending` **还是 false** → AUTH:OK 这包**错过自我触发加速**。
- 之后要等「下一包 FF02」才触发 3541 加速。但第二次 AUTH:OK 后 ~480ms 内无新 FF02 包（周期事件 1s + 时序错开）→ fallback 1000ms 保底，慢。第一次 AUTH:OK 后 ~50ms 有下一包 FF02 → 触发加速，快。

**决定性修复（纯 App，无需固件）**：既然 AUTH:OK 包**本身就是 FF02 实时 notify**（已证明 FF02 通道通），在 `_armPostAuthWrites` 设 pending 后**直接启 120ms 短延时 flush**，不等不确定的「下一包 FF02」。120ms 既留热身窗口（避 10007）又比 480ms+ 空窗快得多，**每次 AUTH:OK 都确定走此路径**，与第一次一样快。保留 3541 首帧加速（快系统更早）+ 1000ms 保底（双保险）。

**预期**：每次断连重连都 ~120ms 后发 FF01（借 AUTH:OK 的 FF02 流热身）→ 一次成；FF03 在 FF01 落地 +250ms 后发 → 一次成。整体收敛到第一次的极快体验，不再有"时快时慢"两极分化。唯一固定慢点是固件 AUTH:OK 回包 ~1.2s（LATENCY 空窗，App 改不了）。

## ★★ 附七：真正的根因 —— 10007 不是"缓存没热"，而是 GATT 事务并发（2026-08-13 第七刀，前六刀前提全错）

### 决定性证据

第六刀后第二次重连**仍然慢**，且用户反馈"连接也变慢了"。这次日志出现了前几次没注意的一组关键行：

```
04.548  电池读失败 1/3   readBLECharacteristicValue:fail property not support
05.014  120ms 短延时 flush
05.030  FF01 写失败 10007          ← 与电池读窗口重叠
05.376  电池读失败 2/3
05.441  FF01 写失败 10007          ← 又重叠
05.456  电池读成功 (255)            ← 电池链路放开
05.898  FF01 写成功                ← 电池读结束后第一次写立刻成功！
06.163  FF03 写失败 10007
06.196  电池读失败 3/3             ← 又重叠
07.012  FF03 写成功
```

**`10007 property not support` 不只发生在 write，也发生在 read。且每一次写 10007 都精确落在一次电池 GATT read 的飞行窗口内；电池读一结束，下一次写立刻成功。**

### 根因

Android `BluetoothGatt` **同一时刻只允许一个未完成的 GATT 事务**——`read` / `write` / `descriptor` 三者**共用同一个事务槽**。若前一操作仍在飞行中，后一个 `writeCharacteristic()` / `readCharacteristic()` 会被框架直接拒绝（返回 `false`），而 uni-app / 微信 BLE 适配层把这种"提交被拒"**统一映射成 `errCode 10007 property not support`**。

这个错误码名字极具误导性：**它压根不是在说"该特征没有 WRITE/READ 属性"，而是"通道忙，没排上队"。**

### 前六刀为何全是治标

第一~六刀（NONCE 提前 300ms、FF02 首帧加速、500ms→1000ms 保底、AUTH:OK 后 120ms 短延时、FF03 等 FF01 落地 +250ms…）全部建立在 **「10007 = OS 属性缓存没刷新，等一会儿就热了」** 这个**错误前提**上。它们能"看似生效"，只是碰巧把某条写**错开了**电池 read / 序列号 read 的飞行窗口而已 —— 所以表现为**「时快时慢」纯看随机时序**：

- **第一次极快**：电池兜底读取在 `56.692` 才发生，**在配置下发之后**，天然无冲突。
- **第二次慢**：电池读的 `2500ms` 起始延时 + `800ms×3` 退避窗口，正好完整覆盖 `04.5~06.2` 的配置下发窗口。
- **"连接也变慢了"**：`04.548` 那次电池读恰好卡在 AUTH 往返中间，同样占用事务槽，把 AUTH:OK 回包又推迟了一个连接事件。**两个现象同一个根因。**

### 修复（治本）

**① `command-queue.js`：写队列升级为 GATT 事务队列**
- `_writeChain` → `_gattChain`，新增 `enqueueRead()`，与 `enqueueWrite()` **共用同一条链**。
- 理由：Android 事务槽是读写共享的，**只串行化写而放任读并发，等于没串行**。

**② 所有裸 read 纳入队列**
- `stores/ble.js` `_fetchBatteryLevel`：`readBatteryLevel` → `enqueueRead(() => readBatteryLevel(...))`。此前**完全绕过队列**直接调 `uni.readBLECharacteristicValue`，是本次并发的主凶。
- `utils/ble.js` `readSerialNumber`：FF04 读取同样纳入队列，避免与 NONCE(FF03 写) 抢槽。

**③ 电池兜底读取让位给配置下发主链（治时序）**
- 新增 store 字段 `_postAuthWritesInFlight`。原 `_postAuthWritesPending` 在 flush **一开始**就置 false，而 FF03 还要等「FF01 落地 +250ms」才发，**不足以表达"整条链收尾"**。
- `_fetchBatteryLevel` 等 `(_postAuthWritesPending || _postAuthWritesInFlight)` 全部落幕（上限 4s 防饿死）后才读，保证「绑定验证 → 配置下发」这条**用户可感知的主链**永远优先拿到事务槽。
- 配套把 `_pushRssiThresholds` / `_doPushRssi` 从 fire-and-forget 改为**返回 Promise**，否则 `await` 立即返回、in-flight 在 FF03 落地前被清掉 → 10007 重现。
- 四处新连接复位点 + 断连复位点均补 `_postAuthWritesInFlight = false`，防标志泄漏把电池读永久卡住。

**④ 移除 NONCE 前置 300ms 延时（第三刀遗留，纯浪费）**
- 该延时基于错误前提，当时"看似有效"只是碰巧错开了序列号 read 窗口。读写已串行化后它毫无作用 → **每次连接省 300ms**。

### 预期

10007 从**源头消失**（不再靠 400ms×2 重试碰运气自愈），配置下发不再被电池读挤占，连接握手也不再被读操作推迟连接事件。**"时快时慢"两极分化根除**。

保留的 `120ms` 短延时与 FF03 的 `250ms` 延时暂不归零 —— 串行队列是新机制，留少量余量比激进归零稳妥，后续实测稳定可再砍。

## ★★ 附八：真正的「时快时慢」瓶颈不在 GATT，而在重连路径本身（2026-08-13 第八刀）

第七刀提交后实测**仍「第一次快、后面慢」**，但这次日志暴露了关键转折：10007 全部发生在 **NONCE(FF03) 写**上，且时间点 `57.116`/`09.488`/`09.892` **远在电池 read 之前**（电池读在 `24:00`/`24:11` 才发生）。→ 第七刀假设的「电池读抢槽」在这条路径上不成立，根因另有所在。

### 决定性证据：慢在重连初始化，不在 GATT 重试

用户确认每次都是「**用户手动断开 → 真断连 → 点重新连接**」。日志时间轴：

```
24:00.546  断连（手动）
24:03.211  全局监听器已初始化（App 回前台 onShow→prepareForAutoConnect）
24:03.227  ★★★ 进入 Android 权限申请 ★★★   ← 每次重跑 6 权限申请（固定 ~3s 前置）
24:04.365  全局监听器已销毁 + 又初始化（connect 内冗余重建）
24:04.397  connect: 已预清理旧连接句柄
24:04.728  扫描停止
24:07.756  连接成功                         ← 断到连 = ~7s
24:09.036  服务发现完成                     ← 连接→发现 = ~1.3s
24:09.488  NONCE 第一次 10007（FF03 写属性未热）
24:10.302  NONCE 写成功（2 次重试后）
```

**「第一次快」= 冷启动直接连，系统 GATT 缓存还在 + 权限早已授予；「后面慢」= 手动断开后系统清缓存 + 每次回前台重跑权限申请 + 重建监听 + 重连重建服务发现。**

### 三大瓶颈（按耗时）

| 瓶颈 | 耗时 | 根因 | 可否绕开 |
|------|------|------|----------|
| **① 权限申请每次重跑** | ~3s | `prepareForAutoConnect→initBluetooth→requestAndroidPermissions` 无「已授权短路」，每次回前台（onShow）都重申请 6 权限 | ✅ 可消除 |
| **② 服务发现全量重做** | ~1.3s | 手动断开=真断连=新 GATT 连接，系统缓存清空，必重发现 | ❌ 系统限制（不动断开语义） |
| **③ NONCE(FF03) 写属性未热** | ~0.4~0.8s | 重连后 FF03 的 WRITE 属性 OS 缓存清空，首帧写必撞 10007（此处无并发读，纯属属性未就绪） | ✅ 可预热 |

### 修复（第八刀，已落地）

**方案 A（瓶颈①，~3s→0）：`requestAndroidPermissions` 加「已授权短路」**
- `utils/ble.js`：首次全量申请成功（`denied.length===0`）后写 `uni.setStorageSync('keygo_perms_granted', 1)`；后续进入先读标记，`===1` 直接 `resolve({granted:true})` 跳过 `plus.android.requestPermissions` 整段。
- `granted=false` 分支（用户系统吊销权限）**不写标记** → 下次仍走全量申请，自动恢复能力不受影响。
- 效果：App 回前台/手动重连不再白等 3s 权限流程。

**方案 C（瓶颈③，~0.8s→0.4s 或 0）：NONCE 前预热 FF03 写属性**
- `stores/ble.js` `_requestNonce`：发 NONCE 前先 `enqueueRead(() => getBLEDeviceCharacteristics(deviceId, FF00))`，该查询让 OS 重新确认 FF03 的 properties(含 WRITE)，预热写属性。
- 走 `enqueueRead` 队列（read 性质，不与 NONCE 写并发，规避第七刀的并发 10007）；失败仅 `console.warn` 降级跳过，**绝不阻塞 NONCE**。
- 预期：重连后 FF03 写属性已热 → NONCE 首帧即成功，不再 10007×2 重试。

**瓶颈②（服务发现）暂不动**：涉及「手动断开=真断连」语义，伪装不断开会破坏用户预期，且 1.3s 属系统固有开销，收益/风险比低。

### 预期

重连总耗时从 ~7s（含 3s 权限 + 1.3s 发现 + 0.8s NONCE 重试）收敛到 ~2~3s（权限短路 + 发现 1.3s + NONCE 预热后一次成）。**「时快时慢」两极分化根除——第一次与后续重连对齐到同一速度。**

纯 JS 改动（utils/ble.js + stores/ble.js），未升 versionCode。
