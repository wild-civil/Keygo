# 固件串口定位 FF02 / CCCD 问题 — 操作清单

> 背景：App 侧已排查并优化了多轮（重订阅风暴、僵尸连接识别、close 白等、看门狗放宽），
> 但"连接存活 ~40s 后 FF02 周期性静默 → 断连 / 绑定验证慢"这个根因**大概率在固件侧**。
> 本清单指导如何抓固件串口日志，把问题定界到「固件在不在发 FF02」「CCCD 是否使能」「谁主动断链」。
>
> 日期：2026-08-17

---

## 一、先搞懂固件 FF02 发送链路（改日志前必读）

固件侧 FF02 状态通知的完整路径：

```
SBP_PERIODIC_EVT（每 1600 tick ≈ 1s，peripheral.c L479）
  → if (g_deviceConnected) KeyGo_NotifyStatus()          // 连接才发
    → snprintf 组 JSON
    → GATT_bm_alloc + simpleProfile_Notify()              // 发 FF02
      → GATTServApp_ReadCharCfg(connHandle, simpleProfileChar2Config)  // 读 CCCD
        ├─ CCCD & GATT_CLIENT_CFG_NOTIFY → GATT_Notification()  → 发出 ✓
        └─ 否则返回 bleIncorrectMode(0x17)                 // CCCD 未使能 → 不发
      → KeyGo_NotifyStatus 里失败【静默，不重试不打印】     // ★ NOTIFY-NOISE-FIX 注释掉了重试
```

**CCCD 是什么**：FF02 特征值上有个 Client Characteristic Configuration Descriptor（CCCD），
App 写 `0x0001` 使能 Notify，固件才能推 FF02。CCCD 存在 `simpleProfileChar2Config[]`（每连接一份）。

**CCCD 何时被固件清零**（gattprofile.c `simpleProfile_HandleConnStatusCB` L508-515）：
连接断开（`LINKDB_STATUS_UPDATE_REMOVED`）时 `GATTServApp_InitCharCfg` 清空。

**CCCD 写回调**（gattprofile.c L479-482）：
App 写 CCCD → `GATTServApp_ProcessCCCWriteReq`，**当前无任何日志** → 看不到"App 写的 CCCD 到没到"。

## 二、确认串口已通（前置条件）

1. 固件 PRINT 宏：`CH583SFR.h` L126-130，`#ifdef DEBUG` 才编译。
   当前工程 MRS IDE 里设置了 `DEBUG=Debug_UART1`（见 keygo_core.h L52），串口日志是开的。
2. 串口：**UART1，115200-8-N-1**。
   - 引脚：PA9（`bTXD1`，peripheral_main.c L201-202 配置为推挽输出）。
   - 接线：板子 **PA9 → USB-TTL 的 RX**，**GND → GND**。
3. 用串口工具（SSCOM / XCOM / MobaXterm 等）打开，115200，8 数据位，1 停止位，无校验。
4. 板子上电后应先看到固件版本打印 `VER_LIB` 等，确认串口链路通。

> 若自焊 PCB 上 PA9 被占用/没引出，可临时改用 UART0/UART2（改 `Debug_UARTx` + 对应引脚），
> 但改引脚会影响低功耗测量（串口外设耗电），定位完记得关。

## 三、定位目标与对应的串口日志

按下面顺序操作，每个目标抓一段日志，对照结论判定。

### 目标 1：确认「固件是否在调 KeyGo_NotifyStatus」（区分 ①固件没发 ②发了但 App 收不到）

**现象**：FF02 静默时，固件串口是否仍有 `[STATUS]` 类输出？

**现状**：当前 `KeyGo_NotifyStatus` 成功发送**不打日志**，失败也不打（NOTIFY-NOISE-FIX）。
所以需要**先加一行成功/失败日志**，才能判断。

**改法**（keygo_core.c `KeyGo_NotifyStatus` L1025-1042）：
```c
if (simpleProfile_Notify(peripheralConnList.connHandle, &noti) != SUCCESS) {
    GATT_bm_free((gattMsg_t *)&noti, ATT_HANDLE_VALUE_NOTI);
    PRINT("[FF02] NOTIFY FAIL (ret=%d), cccd=%04X\n",
          simpleProfile_Notify(peripheralConnList.connHandle, &noti) /* 重读一次拿返回值, 或缓存 */,
          GATTServApp_ReadCharCfg(peripheralConnList.connHandle, simpleProfileChar2Config));
} else {
    s_statusRetry = 0;
    // 可选：PRINT("[FF02] SENT ok, len=%d\n", n);  // 会刷屏, 建议关闭或节流
}
```
> 注意：上面重读 simpleProfile_Notify 会**二次发送**，不可取。正确做法是先把返回值存变量再分支：
> ```c
> bStatus_t notiSt = simpleProfile_Notify(...);
> if (notiSt != SUCCESS) { ... PRINT("... ret=%d", notiSt); }
> ```

**结论判定**：
| 串口日志 | 结论 |
|---------|------|
| 每 ~1s 都有 `[FF02] NOTIFY FAIL`（ret=0x17=bleIncorrectMode） | 固件在发，但 **CCCD 未使能**（固件侧 CCCD=0） |
| 每 ~1s 都有 `[FF02] SENT ok` | 固件在发且发出成功 → **问题在 Android 端收不到**（App 侧 CCCD 订阅没生效/被重置） |
| 完全无 `[FF02]` 日志 | **固件周期任务/KeyGo_NotifyStatus 没跑**（睡眠/卡死/广播问题） |

---

### 目标 2：确认「App 写的 CCCD 到底到没到固件」（定位 CCCD 使能的源头）

**现象**：FF02 静默，需要知道 App 的 `notifyBLECharacteristicValueChange`（写 CCCD=0x0001）是否真到了固件。

**改法**（gattprofile.c `simpleProfile_WriteAttrCB` 的 CCCD 分支 L479-482）：
```c
case GATT_CLIENT_CHAR_CFG_UUID:  // FF02 CCCD
    status = GATTServApp_ProcessCCCWriteReq(connHandle, pAttr, pValue, len,
                                            offset, GATT_CLIENT_CFG_NOTIFY);
    PRINT("[CCCD] WRITE handle=%04X len=%d val=%04X status=%d\n",
          pAttr->handle, len, (len>=2)?(pValue[0]|(pValue[1]<<8)):0, status);
    break;
```

**结论判定**：
| 串口日志 | 结论 |
|---------|------|
| 有 `[CCCD] WRITE ... val=0001 status=0` | App 的 CCCD 写**确实到了**固件 → 使能成功 |
| 有 `[CCCD] WRITE ... val=0000` | App 写的是关闭（异常） |
| 完全没有 `[CCCD] WRITE` 日志 | App 的 CCCD 写**根本没到固件** → Android 端 CCCD 写被吞/未发出 |

> 这是**最关键的定界点**：
> - 若"App 重订阅 CCCD 成功（App 日志 Notify 启用成功）但固件没有 [CCCD] WRITE 日志"
>   → **CCCD 写被 Android 吞了**（Android 底层 GATT 上下文问题，App 侧解决不了，只能靠拆链/重置适配器）。
> - 若固件收到 [CCCD] WRITE val=0001，但 FF02 还是 FAIL(0x17)
>   → 固件 CCCD 存储异常（如多连接数组越界、断连时被误清）。

---

### 目标 3：确认「谁主动断链」（固件主动 vs Android 主动）

**现象**：连接存活 ~40s 后断连，需要知道是固件 `GAPRole_TerminateLink` 还是 Android 断开。

**现状**：固件侧 `SBP_UNBOUND_TIMEOUT_EVT`（30s 未 AUTH 强断）有 `[SEC]` 日志，但 AUTH 成功后无此日志（AUTH 成功会 CancelUnauthTimer）。

**改法**（peripheral.c `Peripheral_LinkTerminated` L900+，在 `g_deviceConnected=0` 前加）：
```c
PRINT("[LINK] TERMINATED reason=%d handle=%x\n", event->reason, event->connectionHandle);
```
原因码（`event->reason`）：`0x13`=远程断开，`0x08`=连接超时（Android 主动断/链路掉线），
`0x16`=本地终止（固件主动），`0x22`=LL resp timeout 等。

**结论判定**：
| reason | 谁断开 | 方向 |
|--------|--------|------|
| 0x13 | 对端（Android）主动 | 问题在 Android 侧 |
| 0x08 | 连接超时（双方久无流量） | 链路问题（连接参数/干扰） |
| 0x16 | 固件本地主动终止 | 固件逻辑（如 30s 超时） |
| 其他 | 视原因码 | 查 BLE spec |

---

### 目标 4：确认「断连时 CCCD 是否被清」（连接重连后 CCCD 是否残留）

**现象**：重连后 FF02 正常（CCCD 从干净开始），但连接中段 CCCD 可能被误清。

**改法**（gattprofile.c `simpleProfile_HandleConnStatusCB` L508-515）：
```c
if (connHandle != LOOPBACK_CONNHANDLE) {
    if ((changeType == LINKDB_STATUS_UPDATE_REMOVED) ||
        ((changeType == LINKDB_STATUS_UPDATE_STATEFLAGS) && (!linkDB_Up(connHandle)))) {
        PRINT("[CCCD] LINK REMOVED, clear cfg conn=%x\n", connHandle);
        GATTServApp_InitCharCfg(connHandle, simpleProfileChar2Config);
    }
}
```

## 四、完整抓取流程（一次搞定）

### 准备
1. 串口工具连 PA9（115200），固件重烧（加好上面 4 处日志）。
2. App 打开，进入扫描页。

### 步骤
1. **记固件串口起始日志**（应有 `VER_LIB` / 广播相关打印）。
2. App 连接设备 → 观察：
   - `[CCCD] WRITE val=0001` 是否出现（App 订阅 FF02）
   - `[FF02] SENT ok` 是否每 1s 出现
3. 观察连接稳定期：FF02 是否持续 `SENT ok`。
4. 等到 FF02 静默/断连：
   - 看 `[FF02] NOTIFY FAIL` 是否出现（固件还在发但 CCCD=0？）
   - 看 `[LINK] TERMINATED reason=?`（谁断的）
   - 看 `[CCCD] LINK REMOVED`（断连时清 CCCD）
5. 如果 FF02 静默期间 App 侧有"重订阅"动作，再抓一次 `[CCCD] WRITE` 是否重新到达。

### 记录
把固件串口日志 + App 控制台日志**时间对齐**（串口工具开时间戳），一起保存。

## 五、根据日志结果的 4 种走向

| 结果组合 | 根因 | 下一步 |
|---------|------|--------|
| `[FF02] SENT ok` 持续，但 App 收不到 | **Android 端 CCCD 订阅没生效/被重置**（App 侧或 OS 层） | App 侧：更激进地重订阅/拆链重建/适配器重置 |
| `[FF02] NOTIFY FAIL(0x17)` + 无 `[CCCD] WRITE` | **App 的 CCCD 写被 Android 吞了**（没到固件） | App 侧：确认 `notifyBLECharacteristicValueChange` 后读回 CCCD 验证；不行就拆链重建 |
| `[FF02] NOTIFY FAIL(0x17)` + 有 `[CCCD] WRITE val=0001` | **固件 CCCD 存储异常**（数组/断连误清） | 固件侧：查 simpleProfileChar2Config 生命周期 |
| 无 `[FF02]` 日志 | **固件周期任务没跑**（睡眠/卡死） | 固件侧：查 SBP_PERIODIC_EVT、HAL_SLEEP、功耗 |

## 六、修复方向（定界后）

### 方向 A：固件侧重启 FF02 发送（应对 CCCD 短暂重置/ATT 忙）
`KeyGo_NotifyStatus` 的 NOTIFY-NOISE-FIX 注释块（L1031-1033）已写明正确方案：
```c
// 按返回码区分：
//   bleIncorrectMode(0x17, 未订阅) → 不重试（无 App OS 重连正常）；
//   blePending / bleMemAllocError   → 保留重试（ATT 忙兜底）。
```
如果 FF02 静默是因为 **ATT 忙/分配失败**（非 CCCD 未使能），恢复 `blePending/bleMemAllocError` 重试
可让 FF02 在瞬时失败后自动补发，打破"静默 → 断连"循环。**但若是 bleIncorrectMode（CCCD=0），重试无效**。

### 方向 B：App 侧（如果坐实是 Android 吞了 CCCD 写）
- `notifyBLECharacteristicValueChange` 后主动 `readBLECharacteristicValue` 读回 CCCD 验证是否 0x0001。
- 读回失败/为 0 → 判定 CCCD 未生效 → 拆链重建（我们已实现僵尸连接识别，可复用）。

### 方向 C：适配器重置（最后手段，影响全局蓝牙）
`closeBluetoothAdapter + openBluetoothAdapter` 强制 Android 丢弃所有 GATT 缓存。
仅当"同一设备持续 FF02 静默、拆链重建也无效"时才考虑。

---

## 七、注意事项

1. **改固件日志后必须重烧固件**；固件侧日志只在 `#ifdef DEBUG` 编译，确认工程已开 DEBUG。
2. **串口打印耗电**（UART1 外设 + PRINT），低功耗测量前记得关掉日志。
3. **时间对齐**：串口工具开启时间戳，和 App 控制台日志逐条对比，才能定位"FF02 静默先出现"
   还是"断连事件先出现"。
4. 建议抓 **2~3 次完整循环**（连接→静默→断连→重连），确认是规律性还是偶发。
5. 若 App 侧已是最新（含 recoveryOnly、僵尸识别、close 跳过），抓串口时保持 App 就是这个版本，
   避免"改了 App 又抓串口"对不上。
