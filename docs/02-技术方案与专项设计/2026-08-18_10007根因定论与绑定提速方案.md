## 一、10007 到底是什么？（定论，2026-08-17 真机实测闭环）

### 一句话结论

**`10007` 不是"属性不支持"，而是 Android BLE 栈本地拒绝 GATT 写**，根因是**固件 ATT 事务槽被 FF02 周期推送占满**，把 App 的 NONCE/AUTH/配置/RSSISET 写请求挤成"通道忙"。**已治本落地**（固件 FF02 自适应退避 + App 提前订阅 FF02）。

### 证据链（2026-08-17 真机串口 + App 日志对齐）

```
[19:02:50.931] [FF02] NOTIFY FAIL ret=16 (ATT忙)     ← 固件自己撞 ATT 事务槽忙（与 Android 无关）
[19:02:53.462] [1007DIAG] FIRST FF01(cfg) AFTER AUTH t=196368 dtAuth=2843 (window② elapsed)
App: 48.792 FF03 NONCE 10007 ×7 → 49.685 命中（窗口①≈0.9s）
App: 53.266 FF03 RSSISET 10007 ×14 → 55.729 命中（窗口②≈2.5s）
```

| 假说 | 判定 | 依据 |
|------|------|------|
| ❌ "Android GATT 缓存冷窗 4.2s" | **已推翻** | 服务发现已完成仍持续 1007；固件自身报 `NOTIFY FAIL ret=16` |
| ❌ "CCCD 订阅被吞" | 已排除 | 日志实证 CCCD 订阅 ~0s 即生效 |
| ❌ "GATT 复用旧连接 / 加密触发" | 已排除 | `g_encRequired=0` 无加密状态变化；AUTH:OK 无 GATT 缓存副作用 |
| ✅ **固件 ATT 事务槽被 FF02 占满** | **定论** | 铁证：固件自己 `blePending`；退避后 RSSISET 零 1007 |

### 已落地的治本改动（两端协同）

| 端 | 改动 | 效果（19:13 真机验证） |
|----|------|------------------------|
| 固件 `keygo_core.c` | `KeyGo_NotifyStatus` 检测 `blePending` → 退避 600ms 让位 App 写（`FF02_BACKOFF_MS`）；握手 RAW 队列（NONCE/AUTH:OK）走独立 `SBP_DEFERRED_RAW_EVT` 不受影响 | RSSISET **零 10007** |
| App `stores/ble.js` | 连接后**立即**订阅 FF02（去掉 800ms 延时，CCCD 写排链队首），SN 读并行在后 | 窗口① 从 5.98s 压回 ~1s |
| App `utils/command-queue.js` | 全部 GATT read/write 走同一串行链（第七刀） | 杜绝并发抢事务槽 |

> 完整过程见 `docs/03-复盘与问题分析/4-硬件与专项分析/2026-08-17_1007固件侧ATT忙窗量化诊断打点.md` 与 `2026-08-17_1007治本收尾_固件退避+App订阅时序.md`。

## 二、能否让绑定验证"超级快速"？（能，方向明确）

### 2.1 绑定验证（AUTH 重连验证）当前耗时拆解

```
连接建立 (GAP)          ~0.5s
  ↓
订阅 FF02 (CCCD 写)     ~0.3s    ← 已优化：连接即订阅，不再等 800ms
  ↓
NONCE 写 (FF03)         ~0.9s    ← 窗口①：FF03 写属性就绪 + 密集重试跨冷窗
  ↓
NONCE 回包 (FF02)       ~0.2~1s  ← ★ 受连接事件空窗波动（LATENCY=2 最坏 720ms）
  ↓
AUTH 写 (FF03)          ~19ms    ← 算法极快（2026-08-12 实测）
  ↓
AUTH:OK 回包 (FF02)     ~0.2~1.2s ← ★★ 绑定"忽快忽慢"的主源：等下一个连接事件窗口
──────────────────────────────
总计                    约 1.5~3.5s（波动主要来自两个 ★ 的连接事件空窗）
```

### 2.2 超级快速的关键：AUTH 期间降 LATENCY + 短连接间隔 ⭐⭐⭐（2026-08-18 已实施）

**物理约束**：`AUTH:OK` 是 GATT Notify，必须等**下一个连接事件窗口**才能发出。当前 `LATENCY=2`、间隔 160~320ms → 最坏 `(2+1)×320ms ≈ 1s` 波动（2026-08-12 实测 1.2s）。

**方案（已落地，固件 3 处改动）**：
1. `peripheral.h` 新增宏 + 事件位：
   - `AUTH_FAST_MIN/MAX_CONN_INTERVAL = 24/48 (30/60ms)`、`AUTH_FAST_SLAVE_LATENCY = 0`、`AUTH_FAST_CONN_TIMEOUT = 400`
   - 事件位 `SBP_AUTH_FAST_PARAM_EVT = 0x0080`（与 `SBP_PARAM_UPDATE_EVT 0x0008` 不冲突），delay 宏 `SBP_AUTH_FAST_PARAM_DELAY=60`、`SBP_AUTH_BACK_TO_SLOW_DELAY=200`
2. `Peripheral_LinkEstablished`：**连接后 60ms 即发 `SBP_AUTH_FAST_PARAM_EVT`**（发 FAST 参数请求），取代原"delay 后发 DEFAULT"。让 NONCE/AUTH 全程走快窗口（不再等 4s 的 `SBP_PARAM_UPDATE_DELAY`）。
3. `Bonding_HandleAuthResp` AUTH:OK 分支：**AUTH 成功后延迟 200ms 触发 `SBP_PARAM_UPDATE_EVT`**（发 DEFAULT 省电参数），先让 AUTH:OK 走 FAST 窗口发出再切回。`SBP_PARAM_UPDATE_EVT` 保留原周期保活逻辑（每 `SBP_PARAM_UPDATE_PERIOD` 重试，防手机 Doze 回溯）。

**预期效果（诚实评估，非保证）**：
- **乐观（手机采纳 fast）**：AUTH:OK 最坏从 ~960ms 降到 **100ms 量级**（LAT=0 时最坏=1 个间隔），平均从 ~360ms 降到 ~40ms；绑定总耗时从 1.5~3.5s 收敛到 ~1~1.5s 且波动显著减小。
- **悲观（手机忽略请求）**：维持连接建立时的间隔（已由广播 `ADV_FAST_*` 声明为 30/60ms，本身也不慢），行为与现状**持平，无退化**。
- **实际大概率**：手机多半采纳更小间隔（60~100ms 常见），综合最坏落在 **100~300ms**，比现在 1.2s 仍显著快。

> 风险与边界：
> - 不带负优化：手机拒绝则持平；AUTH 后切回 DEFAULT 有周期保活，省电行为不丢。
> - 若手机拒绝"切回 DEFAULT"，会停在 FAST（30~60ms）持续 → 略费电但连接更灵敏，非功能性 bug。
> - 纯连接未走 AUTH 的极端场景（如后台扫描未鉴权）会停在 FAST；但设备常态 30s 强断门控必走 AUTH，可忽略。如需更稳可加"连接 N 秒兜底切 DEFAULT"，先不画蛇添足。
> - 串口日志可验证：`[CONN] fast param req (AUTH window)...` + 参数更新回调（看手机是否接受 / 接受值）。

### 2.3 App 侧已无剩余瓶颈（确认）

| 项 | 状态 |
|----|------|
| `AUTH_WARMUP_MS = 0`（订阅后立即 AUTH） | ✅ 已最优 |
| NONCE 150ms×30 密集重试跨冷窗 | ✅ 已最优 |
| FF02 订阅前置（不等 SN 读） | ✅ 已最优 |
| AUTH 互斥锁防并发 | ✅ 已最优 |
| fwSec 持久化避免首轮 AUTH 格式错误 | ✅ 已最优 |

App 侧唯一可再压的点是**连接事件空窗本身**——那属于固件连接参数范畴（2.2），App 无能为力。

### 2.4 首次绑定的"慢"与 AUTH 不同（OS 配对为主，无法加速）

首次绑定含 `createBond`（OS 系统配对、弹窗输码、加密握手）——这是 Android 系统行为，App/固件都无法压缩（实测 30~60s 含人工输码）。**能优化的只有"绑定后的 AUTH 验证"（2.2）与"重连自动验证"**。

## 三、4 条通道够不够？要不要拆分？（结论：够用，不要拆）

### 3.1 通道职责已清晰，无功能性缺口

| 通道 | 职责 | 是否还有别的活要干 |
|------|------|---------------------|
| FF01 | 配置下发 + RSSI 注入 | 无 |
| FF02 | 状态 JSON + 绑定短报文（NONCE/AUTH:OK/BIND:OK/DENY） | 已通过前缀区分两种报文，独立队列（`SBP_DEFERRED_RAW_EVT`）防抢 |
| FF03 | 控制（C1 签名）+ 绑定/鉴权命令（BIND/AUTH/NONCE…） | 已通过前缀路由，独立环形缓冲防重入 |
| FF04 | 序列号读 | 无 |

**所有命令都是"请求-响应"式串行对话**（一次一个），不存在需要并行通道的业务——GATT 事务串行队列（`enqueueWrite`）已经强制了这一语义。

### 3.2 拆分通道对 10007 无用，反而有害

**10007 根因是"ATT 事务槽争抢"，不是"通道数量不足"**：
- Android 的 GATT 事务槽是**所有特征值共享**的（read/write/descriptor 同一时刻只能一个在飞行）；
- 拆出再多通道，它们仍共用同一事务槽 → 10007 的物理成因不变；
- 治本的是"错峰"（固件退避）+ "串行"（App 队列），**与通道数无关**。

**拆分反而带来两个副作用**：
1. **GATT 表变大 → Android discover 变慢** → 连接后"属性就绪"更晚，冷窗口更长（已有文档明确：GATT 表越小、常用特征越靠前，discover 越快）。
2. **每多一个特征 = 多一份独立的"写属性缓存就绪"等待** → 10007 冷窗口的"逐特征值"特性会让新通道也经历同样的 0.5~4.2s 冷窗，等于把问题复制一份。

### 3.3 什么情况下才需要拆？

只有出现**"大流量并行"**需求才需要（当前没有）：
- 例如：未来要边收状态流边传文件（OTA 固件升级）——那时可拆一条独立的 OTA 数据特征（如 FF05，Write Without Response + 独立 MTU 长包），与 FF02 状态流互不干扰。
- 当前绑定/控车/配置都是低频短报文，**没有拆分的理由**。

### 3.4 结论

> **4 条通道够用。不拆。** 绑定提速的正道是"连接参数快窗"（2.2），不是通道拆分。唯一可留意的未来扩展位：若做 OTA，新增独立特征（FF05）走长包写入。

## 五、重要观察：连着 HBuilderX（电脑）时绑定更慢，断开后略快（非错觉）

> 讨论时间：2026-08-18（用户实测反馈）

### 5.1 现象
- 手机 USB 连电脑、HBuilderX 真机调试模式下跑 App：绑定验证**整体偏慢**；
- 拔掉 USB / 断开 HBuilderX 调试链路后，同样操作绑定验证**明显快一截**。

### 5.2 根因（高概率）
uni-app 真机调试模式下，App 内所有 `console.log` **不是只写本地**，而是要通过 USB/adb 桥接**逐条推送到电脑 HBuilderX 控制台**。
BLE 回调是高频事件（NONCE 通知、AUTH:OK、FF02 每秒一帧、电池读兜底等），每个回调若带 log，会把**每条日志的桥接延迟**叠加进 JS 事件循环：

1. 阻塞/拖慢微任务调度：AUTH 握手是"写 → 等通知 → 写"的紧耦合时序，log 桥接延迟直接叠加进每步间隔；
2. 高频 FF02 帧的 log 推送持续占住调试桥带宽，与握手时序抢调度。

断开电脑后 App 跑"正式运行态"（无调试桥，log 落本地甚至被抑制），事件循环干净 → 握手自然快。

### 5.3 次要可能
- HBuilderX 在手机端常驻调试服务（adb 轮询、文件热重载监听）间接占用系统资源，轻微影响调度——但权重低于 5.2 的 log 桥接。

### 5.4 对"优化方向"的关键影响（务必记牢）
**调试态下的耗时 ≠ 正式包耗时。** 任何"绑定快慢"的对比评估，必须区分两种环境：
- 连电脑调试测出的"慢"，含调试桥开销，**不能当作固件/App 逻辑的真实瓶颈**；
- 真要衡量优化收益，**打 release 包（或关掉 BLE 相关 console 输出）** 再测，才是真实数据。
- 之前所有"绑定验证 1.5~3.5s"的波动评估，若是在连电脑下测的，实际 release 包可能已更快、波动更小。

> 验证方法：临时把 BLE/BIND 相关 `console.log` 降级为不推送（或 `manifest` 关调试），对比连电脑时的速度；或直接出 release 包测。

## 六、"连接 3s 才显示" 深度拆解 + "AUTH 提前到订阅后"的优劣评估

> 讨论时间：2026-08-18（用户问：点连接约 3s 才显示，然后才绑定验证；并问把 NONCE/AUTH 从"SN 读回后"提到"订阅 FF02 后立即"的优劣）

### 6.1 先澄清：AUTH 提前到"订阅 FF02 后立即"——**这件事已经完成**

用户提到的优化（AUTH 不再等 SN 读回），**已在 2026-08-16/17 的 commit 中落地**，并非待办：

- `stores/ble.js` `_finalizeConnection` 内 `readSerialNumber().then(...)` 的注释（行 2314-2319）明确：
  > "AUTH 触发**只**由下方 `_enableStatusNotify`（FF02 Notify 订阅就绪后）驱动，此处【不再】触发 `_maybeAutoAuth`。旧逻辑在 readSerialNumber(5000ms 超时).then 里触发 AUTH——但 SN 读一旦慢会延迟到 5s 之后，而固件未 AUTH 踢窗仅 ~3.1s，导致重连 AUTH 永远赶不上、连上即被踢。Notify 订阅在 800ms 后即就绪，AUTH 立即发出，不依赖 SN，必能命中 3.1s 窗。"
- 同一文件 2091-2096 行（重连路径 `_doReconnect`）同步做了"FF02 订阅尽早入链队首、与 readSerialNumber 并行、订阅就绪即驱动 AUTH"。
- 对应 commit：91bbe5c（P-NAME-INSTANT / RSSISET 冷窗）+ 2e8368f（P-AUTH-PRIORITY / 固件快间隔声明）。

**结论**：用户日志里 12:31:58.414 写 NONCE（连接成功 56.691 → 58.414，约 1.7s）这段，已经**不含** SN 读回阻塞——SN 读（58.305）和 NONCE 写（58.414）几乎并行。那 1.7s 是**连接后到 FF02 订阅就绪**本身的开销，与 SN 无关。

### 6.2 "连接 3s 才显示" 的真实耗时构成

用户体感的"3s 才显示"，通常对应 **点击连接 → onConnect 成功 → 界面切到已连接态** 这段。若把"绑定验证"也算进去，则分两段：

```
① 点击连接 → onConnect 成功（界面"已连接"出现）
   包含: 扫描发现 / 按缓存 MAC 直连 → GAP 连接建立
   典型: 0.5~2s（取决于是否走扫描；缓存 MAC 直连更快）
② onConnect 成功 → FF02 订阅就绪 → AUTH 握手完成
   包含: setBLEMTU → getBLEDeviceServices → getBLEDeviceCharacteristics
         → 启用 FF02 Notify(CCCD 写) → NONCE 写 → AUTH:OK
   典型: 1.5~2.5s
────────────────────────────
合计: 约 2.5~4s（与用户"3s 才显示"吻合）
```

**② 段是优化重点，拆细（基于 12:31 日志实测）：**
| 子环节 | 实测/典型 | 说明 |
|---|---|---|
| setBLEMTU | ~0.1s | 已做 3s 超时兜底 |
| 服务发现 (getBLEDeviceServices) | ~0.9s（56.691→57.909） | **大头之一**，无法跳过 |
| 特征发现 (getBLEDeviceCharacteristics) | ~0.1s | 紧随服务发现 |
| 启用 FF02 Notify | ~0.1s（57.930/57.945） | 已尽早，无需等服务发现完成（用常量 UUID）|
| SN 读（并行，不阻塞 AUTH） | ~0.4s（57.945→58.305） | 已与 AUTH 解耦 |
| NONCE 写 → NONCE 回 → AUTH 写 → AUTH:OK | ~0.9s（58.414→59.993） | 握手本身，已最优 |

**关键认知**：SN 解耦之后，"连接后到握手前"的 1.7s 里，**服务发现占 ~0.9s，是绝对大头**；订阅/握手发起已无冗余等待。

### 6.3 进一步压缩"3s"的可行手段与优劣

既然 SN 已解耦，剩余可优化点只有一个真瓶颈（服务发现）+ 几个小头：

| 手段 | 预期收益 | 优劣 |
|---|---|---|
| **A. 服务/特征发现提前并行** | 省 0~0.3s | 优：MTU 协商与服务发现本可并行（部分 ROM 允许）；劣：改动小但收益有限，且必须先 onConnect 才能 discover，天花板在 OS 实现 |
| **B. 缓存 GATT 表（二次连接跳过 discover）** | 省 ~1s（仅重连） | 优：Android `getBLEDeviceServices` 对近期连过的设备有系统级缓存，秒回；**首次连仍要 discover**。劣：部分 ROM 缓存失效会回退全量 discover，不能 100% 依赖 |
| **C. 缩短 ① 段（连接建立本身）** | 省 0.5~1.5s | 优：用缓存 MAC **直连**跳过扫描（你断连重连日志 12:31:50 走了 6s 扫描才连上，那是重连路径问题，非握手）；劣：首连必须扫描，无法压 |
| **D. 固件 AUTH 期间 fast 连接参数（LATENCY=0，见 2.2 ✅已实施）** | 乐观省 ~0.5~1s（握手段），悲观持平 | 优：AUTH:OK 回包最坏从 ~960ms 降到 100ms 量级（需手机采纳）；劣：手机可能忽略参数请求（持平无退化），或拒绝切回 DEFAULT 而持续 FAST（略费电） |
| **E. 关掉调试态 log（见第五节）** | 连电脑时省 0.5~1.5s | 优：零代码风险，纯环境；劣：只在调试态有效，release 包本就无此开销 |

### 6.4 关于"SN 异步回填"方案的优劣（用户原问，已落地，复盘结论）

既然该方案已实现，这里给**定型后的优劣评估**，供后续参考：

**优点（已验证）：**
1. **握手不再被 SN 读回拖慢**：SN 走 `_gattChain` 读，最坏 5s 超时；解耦后 AUTH 在 FF02 订阅就绪（~0.8s）即发，彻底消除"SN 慢 → 握手晚 → 撞固件 3.1s 踢窗"的致命链路（这是之前"连上即被踢"的根因，已治愈）。
2. **设备名与验证解耦**：配合 P-NAME-INSTANT（MAC 索引即时恢复），实现"连接即显名 + 验证走快路径"两不误，终结了"验证快则无名 / 显名则慢"的矛盾。
3. **SN 仍异步回填**：`readSerialNumber().then` 里照常填 `serialNumber`、加载设备配置、恢复 bindKey（以 deviceId 为主键，连接即有其值，不受 SN 异步影响）。

**代价 / 注意点：**
1. **首连新设备（MAC 索引无记录）时**：自定义名要等 SN 读回才能显示（~0.4s 延迟），这是可接受的——首连本就慢（含 discover + 可能系统配对）。
2. **bindKey 恢复时机**：AUTH 触发早于 SN 读回，故 bindKey 必须**以 deviceId(MAC) 为主键**预先恢复（连接即恢复，见 2249-2253 行），不能等 SN——这一点已在 2026-08-18 修复，否则首轮 AUTH 会因 bindKey=null 放弃。
3. **无退化风险**：SN 读失败只影响"名/配置回填"，绝不回堵握手主链；AUTH 成功与否与 SN 完全无关。

**结论**：SN 异步回填是"治本级"修复（解决了踢窗致命问题），且已无副作用。后续绑定提速的重心应转向 **6.3 的 D（固件 fast 连接参数）+ C（重连直连跳过扫描）+ E（区分调试/正式环境测速）**，SN 维度已无油水。

## 八、RSSI 一直显示 `---` 的分析与修复（2026-08-18 用户反馈）

> 现象：烧入 fast 参数固件后，绑定验证明显变快（预期内），但 App 端 RSSI 一直 `---`。
> 用户原疑："绑定变快"与"rssi 消失"是否有关。

### 8.1 真因（2026-08-18 二次深挖，用户指正"仍 ---"后定位）

上一版"协议栈协商异常/毛刺死锁"两个假设**都没命中**。真正根因是 **TMOS 事件位冲突**：

```
#define SBP_AUTH_FAST_PARAM_EVT     0x0080  // ← 我新加的
#define SBP_STATE_MACHINE_EVT       0x0080  // ← 状态机轮询，早已占用 0x0080
```

**破坏机制（致命）**：
- 两个事件共用 `0x0080` → TMOS 把它们当成**同一个事件**；
- 状态机每 ~1s tick（`SBP_STATE_MACHINE_EVT`）时，`Peripheral_ProcessEvent` 收到的 `events` 中 bit 0x0080 恒置位 → **既进状态机分支，也进 `SBP_AUTH_FAST_PARAM_EVT` 分支**（peripheral.c:541）；
- 结果：**`GAPRole_PeripheralConnParamUpdateReq` 每 1s 被重复发送**（不是连接时的一次性，而是永续）；
- fast 参数请求持续抢占 HCI 命令通道，与状态机内每 1s 调一次的 `GAPRole_ReadRssiCmd` 激烈竞争 → RSSI 命令被持续拒绝/排队 → **`peripheralRssiCB` 回调永远不来** → `g_latestRSSI`/`g_filteredRSSI` 永久卡 -999 → App 两处 `> -999` 过滤都不成立 → UI `---`。

**为什么"保守化 + 毛刺修复"都没用**：根因根本不是参数激不激进、也不是毛刺逻辑，而是 fast 请求被无限重复发送堵死了 RSSI 通道。只要事件位冲突在，任何参数值都会每 1s 发一次 → 必然堵死。

### 8.2 已落地修复（2026-08-18 二次修正）

**① 修复事件位冲突（关键修复）**（peripheral.h）
- `SBP_AUTH_FAST_PARAM_EVT` 从 `0x0080` 改到空闲位 `0x0004`（注释明确标注"位释放可用"，且 `SBP_ADV_ULTRA_SLOW_EVT` 已 #if 0 停用、无启动源）；
- 改后：fast 参数请求只在连接建立时触发**一次**（peripheral.c:854 `tmos_start_task`），不再被状态机每 1s 重复触发；
- HCI 通道不再被 fast 请求持续占用 → `GAPRole_ReadRssiCmd` 回调恢复正常 → RSSI 链路恢复。

**② fast 参数保守化（保留，无害更稳妥）**（peripheral.h:174-178）
- interval 40-80ms、timeout 6s、delay 80ms，LAT0 保留。降低手机拒绝概率。

**③ 毛刺死锁修复（保留，健壮性改进）**（keygo_core.c）
- 新增 `SPIKE_RECOVER_LIMIT=6`，连续毛刺超上限强制接受一次样本，防止 Kalman 永久死锁在 -999。

**④ App 侧兜底 + RSSISET 回归修复（上一版已落地，保留）**（stores/ble.js）
- `f` 哨兵 -999 但 `r` 真实时用 r 兜底 f；
- `_armPostAuthWrites` 冗余清除块已删，RSSISET 恢复下发。

### 8.3 验证方法
1. **必做**：烧入新固件（事件位改 0x0004）→ RSSI 应恢复正常显示（fast 请求不再每 1s 重复）；
2. **串口确认**：过滤 `[CONN] fast param req` 看是否只出现**一次**（连接时），而非每 1s 刷屏；同时 `[RSSI]` 应输出真实 r/f 值；
3. **回归**：绑定速度仍应快（fast 参数在 AUTH 窗口内生效一次）。

### 8.5 铁律补充（本次教训）
- **TMOS 自定义事件位必须全局唯一**（0x0001~0x4000），新增事件位前必须 grep 全工程确认无占用；不得使用已分配给状态机/周期任务等核心机制的位（如 0x0080）。
- 连接参数更新请求（`GAPRole_PeripheralConnParamUpdateReq`）每 1s 重复发送会**堵死 RSSI 采样通道**，是隐蔽但致命的副作用。
