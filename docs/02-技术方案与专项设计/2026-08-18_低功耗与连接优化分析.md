> 日期：2026-08-18

## 一、低功耗优化（当前主要缺口）

### 1.1 【固件·高收益】断连态广播：两档恒定（普通 600ms / NoApp 150ms），不分档 ⭐

**现状**：`peripheral.h` 里 `ADV_CONST_NOAPP_TICKS` 与 `ADV_CONST_NORMAL_TICKS` **都是 240 ticks = 150ms**（2026-08-05 统一）。实测断连 ~88µA 的绝大部分是广播电流（每 150ms 醒来发一包）。

**用户决策（2026-08-18 确认）：不做分档降速（3s快窗→慢速→超慢），因为短时重连概率很小，从远处回来直接就是最慢挡位，分档无意义。**

**方案（两档恒定，由 `g_encRequired` 二选一）**：
- **NoApp 模式（g_encRequired=1）**：保持 **150ms**（`ADV_CONST_NOAPP_TICKS` 不变）—— 无App解锁靠 OS 被动发现+重连，发现慢 1 秒用户能感知，150ms 是必要。
- **普通 App 模式（g_encRequired=0）**：改 **600ms**（`ADV_CONST_NORMAL_TICKS` 240 → 960）—— App 会主动扫描连接（扫描窗口 8s，任何时刻扫 1 个广播周期即可捕获），广播慢不影响发现；断连电流可再降 ~40%。

**回答"两个值是否并存"**：是。两个宏本来就分开定义，只是当前值相同（都是 150ms）。改成 960 ticks 后，普通模式 = 600ms、NoApp 模式 = 150ms，由 `KeyGo_AdvEnterFastWindow` 按 `g_encRequired` 分支二选一，**不存在同时存在**——开启 NoApp 时普通档自然不生效，反之亦然。

**实现（极小，不改协议）**：
1. `peripheral.h`：`ADV_CONST_NORMAL_TICKS` 240 → 960（600ms）。
2. 现有 `KeyGo_AdvEnterFastWindow` 已按 `g_encRequired` 分支设置常量，**零代码改动**，仅改宏值。
3. 注意看门狗红线：广播间隔 >2.5s 触发软复位误判（`config.h` HAL_SLEEP 注释），**600ms 远低于 2.5s，安全**。
4. `peripheral.h` 里 `SBP_ADV_SLOWDOWN_EVT` 等降速链死代码继续保留（不启用），勿误以为需要恢复。

> 权衡确认：普通模式 600ms 下，App 扫描 8s 内最坏等一个广播周期（600ms）即捕获，用户无感知；代价是广播平均电流上升周期变长，但断连态本身无连接，收益纯粹。

### 1.2 【固件·中收益】连接态"活跃/空闲"分档连接参数 ⭐

**现状**：连接后固件请求 160~320ms/LATENCY=2 恒定；`SBP_PARAM_UPDATE_EVT` 每 30s 重发同一组参数。连接稳定电流 ~240µA 的主源是"每 320ms 醒来收发空包"（2026-08-04 实测）。

**建议（2026-08-04 已有讨论稿，未落地）**：
- **活跃期（连接后 0~N 秒 / 刚发过控制命令）**：请求 `60~100ms / LATENCY=0` —— AUTH、控车、配置秒级往返。
- **空闲期（N 秒无交互后）**：请求 `360ms+ / LATENCY=3~4` —— 电流可降到 ~80µA。
- 触发点：`Peripheral_HandleFF03` 收到控制命令 → 切回活跃参数；`KeyGo_ProcessStateMachine` 无动作计时 → 切空闲参数。
- 手机（Android 主端）不一定会接受，但固件建议是"协商下限"，值得做；`SBP_PARAM_UPDATE_EVT` 已每 30s 重试，正好用于"空闲期主动拉长"。

### 1.3 【固件·确认】DCDC_ENABLE

**现状**：`config.h` `DCDC_ENABLE=FALSE`。注释说明硬件自焊板已串电感（fix17 曾启用），收益是活跃/连接态电流降至 ~60%。

**建议**：确认当前板子的 VSW/VDCID 电感与 2.2uF 退耦是否合规（注释里 4 条前提），合规则开回 `TRUE`。这是**纯硬件参数、零代码风险**的低功耗收益。

### 1.4 【固件·小收益】断连态停掉 30s 电池轮询？→ 不建议

电池检测 30s 一次（`SBP_BATTERY_CHECK_EVT`），断连态也在跑以保证广播包电量实时。单次 ADC 采样+广播包更新是 μs~ms 级，30s 周期下功耗可忽略。**保持现状即可**（注释也说明这是断连态唯一低频唤醒）。

### 1.5 【App·小收益】扫描功耗

`startScan` 用 `powerLevel: 'high'` + 8s 超时。舒适模式"亮屏触发 8s 扫描"已是最小化（用户可见延迟换功耗）。**不建议改**。极速模式 GPS 围栏已按事件触发。

## 二、连接速度优化

### 2.1 【固件】连接参数"快窗"让 AUTH/服务发现提速 ⭐

连接建立后固件 `Peripheral_LinkEstablished` 启动 `SBP_PARAM_UPDATE_EVT`，**4 秒后**才发参数更新请求。这 4 秒内手机按它自己的默认间隔跑（通常较快，但不可控）。

**建议**：连接建立后**立即**（或 500ms 内）发一次 `60ms/LATENCY=0` 的参数更新请求，把 AUTH/FF04 读/FF02 订阅都压在快窗口里完成；AUTH 完成后（或 30s 重试逻辑）再切 1.1/1.2 的空闲参数。实现上就是 `SBP_PARAM_UPDATE_DELAY` 从 6400 改小 + 分两档参数。

> 参考：2026-08-12 文档已记录"AUTH:OK 延迟 1.2s = 连接事件空窗"，LATENCY=2 时最坏 `(2+1)×320ms≈1s`。**AUTH 期间临时 LATENCY=0** 能把回包波动压到 ~320ms 以内，绑定验证"忽快忽慢"体感直接改善。

### 2.2 【固件】广播包瘦身（可选）

广播包当前含 Flags + Appearance + 3×16bit UUID + Service Data(电量) = 31 字节上限内。已接近满。若未来要加厂商数据（如无App模式指纹），需把电量从广播里拿掉（改 3b 段或注释 3a）。**当前不改**，仅记录。

### 2.3 【App】连接链路已高度优化，剩余观察点

`_doReconnect` 已做：跳过 stale close（省 2s）、connected=false 跳过 700ms 拆链等待、重连=首连复位、NONCE 密集重试（150ms×30 跨 4.2s 冷窗）。**App 侧连接速度主要瓶颈已不在代码，而在 Android GATT 栈本身**（服务发现 ~0.4s、写就绪冷窗 ~4.2s 是平台行为）。

唯一可再压的点：`connectDevice` 的 `timeout: 10000`（10s）+ 外层 18s 硬超时 —— 属安全兜底，不建议改小。

## 三、绑定速度优化（"验证慢"的根治方向）

### 3.1 【固件·关键】AUTH 期间降 LATENCY（见 2.1）⭐

绑定验证"慢"的实测根因：AUTH:OK 回包等连接事件空窗（最坏 ~1s）。**AUTH 期间 LATENCY=0 + 短间隔**，回包延迟可降至 100~300ms 级。这是绑定提速性价比最高的一刀。

### 3.2 【固件·已做】Flash 写延迟已解

`Bonding_FlushLtkFpIfPending`（1s 定时统一落盘）已消除 AUTH 路径的 Flash 阻塞（2026-08-17 落地）。**无需再动**。

### 3.3 【App·已做】NONCE 密集重试 + FF02 订阅前置

`_requestNonce` 150ms×30 跨冷窗、`_enableStatusNotify` 连接即订阅、`_restoreFwSec` 持久化避免首轮 AUTH 格式错误 —— 均已落地。**App 侧绑定流程无明显剩余瓶颈**。

### 3.4 【固件·可选】FF03 命令回包走独立短报文队列（已存在）

`SBP_DEFERRED_RAW_EVT` + `KeyGo_FlushRawNotify` 已保证 BIND:OK/AUTH:OK 不与状态 JSON 抢队列。**保持现状**。

## 四、连接稳定性优化

### 4.1 【固件·确认】监督超时 20s vs 手机 Doze

当前 `DEFAULT_DESIRED_CONN_TIMEOUT=2000`（=20s）。Android Doze/锁屏会拉长连接间隔，若实际间隔被拉到 ~1s+，20s 超时对应 ~20 个事件，理论余量充足。**保持 20s 即可**（≤32s 上限；改大反而让"链路已死"的检测变迟钝）。

### 4.2 【固件·可选】连接参数 30s 重试已覆盖"手机回溯间隔"

`SBP_PARAM_UPDATE_EVT` 每 30s 重发参数更新，专门对抗"手机在 Doze 后回溯为短间隔"与"长间隔未生效"。**保持**。

### 4.3 【App·已做】FF02 自愈链完整

3s 无 FF02 → 重订阅 → 仍无 → 拆链重建；4s 无 FF02 → 僵尸连接探测；`_verifyConnection` 判活重开订阅。**当前最完整的一环，无需再动**。

### 4.4 【App·可选】增加断连原因上报到 UI

固件串口有完整断连原因分类（0x08=链路超时 / 0x13=手机主动 / 0x16=固件主动…），但 App 收不到。可在 FF02 状态 JSON 加一个 `dc`（上次断连原因）字段，App 在"断连"提示里带上（如"信号丢失"/"手机主动断开"），帮助用户定位"为什么又断了"。**中收益，需固件+App 各改一处**。

### 4.5 【固件·观察】`1007` 固件侧 ATT 忙退避

2026-08-17 已做固件侧退避（`gattprofile.c` ATT 忙窗口诊断 + App 订阅时序配合）。**保持**。

## 五、优先级汇总表

| 优先级 | 改动 | 端 | 收益 | 风险/工作量 |
|--------|------|-----|------|-------------|
| ⭐⭐⭐ | AUTH 期间降 LATENCY+短间隔（2.1/3.1） | 固件 | 绑定验证提速 ~1s，体感最大 | 低（参数宏+触发分支，~20 行） |
| ⭐⭐⭐ | 断连广播按模式分档降速（1.1） | 固件 | 断连电流 -40~60% | 低（恢复废弃事件位，~30 行）；注意看门狗上限 2.5s |
| ⭐⭐ | 连接态活跃/空闲分档参数（1.2） | 固件 | 连接电流 240→~80µA | 中（状态机加"空闲计时"，需真机验证手机是否接受长间隔） |
| ⭐⭐ | DCDC_ENABLE 确认后开启（1.3） | 固件(宏) | 活跃/连接电流 -40% | 零代码；需硬件合规确认 |
| ⭐ | FF02 增加断连原因字段（4.4） | 固件+App | 稳定性可诊断性 | 中（JSON 扩字段 + UI 文案） |
| — | App 侧连接/绑定路径（2.3/3.3） | App | — | 已高度优化，剩余是平台行为，不建议再动 |

> ⚠️ 所有固件参数改动注意两条红线（代码注释明示）：
> 1. **广播间隔 >2.5s 会触发软看门狗误复位**（`config.h` HAL_SLEEP 注释）→ 降速上限 1s 安全。
> 2. **AUTH 30s 强断**（防占槽）要求 AUTH 能在高 LATENCY 下完成 → 空闲参数只能"AUTH 之后"生效。
> 3. 改 SNV/DataFlash 布局属破坏性（清空绑定），本次清单**不含**此类改动。

## 六、建议实施顺序（一个下午可完成前三项）

1. **固件**：`peripheral.h` 增加 `CONN_PARAM_FAST_*`（如 60ms/LAT=0）与 `CONN_PARAM_IDLE_*`（360ms/LAT=3）两组宏；`Peripheral_LinkEstablished` 立即请求 fast；`Bonding_HandleAuthResp` 成功后切 idle；`Peripheral_HandleFF03` 控制命令时切回 fast。→ 绑定提速 + 连接省电双收。
2. **固件**：恢复 `SBP_ADV_SLOWDOWN_EVT` 降速链，普通模式断连广播 600ms~1s，无App模式保持 150ms。→ 断连省电。
3. **固件**：`DCDC_ENABLE` 按硬件合规确认后置 TRUE。→ 全面省电。
4. 真机验证：连接电流、断连电流、绑定耗时（应 <1s）、走近解锁响应（应无感知劣化）。
5. 可选：FF02 加 `dc` 字段 + App 断连原因提示。
