# 连接参数与「功耗 vs 速度」权衡分析（2026-08-04）

> 背景：fix28+P15 已提交（commit b677da1）。实测连接态稳定 ~240µA、断连慢速 ~88µA，功能全通。
> 本文档分析「既降功耗又提速度」的可行性，并回答用户 5 个具体问题。仅分析，未改代码。

---

## 一、现状实测

| 阶段 | 电流 | 说明 |
|---|---|---|
| 连接初期 | ~800µA 跳动 | GATT 交互 + FF02 推送 + 加密握手，射频几乎不休眠 |
| 稳定连接 | ~240µA | 连接间隔 360ms 空转，每 360ms 唤醒收发空包（1.3% 占空比） |
| 断连慢速 | ~88µA | 5s 广播，绝大部分时间深睡 |

**240µA 主源不是广播，是连接间隔 360ms 的"心跳"唤醒**：每 360ms 射频醒来一次维持连接。
LATENCY=1 只让空闲跳 1 事件，最低仍是 ~360ms 周期。

---

## 二、影响「速度 vs 功耗」的 5 个因素

### ① 连接间隔 (MIN/MAX)
- 越小 → GATT 越快 / 发现越快，但唤醒越频繁 → 电流↑
- 当前实测 360ms：速度可接受，耗电 240µA
- 降到 30ms：发现/控制秒级，但连接电流可能 1-2mA
- **矛盾**：发现阶段想要快，空闲阶段想要慢——但连接一旦建立间隔就固定

### ② SLAVE_LATENCY
- =N 时从机可跳过 N 个连接事件不回应（前提：没数据要发）
- LATENCY=4 省电最好（空闲跳 4 事件→等效 1.8s 周期），但拖慢主动 GATT
- LATENCY=0 最快但零省电；当前=1 折中

### ③ 广播间隔 (ADV) — 只影响「发现」
- 50ms 快窗：秒发现，但广播电流大；5s 慢速：省电（88µA）但发现等最长 5s
- 已做分段：3s 快 → 5s 慢 → 5min 后 30s 超慢

### ④ 30s AUTH 超时
- 连接后必须在 30s 内完成 AUTH，否则设备主动断开
- 逼着 LATENCY 不能太高（否则 GATT 超时）

### ⑤ 手机侧 OS 行为（不可控）
- Android 后台/Doze 会主动拉长连接间隔（即便你设 40ms，系统可能拉到 360ms+）
- nRF Connect 实测 360ms 即手机裁决结果，固件 MIN/MAX 只是"建议范围"

## 三、核心方案：分段动态连接参数（未实现，待定）

```
阶段             连接间隔    LATENCY  电流      目标
────────────────────────────────────────────────────
连接握手(0-5s)   30ms       0        ~1mA      极速完成 AUTH/服务发现
已连接活跃(控制)  40ms       0        ~800µA    控制指令秒达
已连接空闲(≥3s)  360ms      4        ~80µA     深睡省电(手机仍连)
断连            5s广播       -        ~88µA     待发现
```

**实现方式（讨论稿）**：
1. 固件 AUTH 完成 + 无控制活动 3s 后，主动发 `L2CAP_ConnParamUpdateReq` 拉大到 360ms/LATENCY=4
2. 收到控制命令时先发参数更新回 30ms/0，执行后降回
3. 握手阶段仍用当前已验证的 LATENCY=1 保证 30s 内 AUTH 完成

**难点**：手机可能拒绝参数更新（尤其后台），每次更新有 ~1s 协商延迟，需"活跃期短窗口"策略。

## 四、用户 5 问逐答

### Q1：连接间隔 360ms → 240ms / 120ms 会怎样？
- **240ms**：每 240ms 唤醒一次，连接电流 ≈ 240µA×1.5 ≈ 360µA；GATT 单轮最快 240ms（比 360ms 快 33%）；AUTH 总时长略降。省电变差、速度略好。
- **120ms**：连接电流 ≈ 240µA×3 ≈ 700µA；GATT 单轮最快 120ms；接近"秒连"体验但耗电翻倍。
- 注意：最终间隔由手机裁决，固件只给范围；手机后台可能仍拉到 360ms+。

### Q2：SLAVE_LATENCY 啥意思？
- 从机（设备）被允许"偷懒"的次数。连接本应每间隔都回应主机，但设 LATENCY=N 后，设备可连续跳过 N 次不回应（只要没数据要发）。
- 例：间隔 360ms，LATENCY=4 → 设备最多 5×360ms=1.8s 才回应一次（省电），但若有数据要发会立即发。
- **副作用**：主机发 GATT 请求后，设备可能等最多 1.8s 才回 → GATT 慢。这就是 P15 把 4→1 的原因（1.8s→0.72s）。

### Q3：广播间隔现在多少？改 100ms/200ms 会怎样？
- 当前快窗 = 50ms（普通 3s 窗 / No-App 15s 窗），慢速 = 5s，超慢 = 30s。
- **100ms**：发现速度约 50ms 一半（最坏等 100ms vs 50ms），广播电流略降（占空比减半），连接态无影响。
- **200ms**：发现最坏等 200ms，更接近"按一下就扫到"但仍明显慢于 50ms；广播更省。
- 广播间隔**不影响已连接速度**（连接后用连接间隔，不用广播间隔）。

### Q4：30s AUTH 超时啥意思？
- 设备安全机制：连接建立后若 30s 内未完成 AUTH（挑战应答验证身份），设备认为"连上来的人不是主人"→ 主动断开。
- nRF Connect 无 bindCode → 永远 AUTH 不了 → 30s 后被踢（你之前看到的 status 19 断开就是它）。
- App 用默认码 123456 做 AUTH，正常 <10s 完成 → 解除超时。
- **约束意义**：逼 GATT 必须在 30s 内跑完，所以 LATENCY 不能太高。

### Q5：手机 OS 不可控，但没做低功耗前是秒连的？
- 低功耗前：连接间隔可能 30-50ms（系统默认快连），且 LATENCY=0 → GATT 极快 → 秒连。
- 现在：为省电把间隔拉到 360ms + LATENCY=1 → GATT 变慢 → 连得慢。
- **这是"省电换速度"的代价**。分段动态参数（第三节）正是要兼得：握手时用快间隔，空闲时降慢。

---

## 五、APP 内 RSSI 间隔 100ms 还有用吗？——基本没用
1. RSSI 是固件侧采样（`rssiReadPeriodMs=500` 每 500ms 读一次 GAP RSSI 经 FF02 推），APP 设 100ms 只是更频繁读"已固定的值"，不改变固件采样率。
2. 连接间隔 360ms 卡着 FF02 推送节奏，APP 设 100ms 只是重复显示旧值。
3. 真要提刷新率：改固件 `rssiReadPeriodMs` + 缩短连接间隔才有效。APP 本地节流只是徒增重绘耗电。
