# 连接提速收尾：平台首 ATT 延迟定性 + FF02 零无效推送（2026-08-18）

> 背景：commit 0ef200f 落地三项 App 改动（700ms 条件化、1000ms 盲等→FF02 信号、SN 延迟读）后，
> 真机日志（15:38）实测连接建立→AUTH OK ≈ 4.3s。本文档定性剩余耗时根因，并归档已落地的两项
> 低风险固件微优化（消除连接初期 FF02 无效推送 + 订阅瞬间首发首帧）。

## 二、剩余 ~3s 瓶颈定性（平台行为，三方收敛裁定）

### deepseek 复核的两处误读（已用户裁定 codebuddy 正确）

1. ❌ **误读「Android 自动 discoverServices 排队 3s」**
   - 核实：`utils/ble.js` 的 `notifyBLECharacteristicValueChange` 走 `uni.notifyBLECharacteristicValueChange`
     （CCCD descriptor 直写，经 `enqueueWrite` 队列），**不调用 `getBLEDeviceServices` 做全表发现**
     （仅 `readSerialNumber` 兜底路径才查服务）。
   - 铁证：MTU（22.049）与 CCCD（22.260）**相邻仅 0.2s**——若真是"discover 全表排队"，
     两者不会紧挨。真实原因 = **Android 连接后首个 ATT 事务前的链路稳定窗口（~3s），平台硬延迟**。
2. ❌ **误读「loading 有 4.3s」**
   - 核实：`connect()` 尾部 `_finalizeConnection` 立即调用 + `_waitFf02Ready(1000)` 最多 1s 兜底，
     loading 在 resolve 后 ~1s 结束，AUTH OK 是 loading 之后后台完成。

### 真实因果链
```
T0      连接成功（App resolve，loading 收尾）
T0~1s   _waitFf02Ready 最多等 1s（实际 FF02 在 T0+4.0s 才到，但不阻塞 loading）
T0+3.1s Android 放出首个 ATT 事务（MTU exchange 247）  ← 平台首 ATT 延迟
T0+3.3s CCCD 写真正到固件（FF02 订阅生效）
T0+4.0s FF02 首帧到达（优化前）
T0+4.3s AUTH OK（后台完成）
```
**剩余 ~3s = Android 首 ATT 延迟（平台行为）**：`createBLEConnection` 成功后，Android 要等
底层 BLE 链路稳定（加密/PHY/ATT 通道）才放行首个 ATT 事务。与 GATT 表大小、是否 discover 全表无关
（App 只写已知 descriptor，不 discover）。**App/固件都无实质压缩手段**。

### 已评估但放弃的优化项
| 项 | 结论 |
|----|------|
| 缩短 Android 服务发现 | 不存在（App 不 discover），且非瓶颈 |
| MTU 协商提前 | 同样被平台首 ATT 延迟排队，无法绕过 |
| 固件主动 `GATT_ExchangeMTU`（从机先发） | 收益不确定、CH582M 协议栈支持度未知、风险高，放弃 |
| 条件性注册 HID 服务（noAppMode=0 不挂） | 改 GATT 表有回归风险，收益仅 ~0.2-0.4s，放弃 |
| 提前结束 loading | **已实现**（`_waitFf02Ready` 1s 兜底），无需再落地 |
| 固件 `ret=12` 跳过本周期推送 | 被下方"CCCD 使能守卫"方案完全覆盖，冗余 |

## 三、FF02 零无效推送微优化（已软回滚：commit 1da381a → revert）

> 本节记录该微优化的原始设计与**最终被软回滚的决策**，供后续复盘。

目标：消除日志里 Android 首 ATT 延迟（~3s）窗口内，固件在 CCCD 未使能时连发 3 次
`FF02 NOTIFY FAIL ret=12 (CCCD未使能)` 的无效 ATT 尝试；并让 App 订阅完成瞬间即拿到首帧。

### 原设计（改动 1/2/3）
1. 新增 `g_ff02CccdEnabled` 标志 + `KeyGo_NotifyStatus` 入口守卫
   （`keygo_core.h/c`：`if (!g_ff02CccdEnabled) return;` 跳过未订阅阶段 FF02 发送）。
2. CCCD 写 `0x0001` 置位 + 立即 `KeyGo_NotifyStatus()` 首发首帧（`gattprofile.c`）。
3. 断连清位防残留（`peripheral.c` `Peripheral_LinkTerminated`）。

### 软回滚决策（2026-08-18 当日）
- **回滚触发**：用户实测发现"解锁/锁车变快"是**连接提速专项的连带收益**，而非本微优化直接带来。
  命令加速的真正来源是：① 固件 FF02 ATT 槽自适应退避（1007 治本，commit 2b8cd0e 批次）让出 GATT 事务槽；
  ② App SN 延迟读 + FF02 早订阅（commit 0ef200f）让 AUTH 更早完成、GATT 通道空闲。
  本微优化仅消除连接初期的 3 次降噪推送（ret=12 本就静默），对命令延迟/连接耗时**零贡献**。
- **回滚理由**：专项在 4.3s 已见底（剩余 3s 为平台首 ATT 延迟，不可压）；本改动属边际降噪，
  却引入 `g_ff02CccdEnabled` 守卫位 + CCCD 分支逻辑，增加回归面（如断连清位遗漏、守卫与周期调度耦合）。
  在疗效已达标的前提下，遵循"停止过度优化"原则，**软回滚保留真正有效的 0ef200f + 1007 治本批次**。
- **操作**：`git revert --no-commit 1da381a` → 固件 4 文件恢复至 0ef200f 状态（验证 `g_ff02CccdEnabled` 已无残留）。

### 回滚后的真实表现（预期）
- 恢复为优化前日志形态：连接初期 3 次 `FF02 NOTIFY FAIL ret=12` 重新出现（无害，静默失败）。
- 首帧回到 T0+4.0s（CCCD 使能后下一个 1s 周期才到），比"订阅瞬间首发"晚约 0.7s——**对 AUTH 总耗时无感知影响**（AUTH 仍由平台首 ATT 延迟窗口决定）。
- **解锁/锁车速度不变**：命令加速来自 1007 治本 + 0ef200f，与本微优化无关。

### 经验沉淀
- "降噪型"改动（仅消除静默失败日志、不改变功能时序）在专项见底后应优先回滚，避免无收益的代码面扩张。
- 新增任何"连接后周期推送"特征前，仍建议加 CCCD/使能守卫（见 MEMORY 铁律），但该守卫**不应用于本次被回滚的 ret=12 降噪场景**。

## 四、连接提速专项总结（截至 2026-08-18，软回滚后终态）

1. **固件侧（保留）**：GAPROLE 初始 fast（PPCP 预置 AUTH_FAST_* 40/80ms）+ AUTH 后回 slow + FF02 ATT 槽自适应退避（1007 治本，commit 2b8cd0e 批次）。
2. **App 侧（保留，commit 0ef200f）**：700ms 预清理条件化 + 1000ms 盲等→`_waitFf02Ready` FF02 信号 + SN 延迟读让出 GATT 链。
3. **已软回滚**：FF02 零无效推送微优化（原 1da381a）——降噪型边际改动，对连接/命令耗时零贡献，当日 revert。
4. **剩余瓶颈**：Android 首 ATT 延迟 ~3s（平台行为，无压缩手段）。
5. **结论**：6s → 4.3s（AUTH 快窗口生效）；用户感知 ~1s 连上。命令加速为该专项连带收益。专项已见底，停止优化。
