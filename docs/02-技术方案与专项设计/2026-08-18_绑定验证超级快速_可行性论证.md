# 绑定验证"超级快速"可行性论证：连接参数方案的正确形态

> 日期：2026-08-18
> 目的：认真论证"加两组连接参数宏 + AUTH 前后切换"能否实现绑定验证超级快速，并给出**正确实现形态**。
> 结论先行：**能显著提速（2~3.5s → ~1~1.5s），但"超级快速"（<1s）受 Android 主端裁决限制，无法 100% 保证**；且"连接后请求快参数"不是最优形态，**正确形态是"广播声明快参数 → Android 初始连接即快 → AUTH 后切回慢"**。

---

## 一、必须先厘清的 4 个物理事实

### 事实 1：连接参数的决定权在手机（主端），不在固件（从端）

BLE 中 Central（手机）与 Peripheral（固件）的连接间隔，**最终由主端裁决**。从端只能：
- ① 在**广播/扫描响应**里声明 `Slave Connection Interval Range`（期望参数）—— 主端**发起连接时参考**；
- ② 连接后发 **L2CAP Connection Parameter Update Request** 请求修改 —— 主端**可接受/拒绝/忽略**。

本项目 2026-08-04 实测已铁证：*"nRF Connect 实测 360ms 即手机裁决结果，固件 MIN/MAX 只是建议范围"*（`2026-08-04_连接参数与功耗速度权衡分析.md`）。**固件请求 ≠ 手机执行。**

### 事实 2：Android 对"从机参数更新请求"的接受度（不确定因素）

社区经验（Nordic DevZone / SO 广泛讨论）与 Android 行为：
- Android 5.0+ 支持从机发起的参数更新请求（`onConnectionUpdated` 回调），但 **Android 有自己的一套可接受参数表**（如 interval 下限、latency 上限），超出即拒绝/忽略；
- Android 9+ 倾向应用**自身的连接优先级策略**（`requestConnectionPriority`），可能覆盖从机请求；
- **不同 ROM 行为差异大**（原生 AOSP vs 华为/小米深度定制）。

→ **"连接后发快参数请求"这条路，成功率不可控。** 这是"超级快速"无法 100% 保证的根本原因。

### 事实 3：BLE 规范对从机参数请求有频率限制

Core Spec：从机参数更新请求被**拒绝后必须等待一段时间才能重发**（常见实现 30s）。这意味着**"AUTH 前请求快 → AUTH 后马上请求慢"的快速来回切换在规范层面就不被鼓励**——第二次请求很可能落在拒绝等待期内被忽略。

→ **"AUTH 前后切换"若用两次参数更新请求实现，先天受限。** 正确做法是**只用一次参数请求**（详见第三节）。

### 事实 4：连接建立时手机采用从机广播的 Slave Connection Interval Range（本项目已广播）

`peripheral.c` `Peripheral_BuildScanRspData()`（L225-230）**已经在广播里声明了**：
```
GAP_ADTYPE_SLAVE_CONN_INTERVAL_RANGE = DEFAULT_DESIRED_MIN(128=160ms) ~ MAX(256=320ms)
```
**Android 主端在发起连接时会参考这个字段**（标准 BLE 行为，社区实测多数 Android 版本会采用从机广播的期望参数作为初始连接参数）。

→ 这是本项目**没被利用的杠杆**：当前广播声明的是 160~320ms（慢），所以**手机一连接建立就是慢参数**，AUTH 全程在慢间隔下跑——这正是绑定验证慢的"隐形起点"。

## 二、绑定验证耗时拆解（为什么现在是 2~3.5s）

| 阶段 | 当前耗时 | 决定因素 |
|------|----------|----------|
| 连接建立 → FF02 订阅 | ~0.3s | App 已优化（连接即订阅） |
| NONCE 写（FF03）跨冷窗 | ~0.9s | Android 属性缓存就绪（10007 已治本，密集重试跨窗） |
| NONCE 回包 | 0.2~1s | **连接事件空窗**（慢间隔 × (LATENCY+1)）★ |
| AUTH 写 | ~19ms | 算法快（2026-08-12 实测） |
| AUTH:OK 回包 | 0.2~1.2s | **连接事件空窗** ★★ 波动主源 |
| **总计** | **~1.5~3.5s** | 波动集中在两个 ★ 的连接事件空窗 |

**结论：AUTH 快慢 ≈ 连接间隔快慢。** 若初始连接间隔是 30~60ms/LAT=0，两个空窗合计 ~100ms 级；若是 320ms/LAT=2，空窗最坏 ~1s。**当前慢的根因之一 = 广播声明了慢参数，手机初始连接就慢。**

## 三、正确方案形态（一次参数请求，而非 AUTH 前后切换）

### 方案核心：把"杠杆"用在广播声明上，让手机**初始连接即快**

```
连接前：广播 Slave Conn Interval Range = 30~60ms / LAT=0（改宏）
   ↓ 手机发起连接，参考广播采用快参数 → 初始连接即快
连接后 0~2s：AUTH 全程在快间隔下跑（NONCE 回包 + AUTH:OK 回包 ~100ms 级）
   ↓ AUTH 完成（约 1~1.5s）
连接后 4s（现有 SBP_PARAM_UPDATE_EVT）：请求切回慢参数 160~320ms / LAT=2（省电）
   ↓ 之后每 30s 重试保持慢参数（现有机制，零新增）
```

**为什么这是最优形态：**
1. **广播声明在"连接建立之前"就生效**——不需要赌 Android 是否接受连接后的参数请求（事实 2），Android 大概率直接采用广播的期望值；
2. **全程只有"一次"参数更新请求**（切慢）——避开事实 3 的频率限制（现有 4s/30s 机制正好复用）；
3. **改动极小**：改广播字段用的宏（1 处）+ 确认参数更新请求的宏（1 处）；
4. **AUTH 提速与省电不冲突**：快窗口只在连接初期（AUTH 阶段），4s 后自动切回慢参数。

### 具体改动（固件 `peripheral.h` 两个宏组）

```c
/* 广播声明 + 初始连接（快：AUTH 用） */
#define ADV_DECL_MIN_CONN_INTERVAL   24    // 30ms
#define ADV_DECL_MAX_CONN_INTERVAL   48    // 60ms
#define ADV_DECL_SLAVE_LATENCY       0

/* 连接后请求（慢：空闲省电）—— 沿用现有 DEFAULT_DESIRED_* */
#define DEFAULT_DESIRED_MIN_CONN_INTERVAL  128  // 160ms（不变）
#define DEFAULT_DESIRED_MAX_CONN_INTERVAL  256  // 320ms（不变）
#define DEFAULT_DESIRED_SLAVE_LATENCY      2    // 不变
```

- `Peripheral_BuildScanRspData()` 的 `SLAVE_CONN_INTERVAL_RANGE` 字段改用 `ADV_DECL_*`（快值）；
- `Peripheral_Init()` 的 `GAPROLE_MIN/MAX_CONN_INTERVAL` 建议同步用 `ADV_DECL_*`（与广播一致）；
- `SBP_PARAM_UPDATE_EVT`（连接后 4s 首次）继续用 `DEFAULT_DESIRED_*`（切慢）——**现有机制不动**。

## 四、预期收益与风险（诚实评估）

| 维度 | 预期 | 置信度 |
|------|------|--------|
| 绑定验证总耗时 | ~1.5~3.5s → **~1~1.5s**（AUTH:OK 回包 100ms 级） | 高（快初始间隔直接消除两个空窗） |
| "超级快速"（<1s） | **部分手机可达，无法 100% 保证** | 中（取决于 Android 是否采纳广播快参数） |
| 省电 | 无退化：AUTH 后 4s 切回慢参数，连接态仍 ~240µA | 高 |
| 风险 | ① 个别 ROM 忽略广播声明 → 收益打折但**不退化**（与现状持平）；② 快窗口期（前 4s）连接电流偏高（~800µA），但仅 AUTH 阶段 | 低 |

**验证方法**：改后真机抓固件串口 `[DIAG] LinkEst int=...`（连接建立时的初始参数）——若显示 `int=24~48 (30~60ms)` 即 Android 采纳了广播快参数；若仍显示 128+，则该 ROM 忽略广播声明，需退回现状或评估 App 侧方案（见下）。

## 五、备选/增强：App 主端主动 `requestConnectionPriority`（必生效，但成本高）

Android 主端主动调用 `BluetoothGatt.requestConnectionPriority(HIGH)`（= 11.25~15ms 间隔）**一定生效**（主端自己改自己，无裁决问题）。这是"超级快速"的唯一 100% 路径。

**但本项目不可行（成本）**：
- uni-app 的 `createBLEConnection` 内部管理 BluetoothGatt，**JS/插件层拿不到同一 Gatt 实例**；
- 原生插件（Keygo-Foreground）无法对 uni 已建立的连接调用 `requestConnectionPriority`（需要自己的 Gatt 引用）；
- 除非改造为"原生层自建连接"（推翻 uni 的 BLE 封装，侵入性极大）。

**结论**：App 侧必生效方案在当前架构下成本过高，不推荐；**固件广播声明方案是性价比最优解**。

---

## 六、最终建议

1. **实施"广播声明快参数 + 现有 4s 切慢"**（第三节，~2 处宏改动 + 确认 1 处，纯固件）；
2. **真机验证**：抓 `[DIAG] LinkEst` 确认初始间隔 + 实测绑定耗时（目标 <1.5s）；
3. 若个别手机仍慢（ROM 忽略广播）→ 接受现状（不退化），或后续单独评估该 ROM 的专项方案；
4. 本次**不做**"AUTH 前后两次参数请求切换"（规范频率限制 + Android 裁决双坑）；
5. 本次**不做**通道拆分（2026-08-18_10007根因定论与绑定提速方案.md 已论证：无用且有害）。
