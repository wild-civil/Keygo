# KeyGo 功耗优化分析（基于真实代码与 CH582 手册，2026-08-04）

> 目的：纠正此前凭经验/记忆的推断，逐项用**真实代码 + 官方实测数据**重新分析功耗优化点。
> 背景固件：v3.36.3-fix28+P15（LATENCY=2，断连恒 150ms 广播）。
> 实测（开发板好 LDO，断连+发送混合）：Min 246µA / Max 1804µA / Avg 414µA。

---

## 0. 先确立两个铁证（避免方向性错误）

### 铁证 A：CH582 Sleep 静态电流 ≈ 3.2µA（官方级实测）
参考博客园 CH582 睡眠低功耗实测（作者 oTvTo，2022-11-02）：
- 睡眠模式 `LowPower_Sleep`，RTC 唤醒：睡眠态 **3.22~3.23µA**，唤醒工作 5.4~5.5mA。
- RTC 1s 唤醒 → 周期平均 12.31µA；RTC 250ms 唤醒 → 周期平均 54.46µA。

**推论**：固件 Sleep 链路本身没问题。若实测 Sleep 态仍有 mA 级，100% 是**电源/LDO/外围**问题，不是固件。
→ 印证此前结论：自焊 PCB 用山寨 XC6206（静态 1mA+）导致 4.5mA 假象，换正品 LDO/改 DCDC 直供才是真底噪瓶颈。

### 铁证 B：睡眠模式官方**强制用内部 32K RC，禁用外部晶振**
同一实测文档 + WCH 应用笔记要点：
- 睡眠时**不要使用外部晶振**；两个晶振输入脚必须 **remap 成普通 IO**，并配置 IPU/IPD/PP，**千万不能浮空**。
- 时钟改用**内部 RC 振荡器**。
- **GPIO 浮空会非常耗电**；不用的 IO 设上拉/下拉/推挽/模拟输入均可。

**推论**：本项目 `CLK_OSC32K=1`（内部 RC）+ `GPIOA/B_ModeCfg(GPIO_Pin_All, GPIO_ModeIN_PU)`（全上拉）**正是官方推荐的最优 sleep 配置**。
→ 此前我提的"换外部 32K 晶振更省电"是**错误**的，已纠正。

## 1. 状态机轮询 2s → 4s（断连态最大头的周期性唤醒）？

### 真实代码事实（keygo_core.c:723 `KeyGo_ProcessStateMachine`）
断连态下该函数**几乎什么都不做**，核心逻辑全被门控：
- `if (g_deviceConnected && connHandle != INIT)` → RSSI 采样 `GAPRole_ReadRssiCmd`（断连态跳过）
- 加密链路检测 `linkDB_State(... LINK_ENCRYPTED)`（断连态跳过，且 `g_obsLinkEncrypted=0`）
- 脉冲看门狗 `g_actionActive`（无操作时跳过）
- 手动冷却 `g_manualCooldown`（无操作时跳过）
- **断连态实际只跑**：`Bonding_TickPairingWindow()`（配对窗口计时，仅打印/收尾）+ 少量计数器清零，然后 `tmos_start_task(SBP_STATE_MACHINE_EVT, SBP_STATE_MACHINE_PERIOD)` 自我重排。

### 分析
- 断连态每 2s 唤醒一次状态机 = **纯空唤醒**（唤醒→读几个变量→重排）。唤醒本身耗电（从 Sleep 起来跑几十 µs 内核），但**无射频、无 GPIO 动作**。
- 2s→4s 把这部分空唤醒频率减半，省的是"唤醒开销"，量级约 µA 级（参考铁证 A：250ms 唤醒平均 54µA，1s 唤醒 12µA，差 ~42µA；空唤醒比 RSSI 采样更轻，收益更小）。
- **是否有感**：
  - 断连态：状态机断连时不干活，拉长对功能**零影响**（配对窗口计时本来就在连接态才有效）。
  - 连接态：状态机负责 RSSI 采样（驱动无 App 自动解锁阈值）。4s 采样间隔 → RSSI 更新慢一拍，无 App 自动解锁判定延迟最多多 2s，**车锁场景基本无感**，但阈值调试时日志变稀。
- **结论**：低风险、小收益。**断连态可放心拉到 4s 甚至更长**；连接态拉 4s 仅影响 RSSI 实时性，对锁功能无感。

## 2. 连接态拉大连接间隔 + 提高 LATENCY 会怎样？

### 机制（BLE 协议）
- 连接间隔（MIN/MAX）决定主机-从机"通话"频率；LATENCY = 从机允许**跳过**的连接事件数（不回包也不算断连）。
- 功耗 ∝ 1 / (有效连接事件频率)。LATENCY 越大、间隔越大 → 从机醒来越少 → 越省。
- 代价：GATT 交互延迟变大（每轮最慢 ≈ (LATENCY+1) × 连接间隔）。

### 真实代码约束（peripheral.h）
- 当前：`MIN=120ms / MAX=240ms / LATENCY=2`。
- AUTH 死线 `UNBOUND_CONN_TIMEOUT_MS=30000`：服务发现 + AUTH 最坏 ≈ (LATENCY+1) × MAX × N 轮。此前 LATENCY=3 已偶发超时（实测），回退 2 才稳。
- **拉大风险**：LATENCY=4 + MAX=320ms → 最坏 (4+1)×320=1600ms/轮，AUTH 总时长可能再逼近 30s → 重现"连上---然后断"。必须小步试（如先 LATENCY=3 配 MAX=240ms 测 AUTH 是否仍稳）。

### 结论
- 连接态待机（已 AUTH、无数据）拉大间隔/LATENCY **有效降待机电流**，但**直接受 AUTH 死线约束**，不能无脑拉。
- 建议路径：150ms 广播 + AUTH 已稳前提下，试 `MIN=160 MAX=320 LATENCY=3` 实测 AUTH 时长，再决定是否到 LATENCY=4。

## 3. 系统周期事件 2s 拉长 / 与状态机合并

### 真实代码（peripheral.c:510 `SBP_PERIODIC_EVT`）
- `SBP_PERIODIC_EVT`（周期 `SBP_PERIODIC_EVT_PERIOD=2s`）：`if (g_deviceConnected) KeyGo_NotifyStatus();` —— **仅连接态发状态保活心跳**。断连态直接空转重排。
- `SBP_STATE_MACHINE_EVT`（2s）：见第 1 节。

### 合并分析
- 两者**都是 2s、都受 `g_deviceConnected` 门控**、都只在连接态干活。
- 若合并：连接态时让状态机那次唤醒顺带 `KeyGo_NotifyStatus()`，可省掉一次独立 2s 唤醒（每 2s 少一次从 Sleep 起来）。
- **收益**：连接态每 2s 省一次唤醒开销（µA 级，参考铁证 A 量级）。断连态两者都空转，合并后仍是空转，无额外收益。
- **优劣**：
  - 优：连接态少一次唤醒，逻辑集中。
  - 劣：心跳与状态机采样耦合，若以后想独立调心跳频率（如保活更频）会受限；小改但需测流量。
- **结论**：可合并，但收益小（µA 级），非优先项。

## 4. 分级广播（断连后先快后慢）

### 用户决策：不做
- 理由：突然靠近时若已掉到慢速，发现延迟大、体验差（此前 fix28 的 5s 慢速已踩过"经常连不上"）。
- 当前已采用"断连恒 150ms 不降速"（手环级体验），牺牲长期放置功耗换连接可靠性。
- 若未来要续航最大化，可加"超长无人连（如 5min）才降到 500ms/1s"的温和兜底，但**不做硬分级**。

## 5. 电池检测 30s → 60s

### 用户决策：暂保留 30s
- `SBP_BATTERY_CHECK_PERIOD=30s`：每 30s 读一次 ADC 电量。
- 拉长到 60s 仅省一次/分钟的 ADC 唤醒（ADC 采样耗电极小，µA 级），收益可忽略。
- 电池电量变化极慢，60s 甚至 120s 完全够，但当前看不出必要性，**先不动**。

## 6. LDO / 电源芯片静态功耗（真瓶颈）

### 真实情况
- 开发板（好 LDO）Sleep 实测可达 µA 级（铁证 A）。
- 自焊 PCB 用 **XC6206 山寨货**：静态电流 1mA+ → 真 Sleep 仍 4.5mA（差 100×）。
- 用户计划实测对比 **ME6215 vs XC6206** 静态功耗。

### 结论
- **这是当前实测 414µA  avg 的主要贡献者之外的最大潜在瓶颈**（若回到 PCB）。
- 优先于一切固件微调：换正品 LDO（XC6206 正品静态 3µA / ME6215 更低）或确认 DCDC 直供路径。
- 开发板上 414µA 主要来自**恒 150ms 广播**（每 150ms 发射一次），这是体验换来的，非 LDO 问题。

## 7. GPIO 漏电复查

### 真实代码（peripheral_main.c:264-265）
```c
GPIOA_ModeCfg(GPIO_Pin_All, GPIO_ModeIN_PU);
GPIOB_ModeCfg(GPIO_Pin_All, GPIO_ModeIN_PU);
```
- 全部上拉输入。**符合铁证 B"GPIO 不能浮空"要求**，是当前最优。

### 待考究点（用户提出）
- 全部上拉 vs 按信号电平配上拉/下拉/模拟输入，哪个更省？
- 官方文档：浮空**最耗电**；上拉/下拉/推挽/模拟输入均安全。差异在**上下拉电阻的静态电流**（约 µA 级，取决于引脚电平与上下拉方向是否匹配外电路）。
- 若某引脚外电路为低电平却配了上拉 → 上拉电阻持续有小电流流向外部（µA 级漏电）。**最优做法：引脚电平与外电路一致**——外部高则上拉、外部低则下拉、悬空则模拟输入。
- 自定义 PCB 切回时需逐脚核对（尤其未用的 ADC/UART 脚、KEY_POWER 驱动脚）。

## 8. 内部 vs 外部 32K 晶振，哪个更省电？

### 纠正此前错误说法
- **此前我说"外部晶振更省电"是错误的。**
- 铁证 B（官方实测 + WCH 应用笔记）：**睡眠模式应使用内部 32K RC，弃用外部晶振**。
  - 外部晶振需多挂晶振+2 电容，且晶振脚在 sleep 时必须 remap 成普通 IO 并上/下拉（否则浮空巨耗电）。
  - 外部晶振精度更高（连接稳定性好），但**更费电 + 更占脚 + 需 remap**。
- 本项目 `CLK_OSC32K=1`（内部 RC）是**正确且最省电**的选择。
- 内部 RC 精度差（±%级）对 BLE 连接略有影响，但 CH582 BLE 栈自身有时钟校准，实际连接稳定（已实测可连）。

### 结论
- **保持内部 32K RC，不改外部晶振**。要提升连接精度而非省电才考虑外部，且需配套 remap 脚，得不偿失。

### 官方建议与主流做法（补充权威依据）
> 对于 CH582 在低功耗下使用 RTC 唤醒，**官方建议和主流做法都是使用内部 32K RC 振荡器（LSI）**。在睡眠模式下使用外部 32.768K 晶振（LSE）可能会遇到**无法唤醒**的问题。

| 特性 | **内部 32K RC 振荡器 (LSI)** | **外部 32.768K 晶振 (LSE)** |
| :--- | :--- | :--- |
| **低功耗唤醒** | **稳定可靠** | **可能无法唤醒**或仅能唤醒一次 |
| **时钟精度** | 较低，有明显误差，**需要校准** | **高精度**，适合对时间要求严苛的场景 |
| **功耗** | 更低，是低功耗模式的**推荐选择** | 相对较高 |
| **硬件成本** | 无需外部元件 | 需要额外焊接外部晶振和负载电容 |

- 据此：本项目 `CLK_OSC32K=1`（LSI）不仅是省电最优，且**避免 LSE 的"睡眠后无法唤醒"硬风险**，结论进一步夯实。

## 9. 连接态"事件驱动"替代轮询（用户不清楚，解释）

### 当前机制
- 锁状态（解锁/上锁/RSSI 阈值）目前由**状态机每 2s 轮询**检测：读 GPIO、算 RSSI、比对阈值。
- 即"每隔 2s 醒来问一次：状态变了吗？"

### 事件驱动是什么
- 改为：**外部中断触发**而非轮询。例如：
  - 锁状态变化 → GPIO 外部中断（下降/上升沿）直接唤醒 MCU 处理，平时不必周期性醒来。
  - RSSI 阈值越界 → 当前仍靠轮询采样，若要事件驱动需在基带层设 RSSI 阈值中断（CH582 部分支持，但 App 逻辑依赖连续滤波值，纯中断难做 Kalman）。
- 收益：**彻底消除 2s 周期性空唤醒**，断连/待机态只剩广播包唤醒（150ms）+ 真实事件唤醒。
- 代价：大改。GPIO 中断驱动锁状态相对容易；RSSI 阈值用中断驱动 Kalman 滤波困难（需连续采样）。
- 当前代码已部分事件驱动：`SBP_GPIO_PULSE_END_EVT`、`SBP_RIDE_EXIT_LOCK_EVT` 等已是事件驱动（注释明确"兼容 HAL_SLEEP，时序确定"）。状态机轮询主要剩 RSSI 采样一项。

### 结论
- 全事件驱动是**终极省电手法**，但 RSSI 滤波天然需连续采样，难纯中断化。
- 务实做法：锁状态类用中断（已基本是），RSSI 采样保留轮询但可拉到 4s（见第 1 节）。

## 关键纠正记录
1. **外部 32K 晶振更省电 = 错误**。官方实测与文档均指向睡眠用内部 RC 最省，外部晶振更费电+需 remap 脚。
2. **"状态机 2s 是断连态最大头" = 部分错误**。断连态状态机是**空唤醒**（核心逻辑被 g_deviceConnected 门控），真正最大头是**恒 150ms 广播**（每 150ms 发射）。
3. **分级广播**因用户体验已否决，不做硬分级。
4. 当前 414µA avg 的主因 = 恒 150ms 广播（体验代价）+ 若回自焊 PCB 则山寨 LDO。
