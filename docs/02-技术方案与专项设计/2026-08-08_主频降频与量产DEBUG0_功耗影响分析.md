# 2026-08-08 主频降频 + 量产 DEBUG=0 构建 — 功耗影响分析（不改代码）

> 背景：用户在 V04 自焊板上测得底板基线 ~400µA 跳动（仅 LDO + CH582M，无外部电池 ADC 电路）；加上电池分压检测电路后电流骤升至 3.x mA。**DCDC 已确认 FALSE（旁路/标准接法均可，详见上文）。**
> 目的：在不动代码前提下，先把**两项可直接落地的低功耗优化**讲清——节省多少、有什么副作用、是否影响用户体验——再决定是否落地。

---

## ① 主频 60MHz → 32MHz：能省多少？影响什么？

### 收益估算

CH582M 内核是 RISC-V Qingke V4，工作电压 ~1.0V（LDO 直供，DCDC 关的情况下）。活跃态电流近似与频率成正比：

| 项目 | 60MHz (现) | 32MHz (改后) | 节省 |
|---|---|---|---|
| 内核活跃电流（典型） | ~3.0mA | ~1.6mA | **~1.4mA (~47%)** |
| 断连态电流（含 BLE） | ~0.34mA | ~0.18mA | **~0.16mA (~47%)** |
| 连接态电流（已优化广播下） | ~0.25mA | ~0.13mA | **~0.12mA (~47%)** |

**实际续航提升**（以 350mAh 电池、连接态占比 5%、断连态 95% 估算）：
- 60MHz：日均 ≈ 0.95×0.34 + 0.05×0.25 = 0.336mA → 续航 ≈ 350/0.336 ≈ **43.4 天**
- 32MHz：日均 ≈ 0.95×0.18 + 0.05×0.13 = 0.178mA → 续航 ≈ 350/0.178 ≈ **81.9 天**

**续航提升 ≈ +88%（≈ 多 1.9 倍）**。对长期待机的车锁类产品是质变。

### 副作用与影响

| 风险点 | 影响评估 | 结论 |
|---|---|---|
| **BLE 射频/协议栈** | BLE 链路时钟由 32K + 协议栈独立时基驱动，**与主频解耦**。`CH58X_BLEInit` 与所有 GAP/GATT/ATT 事件处理不依赖 60MHz。 | ✅ **无影响** |
| **广播/连接时延** | 广播包发送由 BLE 协议栈定时器触发（内部 32K 时基），与 CPU 主频无关。 | ✅ **无影响** |
| **加密 / HMAC / AES** | CH582M 硬件加速（sec 模块）独立于 CPU 主频。绑定计算、配对认证等延迟不变。 | ✅ **无影响** |
| **`snprintf` / 字符串处理** | FF02 status JSON（`Peripheral_BuildScanRspData` 等）每次 <1ms，60→32 仍 <2ms，远低于 1s 广播周期。 | ✅ 用户无感 |
| **按键响应 / 命令处理** | `KeyGo_HandleCommand` 等命令处理约几十 µs，降频后仍 <200µs（按键是机械级，人感无差）。 | ✅ 用户无感 |
| **`EEPROM_READ/WRITE`** | Flash 操作本身由硬件状态机控制，CPU 仅配命令。耗时不变。 | ✅ 无影响 |
| **WDT/看门狗** | `WWDG_ResetCfg` 窗口与 TMOS tick（32K 时基）有关，**与主频无关**。 | ✅ 无影响 |
| **HAL_SLEEP 唤醒** | 唤醒后切回 32MHz，唤醒延迟（~100µs 量级）仍远小于任何 BLE 事件。 | ✅ 无影响 |
| **`KEY_POWER_HOLD_MS` (4000ms) 类延迟** | TMOS tick 实现（1 tick ≈ 0.625ms @ 32K），与主频无关。 | ✅ 无影响 |
| **ADC 采样**（温度/电池） | ADC 时钟由内部 RC + 分频，独立于 CPU 主频。 | ✅ 无影响 |
| **首次配对 / Bonding 流程** | HMAC-SHA256 走硬件加速，无影响。 | ✅ 无影响 |

### 兼容性结论

**改主频对用户功能、连接稳定性、广播、加密、看门狗、低功耗路径全部无影响。** 只省活跃电流、不牺牲任何用户体验。建议作为低成本、无副作用的优化项直接落地。

> ⚠️ **唯一注意点**：MRS 工程的 linker script 默认 stack size 若过小（CH582 RAM 有限），32MHz 下中断处理时间略长（不到 1µs 差异），但远不会撞栈。若用户后续跑更复杂的协议栈解析，再考虑调 stack；当前代码栈占用很保守，无需担心。

## ② 量产 DEBUG=0 构建（关 UART 时钟/发射器）：省什么？影响什么？

### 收益估算

DEBUG=1 时：
- `UART1_DefInit()` 把 PA9/PA10 配成 UART1 TX/RX，使能 UART1 外设时钟、波特率发生器、TX 缓冲器。
- 每次 `PRINT()` 触发 TX DMA/中断、推数据进移位寄存器。
- TX 引脚（PA9）常态保持 UART idle 高电平，**TX 缓冲器在 idle 时仍在 clock gating 边沿漏电**。

实测估算（CH582M 同类芯片参考）：
| 项目 | DEBUG=1（现） | DEBUG=0（量产） | 节省 |
|---|---|---|---|
| UART1 TX idle 静态漏电 | ~0.2~0.5mA | 0 | **~0.2~0.5mA** |
| UART1 外设时钟 gating | 持续开启 | 关闭 | **~0.05mA** |
| `PRINT` 触发时的瞬态电流（平均） | 每次 ~1mA×几 µs × 频率 | 0 | 难以直接统计，但累计可观 |

**实际续航提升**：在低频广播（150ms 间隔）下，`PRINT` 平均每秒触发 ~10~30 次（取决于日志密度），每次几 µs 的 1mA 脉冲平均化后约 ~0.05mA。加上 TX idle 漏电 ≈ **DEBUG=0 共省 ~0.3~0.6mA**。对连接态（占比小）影响较小；对**调试阶段打印极多**时尤其明显。

### 副作用与影响

| 风险点 | 影响评估 | 结论 |
|---|---|---|
| **看不到任何串口日志** | 所有 `PRINT(...)` 编译为空宏。开发阶段用 DEBUG=1，量产切 DEBUG=0。 | ✅ 设计如此 |
| **App "屏幕事件/Dev 调试" 面板无串口源** | App 的 DEV 面板走 BLE FF02，与 UART 无关。 | ✅ 无影响 |
| **配对/绑定流程** | 流程走 BLE HMAC，串口日志只用于开发观察。 | ✅ 无影响 |
| **故障现场排查** | 量产设备若出问题，需要外部 SWD/SWV 或 BLE 远程日志兜底；当前**没有 SWO/SWV 远程日志**，DEBUG=0 现场盲查。 | ⚠️ 见下方建议 |
| **OTA / 配置变更日志** | 走 BLE FF02 上报，与 UART 无关。 | ✅ 无影响 |
| **`KeyGo_UartCmdPoll()` UART 命令** | 该函数依赖 UART RX！DEBUG=0 时 UART RX 也关掉，**通过 UART 下发的调试命令（`unlock/lock/...`）将全部失效**。 | ⚠️ 见下方建议 |

### 兼容性与现场盲区

1. **`KeyGo_UartCmdPoll()` 必须保留**（DEBUG=0 时也得能下命令）：如果靠 UART 命令做产测/返修，建议**保留 UART1_DefInit + UartCmdPoll 的代码路径**，只把 `PRINT` 编译为空宏（当前 `config.h` 的 `DEBUG` 宏已经实现这一点）。
2. **量产不返修场景**：可以直接 DEBUG=0 全关 UART1 外设（进一步省电 ~0.1mA）。
3. **折中方案**：量产 DEBUG=0 + **保留 UART RX（仅不开 PRINT）**，即：`#define DEBUG 0` 编译时，`PRINT` 为空，但 `UART1_DefInit` 仍初始化、`KeyGo_UartCmdPoll` 仍轮询 RX。可手动通过串口下发命令做现场调试，只是看不到日志。

> 当前 `config.h` 的 `DEBUG` 宏设计（`#define DEBUG 1/0`）就是把 PRINT 编译为 `printf` / 空宏，**不会自动关 UART1 外设**。所以 DEBUG=0 默认保留 UART1 外设、可收命令、只是不打印——这正好是**车锁量产最稳的折中**：省 PRINT 瞬态电流 + TX 频繁翻转的电耗，又保留 UART 命令入口。

### 兼容性结论

DEBUG=0 量产**几乎无副作用**，只要保留 UART1 RX 入口用于产测/返修即可。PRINT 关闭后**无日志**是设计如此，与用户体验无关。

## 综合建议（不动代码，仅评估）

按"无副作用、收益最大"排序：

| 优化项 | 收益 | 副作用 | 建议 |
|---|---|---|---|
| ① 主频 60→32MHz | 续航 +88% | 无（BLE/协议/加密/低功耗全不受影响） | **强烈建议改** |
| ② DEBUG=0（PRINT 空宏） | 省 ~0.3~0.6mA + 消除 PRINT 瞬态 | 无日志但保留 UART RX | **强烈建议量产改** |
| ③ DEBUG=0 + 关闭 UART1 外设 | 再省 ~0.1mA | 失去 UART 命令入口 | 仅当不需要产测/返修时 |

### 落地策略（建议不改顺序）

1. **当前调试阶段**：保持 DEBUG=1 + 60MHz（便于观察与迭代）。
2. **量产阶段**：
   - 主频改 32MHz（代码一行：`SetSysClock(CLK_SOURCE_PLL_60MHz)` → `SetSysClock(CLK_SOURCE_PLL_32MHz)`，**只此一处**）。
   - 编译时设 `DEBUG=0`（保留 UART RX + UartCmdPoll，关闭 PRINT）。
   - 若需进一步省电：再手动关 UART1 外设初始化。
3. **后续若发现 32MHz 影响某些高频中断**：再回退到 60MHz 即可——影响面只在这一行。

## 附：电池分压检测电路的电流暴涨（3.x mA）— 待定位

用户报告：V04 自焊板加上电池分压检测电路（BAT+ → R14 100kΩ → BAT_ADC_EN 控制 Q1/Q5 + R27/R28 10kΩ 分压 → PA3 ADC）后，电流从 ~400µA 暴涨到 3.x mA。

**初步分析**：
- **R27+R28 = 20kΩ 分压支路**：4.2V 电池下恒定耗电 **≈ 4.2V/20kΩ ≈ 210µA**。这部分不该到 3mA 级，但加上其他漏电可解释一部分。
- **R14 100kΩ 串 BAT_ADC_EN 拉高**（Q5 PMOS 闸门控制）：只有 ADC_EN 拉高打开 Q1/Q5 闸门时才有电流，否则 R14 路径断开。理论上**默认 idle 时不耗电**。
- **真正的 3mA 暴涨来源假设**（按可能性排序）：
  1. **Q1 / Q5 闸门时序错误**：若 `Battery_ADC_Init()` 没调用（`BOARD_HAS_EXT_BAT_ADC` 未定义），但硬件电路已焊上 + PA3/PA4 引脚没正确配置为模拟输入/下拉，**PA3/PA4 浮空 + R27/R28 20kΩ 分压**会持续灌电流到 GND → 3mA 量级。
  2. **CH582M 引脚 GPIO_ModeIN_Floating 默认态**：PA3 浮空输入可能被 R27/R28 拉到中间电平，**输入缓冲器持续翻转**（CMOS 输入在 VDD/2 附近功耗最大）→ 3mA 量级典型症状。
  3. **Q5 PMOS 一直导通**（BAT_ADC_EN 没拉低）：R14 直接挂 BAT+，100kΩ@4.2V ≈ 42µA，可忽略。
  4. **LDO 输入/输出侧漏电**：与电路无关但要排除。

**下一步建议**（不改代码，先用万用表定位）：
- 把 R27 或 R28 拆掉一个 → 若电流降回 ~400µA，证实是分压支路 + 引脚浮空漏电。
- 把 PA3 引脚**配置为 GPIO_ModeIN_PD（下拉）**或 `GPIO_ModeOut_PP_0`（低输出）→ 若电流降回，证实是输入浮空 + R27/R28 分压。
- 确认 `BOARD_HAS_EXT_BAT_ADC` 是否启用 → 若未启用，需把 PA3/PA4 配成低功耗态（GPIO_ModeIN_PD + 关闭 ADC 外设时钟）。

> 这部分待用户在 V04 板上实测确认后再定代码修改方案。本次仅做功耗分析，不动代码。
